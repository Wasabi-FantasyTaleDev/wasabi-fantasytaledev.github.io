서버 설정

Bubble Fighter Fantasy에는 고정된 서버 구성 요소 집합이 없습니다. profiles/ 아래의 프로필이 실행할 플러그인 행, 제공할 클라이언트 빌드, 열 포트, 사용할 저장소를 결정합니다. 이 페이지는 프로필이 실행 중인 서버가 되는 과정, 구성 파일의 위치, 환경 변수와 포트의 동작 방식, 영속성과 클라이언트 데이터를 전환하는 방법을 설명합니다.

대상 독자: 서버가 실행하는 내용을 바꿔야 하는 운영자와, 시작 전에 실제 구성을 확인해야 하는 개발자입니다.

시작하기 전에:

  • 서버를 한 번 빌드하십시오. dotnet build BubbleFighter.Fantasy.sln -c Release가 경고 0개로 끝나야 합니다. 설치를 참고하십시오.
  • 저장소 루트에서 터미널을 여십시오. 이 페이지에서 dotnet run을 사용하는 명령은 현재 디렉터리가 저장소 루트라고 가정합니다. 프로필, 패킷, 클라이언트 데이터가 작업 디렉터리를 기준으로 확인되기 때문입니다.
  • 실제 배포에서는 .env.example을 .env로 복사하십시오. MySQL을 비활성화하거나 메모리 또는 SQLite를 사용하는 점검에는 BFF_MYSQL_* 변수가 필요하지 않습니다. 실제 자격 증명을 커밋할 파일에 넣지 마십시오.
  • 게임 빌드를 시작할 계획이라면 클라이언트 데이터를 준비하십시오. 저장소에는 포함되어 있지 않습니다. 이 페이지의 "클라이언트 데이터" 절을 참고하십시오.

설정 작동 방식 ​

서버를 시작하는 방법은 두 가지입니다.

  • bff run --profile <id>는 YAML 파일에서 프로필을 구성하고 그 행을 시작합니다. 아래의 모든 절은 이 경로를 설명합니다.
  • bff start(실행 파일을 인수 없이 시작할 때도 사용)는 설치 도우미와 관리 행이 포함된 패키지된 최초 설치 프로필을 실행합니다. 이 경로는 저장소 .env를 의도적으로 읽지 않습니다. 이 페이지의 "환경 변수" 절을 참고하십시오.

구성 순서 ​

프로필은 계층으로 구성되며, 뒤 계층이 앞 계층의 결과를 바꿉니다.

  1. profiles/<id>/profile.yaml은 프로필 ID, 제공할 클라이언트 빌드, 사용할 번들, 자체 vars, 적용할 패치 파일을 선언합니다.
  2. profiles/bundles/<name>.yaml의 각 번들이 파일 순서대로 플러그인 행을 제공합니다.
  3. patches:에 나열된 순서대로 프로필의 패치 파일을 적용합니다. 빌드 프로필은 보통 자체 patch.yaml을 적용한 뒤 profiles/bundles/shop-supplement-lucci.yaml 같은 공용 보충 패치를 적용합니다.
  4. 프로필이 profiles/<id>/local.patch.yaml을 나열하면 그 파일을 그다음에 적용합니다. 이 파일은 Git에서 제외되며 없으면 조용히 건너뛰므로, 개발자 재정의를 두기에 적합합니다.
  5. 명령줄의 각 --patch <file>은 모든 프로필 패치 뒤에 주어진 순서대로 적용됩니다.
  6. 문자열 값은 프로필의 vars와 프로세스 환경을 기준으로 보간됩니다. --dump-config가 최종 결과를 보여 줍니다.

명령줄 패치가 마지막에 적용되므로, 로컬 재정의 파일이 persistence.mysql을 특정 데이터베이스로 가리키더라도 명령줄 패치로 한 번의 실행에서 끌 수 있습니다.

플러그인 행 ​

실행되는 모든 것은 플러그인 행입니다. 행은 플러그인 구현을 지정하고 설정을 전달합니다.

yaml
- id: admin.http
  plugin: admin.http
  config:
    listen: "${BFF_ADMIN_HOST:-127.0.0.1}:${BFF_ADMIN_PORT:-7300}"
키필수의미
id예패치와 관리 API가 사용하는 안정적인 행 식별자입니다. 한 프로필 안에서 고유합니다.
plugin예플러그인 디렉터리에서 검색된 플러그인 구현 id입니다.
config아니오플러그인의 옵션 형식에 바인딩되는 매핑입니다. 알 수 없는 키는 바인딩에 실패합니다.
disabled아니오true이면 행은 구성에 남지만 활성화되지 않습니다. 기본값은 false입니다.

고급 행은 parent_id, isolated_services, version, lifecycle도 선언할 수 있습니다. 이 키들은 중첩, 빌드별 서비스 격리, 리소스 예산을 제어하며, 제공되는 프로필은 필요한 곳에 이미 설정해 두었습니다. 배포 설정이 아니라 프로필 정의의 일부로 취급하십시오.

서버는 목록 순서가 아니라 "필요한 서비스가 언제 사용 가능한지"에 따라 행을 활성화합니다. 활성화된 두 행이 같은 서비스 인터페이스를 게시할 수는 없습니다. 레지스트리가 두 번째 등록을 거부하기 때문입니다. 이 때문에 한 번에 하나의 영속성 공급자만 활성화되며, 저장소 전환은 런타임 스위치가 아니라 구성 변경입니다.

패치 작업 ​

패치 파일은 단일 키 작업으로 이루어진 YAML 목록입니다.

작업형식효과
replace{id, plugin?, disabled?, config}지정한 행을 교체합니다. 주어진 config는 행 구성 전체를 교체합니다.
set{id, config: {...}}지정한 구성 키만 바꾸고 나머지는 유지합니다. null 값은 키를 제거합니다.
insert행 목록새 행을 추가합니다.
remove행 id해당 행을 제거합니다.

행이 없으면 replace와 set이 실패하고, 알 수 없는 작업은 구성을 실패시킵니다. 로컬 점검에 사용하는 메모리 격리 패치는 아주 작은 replace 패치입니다.

yaml
- replace:
    id: persistence.mysql
    disabled: true
- replace:
    id: persistence.memory
    disabled: false

보간과 검증 ​

${VAR}는 변수 값을 삽입하고 ${VAR:-default}는 기본값을 제공합니다. 프로필의 vars와 프로세스 환경 모두 변수를 정의하지 않았고 기본값도 없으면 구성이 실패하며 파일, 행, 변수를 알려 줍니다. 프로필 자체 vars가 같은 이름의 환경 변수보다 우선하며, 비활성화된 행은 보간되지 않습니다.

구성 바인딩은 snake_case 키를 플러그인의 형식화된 옵션에 매핑합니다. 알 수 없는 키, 잘못된 형식, 범위를 벗어난 숫자, 옵션 검증 실패는 하나의 Invalid configuration for row '<id>': ... 오류로 함께 보고됩니다.

인벤토리 게시 제한 ​

dialect.messages 행은 연결별로 인벤토리, 상점 상태 및 구형 과학실 완료 결과를 순서대로 게시합니다. max_inventory_publications_per_connection은 실행 중인 게시와 대기 호출의 합계를 제한합니다(기본값 8, 범위 1..256). max_shop_sessions는 시간 기준이나 승인된 게시를 보유한 연결 수를 제한합니다(기본값 512, 범위 1..65536). 폐기되었지만 아직 종료되지 않은 작업도 계산에 포함됩니다. 다른 연결은 독립적으로 게시할 수 있습니다. 어느 한도든 초과하면 대기 호출을 추가하지 않고 즉시 실패합니다.

연결 종료 또는 행 언로드는 대기 호출을 취소하고 진행 중인 준비를 무효화하므로, 지연된 호출이 이전 시간 기준을 다시 설치할 수 없습니다. 결정적인 인코딩 오류는 기존 시간 기준을 유지합니다. 전송 순서가 시작된 뒤 실패하면 해당 연결의 게시 상태를 폐기하고 연결 종료를 요청합니다. 이미 커밋된 인벤토리는 유지되며 정리 과정에서 비용을 다시 차감하거나 아이템을 다시 지급하지 않습니다. 대기 한도를 높여도 게시는 클라이언트 확인이나 데이터베이스 트랜잭션이 되지 않습니다.

행 안의 경로는 프로세스 작업 디렉터리를 기준으로 확인됩니다. dotnet run을 사용할 때는 저장소 루트에서, 게시된 Host를 사용할 때는 릴리스 디렉터리에서 실행하십시오. 다른 위치에서 시작하면 --profiles-dir를 전달해야 하며, packets와 client-data 경로는 여전히 작업 디렉터리를 기준으로 확인된다는 점에 유의하십시오.

실행 전 확인 ​

현재 체크아웃이 제공하는 프로필과 검색된 플러그인 구현을 나열합니다.

sh
dotnet run --project src/BubbleFighter.Fantasy.Host -c Release -- profiles list
dotnet run --project src/BubbleFighter.Fantasy.Host -c Release -- plugins list

profiles list는 각 줄에 프로필 id, 탭, 설명을 출력합니다. 이 릴리스에는 총 19개 프로필이 있습니다(클라이언트 빌드 프로필과 all, management, setup). plugins list는 플러그인 id, 버전, 지원하는 클라이언트 빌드, 출처를 출력합니다. --plugin-root <dir>(반복 가능)로 검색 위치를 다른 디렉터리로 지정할 수 있습니다.

서버를 시작하지 않고 실제 구성을 출력합니다. 실제 데이터베이스를 가리키는 개발자 .env나 local.patch.yaml에 접속하지 않도록 항상 메모리 격리 패치를 추가하십시오.

sh
dotnet run --project src/BubbleFighter.Fantasy.Host -c Release -- run --profile kr-812 --patch tools/local-checks/isolated-memory.patch.yaml --dump-config

덤프는 각 행의 id, plugin, 행을 제공한 source 파일, 설정된 경우 disabled, 수명 주기 예산, 보간된 config를 나열합니다. 포트나 저장소를 바꾸기 전에 읽어 보십시오. 서버가 실제로 실행할 구성 그대로입니다. 구성이 실패하면 Host는 stderr에 error: <message>를 출력하고 종료 코드 1로 끝납니다. 메시지는 실패한 파일, 행, 키를 알려 줍니다.

환경 변수 ​

로드 규칙 ​

  • start를 제외한 모든 명령은 먼저 작업 디렉터리에서, 다음으로 Host 디렉터리에서 위로 올라가며 BubbleFighter.Fantasy.sln 또는 .git 항목이 있는 저장소 루트를 찾습니다. 그곳에 .env가 있으면 아직 설정되지 않은 변수에만 값을 적용합니다.
  • 이미 존재하는 프로세스 환경 변수가 우선합니다. .env는 빈 곳을 채울 뿐 셸이나 서비스 관리자를 덮어쓰지 않습니다.
  • start는 저장소 .env를 절대 읽지 않습니다. 최초 설치 프로필은 프로세스 환경과 --state-dir에서 자체 변수를 받습니다.
  • 파일은 UTF-8로 읽으며 크기 제한은 64 KiB입니다. 각 줄은 KEY=VALUE이고 export KEY=VALUE도 허용됩니다. 값은 따옴표로 감쌀 수 있고, 공백 뒤의 인용되지 않은 #은 주석을 시작하며, 형식이 잘못된 줄은 파일 경로와 줄 번호를 포함해 실패합니다. 값은 절대 로그에 남지 않습니다. 파일을 읽으면 콘솔에 Loaded unset variables from <path>.가 출력됩니다.
  • 릴리스 디렉터리에는 솔루션 파일이나 .git 항목이 없으므로 게시된 Host 옆에 복사한 .env는 읽지 않습니다. 배포에서는 프로세스 환경, 서비스 관리자 또는 컨테이너 환경으로 변수를 설정하십시오.

포트와 주소 ​

BFF_BIND_HOST는 서버가 수신 대기하는 인터페이스이고, BFF_PUBLIC_HOST는 서버가 클라이언트에 알려 주는 주소입니다. NAT 뒤에서는 두 값이 다를 수 있습니다. 클라이언트에 닿는 인터페이스에 바인딩하고, 클라이언트가 실제로 접근할 수 있는 공용 주소를 알리십시오. BFF_PUBLIC_HOST를 루프백 기본값으로 두는 것은 클라이언트가 같은 머신에서 실행될 때만 유효합니다.

리스너 포트는 보통 빌드별 변수와 vars를 통해 프로필에서 옵니다. 이 릴리스의 두 기준선은 다음과 같습니다.

영속성 ​

핵심 번들은 세 가지 영속성 행을 제공합니다.

행지속성사용 시점
persistence.memory프로세스 수명 동안만 유지되며 재시작 시 초기화됩니다.일회성 로컬 점검과 테스트.
persistence.sqlite로컬 저장 파일 하나입니다.데이터베이스 서버 없이 영속 데이터가 필요한 단일 호스트.

한 번에 하나의 공급자만 활성화할 수 있습니다. 레지스트리가 같은 저장소 인터페이스의 두 번째 등록을 거부하므로, 같은 패치에서 하나만 활성화하고 나머지 둘을 비활성화해야 합니다. 핵심 번들에서는 MySQL 행이 활성화되어 있고 나머지 둘은 비활성화되어 있으며, 패치가 이를 전환합니다.

패치로 공급자 전환 ​

기본 MySQL 구성에서 SQLite로 전환합니다.

yaml
- replace:
    id: persistence.memory
    disabled: true
- replace:
    id: persistence.sqlite
    disabled: false
    config:
      database_path: "${BFF_SQLITE_DATABASE_PATH}"

MySQL로 돌아가려면 persistence.mysql을 disabled: false로 바꾸고 활성화한 다른 공급자를 비활성화하십시오.

MySQL ​

기본 연결 문자열은 BFF_MYSQL_* 변수를 보간하고 SslMode=none을 고정합니다. TLS가 필요한 배포는 번들을 수정하지 말고 패치에서 connection_string 전체를 덮어쓰십시오.

행이 활성화되면 연결을 열고 SELECT 1을 실행합니다. 암호 누락, 잘못된 연결 문자열, 서버 접속 불가는 행을 실패시키며, 시작은 저장소 없이 계속 실행되는 대신 실패를 보고합니다. auto_migrate의 기본값은 true이며, 이때 플러그인이 내장 마이그레이션을 적용합니다.

  • 마이그레이션 스크립트는 NNNN_description.sql 이름의 내장 리소스이며 파일 이름 순서로 적용됩니다. 이 릴리스의 최고 버전은 0032입니다.
  • schema_migrations를 먼저 만들고(없는 경우), 이후 각 대기 버전이 자체 트랜잭션에서 실행되고 기록됩니다. 콘솔에는 Applied migration <version> (<name>).이 출력됩니다.
  • 이름이 잘못되었거나, 버전이 중복되었거나, 내용이 빈 스크립트는 건너뛰지 않고 실행을 실패시킵니다.
  • 마이그레이션은 순방향 전용입니다. 다운그레이드 경로가 없으므로, 이전 서버 바이너리는 새 릴리스가 마이그레이션한 데이터베이스에서 실행되지 못할 수 있습니다. 백업과 롤백 절차는 배포를 참고하십시오.

SQLite ​

SQLite 행은 절대 database_path를 요구하며, 이 옵션은 상대 경로를 거부합니다. 릴리스를 교체해도 사라지지 않도록 파일을 릴리스 및 로그 디렉터리 밖에 두고, 실행 중인 두 서버가 하나의 저장 파일을 공유하지 않도록 하십시오. 이 행에는 플레이어 수, 계정 수, 데이터베이스 크기, 잠금 대기 한도도 있으며 같은 구성 매핑에서 설정할 수 있습니다.

메모리 공급자는 같은 저장소 인터페이스를 제공하는 경계가 정해진 프로세스 내 저장소입니다. 상태는 종료 시 사라지며, 이 행은 의도적으로 데이터베이스 팩토리를 게시하지 않습니다. 메모리와 MySQL은 상호 배타적입니다.

전적 기록 ​

ingame의 record_battle_statistics 기본값은 false입니다. 활성화하려면 전적을 명시적으로 지원하는 진행 저장소, 레벨 표 및 공통 결과 전송기가 필요합니다. 승인된 버블, 팡, 도움, 사망 및 점수를 게임 모드별로 최종 결과와 함께 저장합니다. 진행 중 이탈은 탈주로 기록하며 완료 보상을 지급하지 않습니다. 완료 기록은 결과 화면을 보내기 전에 정산하므로 결과 화면에서 나가도 완료한 경기가 사라지지 않습니다. 로딩 실패와 취소된 경기는 결과를 만들지 않습니다.

Memory, MySQL 및 SQLite가 이 옵션을 지원합니다. MySQL 마이그레이션 0039는 player_battle_records를 추가하고 SQLite 스키마 9는 플레이어 스냅샷에 모드별 통계를 추가합니다. 두 영구 저장소는 통계, 진행 상태, 지갑 보상과 기존 경기 영수증을 하나의 트랜잭션으로 저장합니다. 데이터베이스를 다시 열어도 기록이 유지되며 같은 경기를 재시도해도 중복 누적되지 않습니다. 기존 영수증에 새 통계를 소급하여 추가하지 않습니다. 업그레이드 전에 저장소를 백업하세요. 이전 SQLite 판독기는 스키마 9를 거부합니다. 과거에 기록되지 않은 전적은 복원하지 않습니다. 모든 저장소의 max_battle_modes_per_player 기본값은 128이며 MySQL과 SQLite의 범위는 1..4096입니다. 모드 한도에 도달하면 기록을 제거하지 않고 새 정산 전체를 거부합니다. Memory는 임시 저장소이며 max_battle_settlements_per_player(기본값 4096)도 제공합니다. 영구 저장소는 기존 데이터베이스 경기 영수증을 유지합니다.

폭파 시리즈는 다음 라운드 로딩 중에도 하나의 경기 식별자와 누적 수치를 유지합니다. 이미 진행한 라운드 사이에서 상대 팀이 이탈하면, 다음 이탈이 결과 표시를 취소하기 전에 남은 최종 참가자를 기록합니다. 최초 로딩만으로는 경기가 성립하지 않습니다. 정산 재시도 횟수는 제한되며 최종 실패는 로그에 남습니다. 임의의 지속적인 저장 장애를 복구하는 영속 outbox는 없습니다.

캐릭터 외형과 기록된 전적 ​

lobby.fighter_info는 조회 대상 온라인 계정의 캐릭터 가방에서 현재 착용한 아이템을 읽고, 만료되거나 수명이 소진된 항목을 제외합니다. 캐릭터 정보 응답 전에 대상의 장비 캐시를 전송합니다. 캐릭터가 없거나 여러 개 선택되어 있거나 로그인 세션이 교체되었다면 성공 스냅샷을 반환하지 않습니다. 조회는 읽기 전용이며 같은 빌드와 데이터 영역의 온라인 플레이어로 한정됩니다. 별도 프리셋 페이지나 인스턴스별 속성을 만들어 보내지 않습니다.

별도 옵션 lobby.fighter_battle_statistics의 기본값은 false입니다. 활성화하려면 fighter_info와 같은 데이터 영역의 전적 저장소가 필요합니다. 원본 주 페이지인 노템/아이템에는 모드 1, 3의 기록된 승, 패, 무, 도망, 버블, 팡, 헬프 합계만 전달합니다. 다른 모드, 서버 개인 점수와 아레나 계급은 표시하지 않습니다. 각 클라이언트가 자신의 무승부 규칙에 따라 구성 수치로 경기 수와 승률을 계산합니다.

주 모드의 기록이 없거나 실제 수치가 클라이언트의 부호 있는 연산 범위를 넘으면 원본 실패 응답을 보냅니다. 수치를 자르거나 축소하거나 0인 전체 경력으로 대체하지 않습니다. 옵션을 끄면 외형 조회는 원본 생성자의 통계 기본값을 유지하며, 그 값은 실제 기록이 아닙니다. Memory는 현재 프로세스에서 기록한 경기만 포함하며 원래 서버의 전체 경력이나 랭크 참가 규칙을 복원하지 않습니다.

검토한 주 페이지 구조는 kr-1256(KR2026), kr-812, id-400, id-1809, cn-324, cn-717, cn-774, tw-454, cn-279, cn-406, cn-706, cn-404, cn-408을 포함합니다. TW454의 전체 캐릭터 정보 교환은 별도로 BFF_TW_454_FIGHTER_INFO=false에 의해 제어됩니다. true로 설정해야 방언과 로비 바인딩이 함께 활성화됩니다. 구조 검토는 실제 클라이언트 검증 완료를 의미하지 않습니다.

격리된 단일 빌드 프로필에서 다음 패치를 tools/local-checks/isolated-memory.patch.yaml과 함께 적용합니다. set은 기존 프로토콜, 레벨과 결과 설정을 유지합니다. 필요한 기능이 없으면 시작이 실패하며 가짜 데이터를 만들지 않습니다.

yaml
- set:
    id: ingame
    config:
      record_battle_statistics: true
- set:
    id: lobby
    config:
      online_players: true
      fighter_info: true
      fighter_battle_statistics: true

커플 관계 저장소 ​

메모리 행은 ICoupleStore로 프로세스 내부 커플 상태를 제공합니다. couples 설정의 한도는 max_relationships(기본 4096, 범위 1–65536), max_pending_invitations(1024, 1–65536), max_pending_per_account(16, 1–1024), max_completed_invitations(1024, 1–65536), max_message_length(UTF-16 코드 단위 512개, 1–4096), max_authority_length(UTF-16 코드 단위 128개, 1–1024)입니다. SQLite와 MySQL도 이 계약을 제공합니다. 수락한 관계, 생성 시간과 반지 선택은 재시작 후에도 유지되지만 대기 중인 초대와 완료 응답 기록은 유지되지 않습니다. 트랜잭션이 두 사람의 관계를 함께 저장하며, 한 계정은 다른 커플의 어느 위치에도 중복 참여할 수 없습니다. MySQL 마이그레이션 0060은 couples와 couple_members를 추가합니다. 이 브랜치의 SQLite 스키마는 15이며 다른 미병합 마이그레이션과 통합할 때 번호를 조정해야 합니다.

lobby 행의 couples는 기본적으로 활성화되며 커플 바인딩이 검증된 kr-812, kr-1256, cn-324, tw-410, cn-404, cn-406, cn-408, cn-705, cn-706, cn-717, id-400, id-1809, cn-774, tw-454에 적용됩니다. online_players: true, 인벤토리, 커플 저장소와 해당 빌드의 inventory.couple-catalog 서비스가 필요합니다. couple_proposal_seconds는 기본 180(10–3600), couple_breakup_wait_hours는 기본 24(0–8760), couple_message_length는 UTF-16 코드 단위 256개(1–512)입니다. 두 플레이어가 해당 빌드 서비스에 접속 중이고 경기 중이 아니어야 합니다. 제안 또는 초대용 반지를 이용한 반지 변경에는 만료되지 않은 양수 수량의 네이티브 커플 초대 아이템이 필요하며 일반 소유 아이템으로 대체할 수 없습니다. 수락 시 소유권을 다시 확인합니다. 초대 아이템은 소비하지 않습니다. 저장하는 초대 아이템 ID와 화면에 표시하는 반지는 다르며 표시용 반지는 해당 빌드의 네이티브 stock 데이터에서 해석합니다. 수락, 거절, 철회와 만료를 지원하며 이전 연결이나 장면의 초대는 관계를 만들 수 없습니다. 커플 해제는 설정된 대기 시간이 지나야 하고 반지 변경은 두 사람이 접속 중이어야 합니다. 다시 로그인하면 파트너를 복원합니다. 즉시 알림은 이 서비스 내부에 한정되며 노드 간 온라인 알림은 제공하지 않습니다. 초대 외형은 해당 빌드의 장비 선택을 읽기 전용으로 조회하고 네이티브 아이템 속성을 포함하며 인벤토리를 초기화하거나 수정하지 않습니다.

dialect.messages 행의 couples도 기본적으로 활성화되며 검증된 빌드 기능으로 제한됩니다. 커플 기능을 의도적으로 끄려면 lobby와 dialect.messages 모두에서 couples: false를 설정합니다. 비활성 전송 바인딩은 커플 opcode 이름을 요구하지 않습니다. 반지 카탈로그 조회는 네이티브 out 매개변수를 사용하며 현재 원격 SDK 어댑터가 없습니다.

독립적인 inventory.couple-catalog 행은 선택한 빌드의 클라이언트 데이터 서비스에서 shop_item_client_path(기본 Config/ShopItem2.xml)의 ShopItem과 Stock 시트를 읽습니다. max_shop_item_bytes는 기본 134217728(범위 1–268435456), max_couple_rings는 기본 256(1–65535)입니다. 네이티브 기능 값 17이 초대 아이템을 식별하고 해당 parameter는 Stock.stockId를 가리킵니다. 그 행의 itemId가 표시용 반지입니다. 참조된 stock이 없거나 정의가 모호하거나 용량을 넘으면 활성화에 실패합니다. allowed_missing_display_stock_ids는 기본적으로 빈 목록이며 서로 다른 양수 stock ID를 최대 256개 받습니다. 해당 빌드의 네이티브 데이터에서 확인한 누락만 허용하며 초대 아이템은 유효하게 유지하고 표시용 반지는 0으로 둡니다. CN408은 stock 1004192, ID400은 stock 1002134를 선언합니다. stock 행이 존재하면 표시 아이템도 유효해야 합니다. 다른 빌드의 stock ID나 반지 매핑을 대신 사용하지 않습니다.

관계 형성, 반지 변경과 로그인 후 자신의 커플 프로필을 갱신하며 파트너 접속 상태는 관계 존재 여부와 별도로 관리합니다. 일반 사용자 정보 갱신도 이 상태를 유지합니다. 저장된 초대 아이템이 현재 클라이언트 목록에 없으면 관계와 생성 시간은 그대로 유지하고 표시용 반지만 0으로 보냅니다. 다른 반지로 대체하거나 소유권을 변경하지 않습니다.

오른쪽 클릭으로 여는 전투원 정보에는 조회 대상의 저장된 파트너가 표시되며, 파트너가 오프라인이어도 신원은 유지됩니다. 방과 광장 입장 정보에 파트너 신원을 포함하고 이후 관계 변경은 해당 빌드의 네이티브 커플 갱신으로 알립니다. 현재 장면에 대상 인물을 성공적으로 로드한 클라이언트에만 전송하며 인물을 다시 만들거나 이동을 초기화하지 않습니다. 광장 페더레이션의 외형 스냅샷에도 관계 신원을 포함합니다. 디렉터리와 참여하는 모든 워커를 함께 업그레이드해야 합니다. 이전 페더레이션 판독기는 추가된 관계 필드를 거부합니다. 이 장면 동기화는 노드 간 커플 제안 전달이나 접속 상태 알림을 추가하지 않습니다.

SQLite와 MySQL 행의 couple_invitations는 max_pending_invitations(1024, 1–65536), max_pending_per_account(16, 1–1024), max_completed_invitations(1024, 1–65536), max_message_length(UTF-16 코드 단위 512개, 1–4096)를 받습니다. 데이터 권한 이름은 비어 있거나 앞뒤 공백을 포함할 수 없으며 UTF-16 코드 단위 128개 이하입니다. 중복 응답은 관계를 다시 만들지 않고 이전 관계 세대의 해제나 반지 변경 요청은 새 관계에 영향을 주지 않습니다. 제거된 응답 기록은 찾을 수 없으므로 호출자는 항상 서버에서 새 초대 ID를 생성해야 합니다.

로컬 격리 점검 ​

tools/local-checks/isolated-memory.patch.yaml은 persistence.mysql을 비활성화하고 persistence.memory를 활성화합니다. 명령줄 패치가 마지막에 적용되므로 실제 데이터베이스를 가리키는 개발자 .env나 local.patch.yaml보다 우선합니다. 모든 로컬 run(--dump-config 점검 포함)에 추가하십시오. 아래 "격리된 로컬 점검" 레시피에 전체 명령이 있습니다. 프로세스가 멈추면 메모리 데이터는 사라지며, 이 패치는 운영 영속성 구성을 대신할 수 없습니다.

클라이언트 데이터 ​

게임 프로필은 선택한 클라이언트 빌드 자체의 데이터를 읽습니다. 저장소에는 게임 클라이언트와 그 파일이 포함되지 않습니다. 데이터 루트의 기본값은 client-data이며 BFF_CLIENT_DATA로 옮길 수 있습니다. 구조는 다음과 같습니다.

text
client-data/
  <build>/
    data/      클라이언트 원래 경로를 유지한 클라이언트 패킷(예: Packs/, Config/)
    dataraw/   같은 클라이언트 경로의 압축 해제된 개별 파일, 먼저 읽음

<build>는 프로필 id입니다(예: kr-812, kr-1256). 레거시 프로필은 ${BFF_CLIENT_DATA:-client-data}/${BFF_PROFILE_ID}/data와 .../dataraw를 읽고, 모던 kr-1256 프로필은 kr-1256에 대해 같은 구조를 사용합니다.

두 디렉터리가 모두 없으면 clientdata 행이 활성화 단계에서 실패하며, 오류 메시지는 찾은 두 경로를 알려 주고 서버는 시작을 완료하지 못합니다. 게임 프로필을 시작하기 전에 데이터를 준비하십시오. 이 파일은 읽기 전용 입력이므로 Docker 구성은 읽기 전용으로 마운트합니다.

management와 setup은 클라이언트 데이터 행을 마운트하지 않습니다. 최초 설치 흐름은 준비된 데이터를 상태 디렉터리로 가져올 수 있습니다. 설치를 참고하십시오.

설치된 클라이언트 업로드와 tools/client-data/bfdata.py는 같은 생성 규칙을 사용합니다. 중첩된 Maps/<Directory>/track.wb를 포함한 지도 .wb 리소스는 원래 클라이언트 경로로 dataraw에 추출되며, sources.tsv에 출처와 SHA-256이 기록됩니다. 준비된 data/dataraw 가져오기도 이 파일을 보존합니다. 이전 데이터 트리에 지도 WB가 없다면 해당 기능을 켜기 전에 같은 빌드의 클라이언트에서 새 디렉터리로 다시 생성하십시오. 공용 WorldBlockFile helper 리더는 이름, 위치, 회전을 그대로 제공하며 모드별 처리는 호출자가 담당합니다. 서버에 지도 좌표를 하드코딩하지 않습니다.

CN2011(cn-279)의 ingame.item_mode_fallback_point_count: 4는 일반 아이템 모드에서 방장의 지도 보고에 무작위 상자 지점이 없을 때 서버 보충 정책을 켭니다. 현재 지도의 #sp_star_ helper에서 서로 다르고 공간적으로 분산된 위치를 최대 네 개 선택하며, 별 지점이 없으면 #ic_ helper를 사용합니다. 중립 kind-0 상자는 supply_default_min_ms / supply_default_max_ms(기본 15–30초)에 따라 생성됩니다. 이 주기적 공급은 서버 정책이며 원래 클라이언트에 고정 무작위 상자 표식이 있었다는 의미가 아닙니다. 보고된 기존 무작위 지점은 유지되고 다른 프로필의 옵션 기본값은 0입니다. item_mode_fallback_maximum_file_bytes의 기본값은 8388608, item_mode_fallback_maximum_candidates는 4096입니다. 지도 리소스가 없거나 지원되지 않거나 잘못되면 좌표를 추측하지 않고 보고를 거부합니다.

CN279는 등급별 가중치 표의 17종 아이템과 기본 보유 슬롯 하나를 유지합니다. 충돌 시 클라이언트가 선택한 아이템을 서버가 검증합니다. CN279는 item_mode_resolve_invalid_random_pickups도 켭니다. 존재하고 획득 조건을 충족하는 무작위 상자의 요청 종류가 0이거나 허용 목록 밖이면, 서버가 허용 목록에서 균등하게 한 번 선택합니다. 유효한 클라이언트 결과는 유지되며 고정 종류 상자와 부적격 객체에는 적용되지 않습니다. 옵션이 꺼져 있으면 미해결 종류 0 요청을 거부하고 상자를 보존합니다. 이 보충 분포는 서버 정책이며 기본 등급별 가중치와 다릅니다. 기본 행동 게이지 드롭은 초기 속도를 보존합니다. 슬롯이 비면 가득 찬 슬롯 때문에 거부되었던 살아 있는 상자를 새 객체 ID로 다시 생성하며, 드롭 상자의 재생성 속도는 0입니다. 팀 메디팩 129를 포함한 아이템 사용은 사용자와 모든 참가자에게 방송되어 클라이언트의 기본 효과 경로를 실행합니다. 서버에 별도의 HP 장부를 도입하지 않습니다. 이 자동화 경로는 실제 클라이언트 검증이 여전히 필요합니다.

일반 구성 ​

첫 번째 레시피는 격리 점검입니다. 나머지는 의도적으로 영속 저장소를 향하는 구성입니다. 즉, 직접 소유한 저장소를 가리키며 구성 중인 공급자를 비활성화하므로 격리 패치를 포함하지 않습니다. 영속 레시피를 변경할 의도가 없는 데이터베이스에 겨냥하지 마십시오.

격리된 로컬 점검 ​

sh
cp .env.example .env
# 데이터베이스 설정은 필요하지 않습니다. 격리 메모리 패치가 MySQL을 비활성화합니다.
dotnet run --project src/BubbleFighter.Fantasy.Host -c Release -- run --profile management --patch tools/local-checks/isolated-memory.patch.yaml

콘솔은 활성화된 행을 보고하고, Host가 준비되면 Server started with <n> active row(s).를 출력합니다. http://127.0.0.1:7300/의 GET /health를 확인하십시오. status 필드가 있는 JSON을 반환합니다. Ctrl+C로 중지합니다.

SQLite 서버 ​

저장소 루트에 sqlite.patch.yaml을 만듭니다.

yaml
- replace:
    id: persistence.mysql
    disabled: true
- replace:
    id: persistence.memory
    disabled: true
- replace:
    id: persistence.sqlite
    disabled: false
    config:
      database_path: "${BFF_SQLITE_DATABASE_PATH}"

.env에서 BFF_SQLITE_DATABASE_PATH를 절대 경로로 설정한 뒤 대상 프로필을 시작하십시오(게임 빌드는 클라이언트 데이터가 필요합니다).

sh
dotnet run --project src/BubbleFighter.Fantasy.Host -c Release -- run --profile kr-1256 --patch tools/local-checks/isolated-memory.patch.yaml --patch sqlite.patch.yaml

콘솔에서 SQLite 활성화 줄을 찾고 저장 파일이 설정한 경로에 생겼는지 확인하십시오. Ctrl+C로 중지합니다. 저장 파일은 남습니다.

MySQL 서버 ​

.env에 실제 연결 값을 설정하고 기본 MySQL 행을 활성화된 상태로 두십시오.

sh
BFF_MYSQL_HOST=127.0.0.1
BFF_MYSQL_PORT=3306
BFF_MYSQL_USER=bff
BFF_MYSQL_PASSWORD=<your-database-password>
BFF_MYSQL_DATABASE=bf_game_db

로컬 설정을 확인할 때는 이 데이터베이스에 연결하지 말고 격리된 메모리 저장소로 프로필을 검사하십시오.

sh
dotnet run --project src/BubbleFighter.Fantasy.Host -c Release -- run --profile kr-1256 --patch tools/local-checks/isolated-memory.patch.yaml --dump-config

이 덤프는 MySQL을 명시적으로 비활성화하며 리스너를 시작하지 않습니다. 데이터베이스 연결을 검증하거나 마이그레이션을 실행하지 않습니다. 영구 저장소로 운영하려면 데이터베이스 설정을 명시적으로 검토한 후 배포를 따르십시오. 실제 MySQL 활성화 시에는 MySQL persistence connected to <host>:<port>/<database> as <user>.가 기록되고 대기 중인 마이그레이션이 적용됩니다.

NAT: 바인드 및 공개 주소 ​

리스너가 모든 인터페이스에 바인딩되고 클라이언트에는 공용 주소가 알려지도록 두 주소를 .env에 설정하십시오.

sh
BFF_BIND_HOST=0.0.0.0
BFF_PUBLIC_HOST=<public-address-clients-use>

포트 변수도 같은 방식으로 바꿀 수 있습니다(예: KR_1256_GAME_PORT, KR_1256_RELAY_PORT). 방화벽에서는 해당 포트만 열고, 시작 전에 --dump-config로 주소를 확인하십시오. 특정 리스너의 주소가 프로필 기본값과 달라야 한다면 그 리스너 행에 set 패치를 쓰는 방법도 있습니다.

yaml
- set:
    id: game-listener
    config:
      listen: "0.0.0.0:7100"

다중 클라이언트 프로필 ​

프로필은 서로 다른 역사적 클라이언트를 제공합니다. 빌드 id는 <region>-<wire version>이며, 여기서 wire version은 파일 버전이 아니라 클라이언트의 ClientVersion_Major입니다(kr-812, cn-324, id-400, tw-454, kr-1256). 프로필 디렉터리 이름이 패킷 표 전체에서 사용하는 빌드 id입니다.

kr-812(한국 2015)는 레거시 기준선입니다. profiles/bundles/legacy.yaml이 그 행 집합이며, 레거시 빌드는 자체 vars와 patch.yaml에 차이(포트, 암호 표, 좌석 수, 좌석 관련 설정, 패킷 스위치)만 선언합니다. kr-1256(한국 최종 빌드)은 모던 기준선입니다. 자체 kr-1256, ingame, shop 번들을 가지며, 그 패킷 레이아웃이 cn-774와 tw-454의 기준입니다.

프로필클라이언트 빌드역할
kr-812kr:812:458레거시 계열의 기준선입니다.
kr-1256kr:1256:1304모던 기준선이며 Dockerfile의 기본 프로필입니다.
all16개 빌드기동된 모든 빌드를 하나의 프로세스에서 각자의 리스너 포트로 실행합니다.
management없음관리 HTTP와 저장소만 제공하며 게임/릴레이 포트가 없습니다.

나머지 클라이언트 빌드 프로필은 각각 하나의 빌드를 제공합니다. 패킷 레이아웃은 packets/builds.yaml과 프로필 자체 parent: 계보를 통해 상속됩니다. cn-279는 cn-324를 기반으로 하고 cn-324는 kr-812를 기반으로 합니다. cn-738과 cn-742는 cn-735의 레이아웃을 따르며, tw-454는 cn-774를 기반으로 하고 cn-774는 kr-1256을 기반으로 합니다. 차이가 작은 빌드는 레이아웃을 다시 쓰지 않고 차이만 표기합니다.

빌드는 기능(capability)에서도 다릅니다. 기능은 packets/builds.yaml에 빌드별로 기록되고 기준선을 통해 상속됩니다. 예를 들어 만료된 아이템을 버릴 때 범주 6을 제외하는 제한은 kr-812에서 켜져 있고 cn-324에서 꺼져 있으며, 모던 kr-1256은 해당 빌드에서 소비자가 감사될 때까지 여러 레거시 기능을 꺼 둡니다. 레거시 방의 좌석은 기준선에서 12개, cn-324에서 8개입니다. 기능 스위치는 빌드의 프로토콜 계층이 무엇을 보내고 활성화할지 결정하며, 이는 추측이 아니라 데이터입니다.

연결하려는 클라이언트 빌드로 프로필을 선택하십시오. 클라이언트 버전을 읽고 일치하는 프로필 id를 찾은 뒤 그 프로필의 포트를 사용하고 해당 빌드의 클라이언트 데이터를 준비하십시오. all은 여러 빌드를 함께 실행할 때 사용하며, 각 빌드의 리스너를 시작하고 선택한 모든 빌드의 데이터가 필요합니다.

나열된 프로필이 의미하는 것은 저장소가 이 행들을 구성하고 이 빌드의 패킷 데이터와 기능 기록을 포함한다는 것입니다. 의미하지 않는 것은 모든 게임플레이 기능이 구현되었거나 실제 클라이언트가 검증되었다는 것입니다. 자동화 점검 통과, 기능 활성화, 프로필 목록 등재는 실제 클라이언트 호환성을 입증하지 않습니다. 기능 기록은 감사된 네이티브 지원을 설명하며, 네이티브 수용 테스트는 별도로 수행해야 합니다.

선택 기능 번들 ​

일부 번들은 명시적으로 활성화해야 하며, 클라이언트 감사가 뒷받침하는 프로필에서만 나열됩니다.

**player-settings**는 player.settings를 마운트하며, 이는 플레이어 사용자 지정 키의 형식화된 저장소입니다. 패킷 자체는 dialect.messages 행의 customized_keys 옵션이 묶으며 kr-812, kr-1256, cn-774, tw-454가 선언합니다. 다른 프로필은 먼저 네이티브 컨트롤 이름과 패킷 경로를 감사해야 합니다. 각 player.settings 행은 protocol이 필요하고 프로필별 scope를 사용해 서로 다른 빌드의 이름이 섞이지 않게 합니다. 영속성 공급자는 계정별로 매핑을 저장하며, MySQL은 마이그레이션 0032_customized_keys.sql을 통해 저장합니다. 계정당 예산은 각 공급자의 customized_keys로 설정합니다(max_scopes 1–64, max_mappings 1–512, max_name_characters 1–1024이며, 세 값의 조합이 패킷 본문에 들어가야 합니다). 예산을 넘기면 다른 저장 매핑을 밀어내지 않고 실패합니다.

dialect.messages.config.science_lab의 기본값은 false이며 kr-1256, cn-774, tw-454의 검증된 실험실 작업을 라우팅합니다. 담당 처리기가 없는 작업은 클라이언트의 실험실 닫힘 결과(KR은 5, CN/TW는 4)를 반환합니다. 활성화하려면 모든 요청과 응답 쌍이 검증되고 해당 레이아웃이 있어야 하며, 불완전한 테이블은 실패합니다. 이 옵션만으로는 조합법, 경제 정책, 아이템 변경 또는 실험실 설정을 제공하지 않습니다. 선택적 아이템 강화 번들은 kr-1256에서 이 옵션과 science_lab_configuration, 강화 처리기를 함께 활성화하고, 해당 빌드에서 별도로 활성화하는 선택적 개조(Modification) 정책을 제공합니다. 레거시 kr-812의 합성과 분해는 별도의 선택적 레거시 과학실 설정을 사용합니다. 네이티브 실험실 UI 검증은 아직 남아 있습니다.

만료된 아이템 버리기도 같은 방식으로 선언합니다. dialect.messages 행의 inventory_actions 옵션이 gcpReqInventoryThrowItem/gspRepInventoryThrowItem을 묶고(모든 legacy 빌드와 kr-1256에서 켬), 빌드 자신의 bundle 안 inventory.throw 행이 저장 장비 서비스를 통해 해당 아이템을 제거합니다. 동작은 의도적으로 좁습니다. 인증된 한 플레이어의 두 가방에서 해당 만료 아이템만 제거하고, 일치하는 이용 권한이 유효하면 제거 전체를 거부하며, 빌드의 범주 6 제외 규칙을 따릅니다. 경기 중 요청은 거부됩니다. 실제 클라이언트 수용은 아직 남아 있으며, 패킷 표 지원만으로 다른 빌드에서 이 옵션을 선언할 수는 없습니다.

**launcher.http**는 선택적 공용 런처 API입니다. 기본적으로 비활성화되며 관리와 분리됩니다. minimum_launcher_version(비우면 검사 안 함)과 런처가 적용하는 플러그인별 유형 규칙인 client_policy를 받습니다. 규칙은 스토어 ID와 선언된 스토어 소스만 가리키며 실행 파일 경로는 절대 포함하지 않습니다. 최소 버전이 설정되면 구버전 런처는 HTTP 426을 받습니다. 각 로비 행의 authentication 옵션(BFF_LOGIN_AUTHENTICATION, 기본값 ticket)은 런처 티켓을 교환하는 로그인만 허용하며 이때 이 행이 활성 상태여야 합니다. open은 모든 계정 이름을 허용하므로 신뢰할 수 있는 LAN에서만 사용하십시오. 런처 페이지에서 API, 클라이언트 프리셋, 계정과 티켓 흐름, 운영자 설정을 설명합니다.

런처 요청 및 로그인 세션 제한은 launcher.http 행에서 설정합니다.

키기본값동작
requests_per_minute120전송 연결의 원본 IP별 1분 요청 수입니다. 전달 헤더로 원본 IP가 바뀌지 않습니다.
max_rate_limit_addresses4096보관할 IP별 시간 창 수(1–100000)이며, 가득 차면 가장 오래된 창을 제거합니다.
max_sessions_per_account8계정별 유효한 영구 로그인 세션 수(1–1024)이며, 새 로그인 시 생성 시간이 가장 오래된 세션을 취소합니다.

오래된 세션을 취소하면 이 프로세스의 접근 토큰과 대기 중 게임 티켓도 제거됩니다. 만료된 갱신 세션은 리스너 시작 전에 삭제하며, 이후 로그인 과정에서는 최대 1시간에 한 번 삭제합니다. 계정 제한은 세션 저장소에서 적용되므로 서버를 다시 시작해도 유지됩니다.

수동 릴레이 지연 응답 ​

relay-latency 번들은 kr-1256, cn-738, cn-742, cn-774, tw-454에만 기본 비활성 상태인 dialect.relay-latency와 match-latency 행을 추가합니다. 네이티브 클라이언트 수용 테스트에서는 배포 패치로 두 행을 함께 활성화할 수 있습니다.

yaml
- set:
    id: dialect.relay-latency
    disabled: false
- set:
    id: match-latency
    disabled: false
    config:
      reply_word: 0

두 행의 protocol은 kr-1256/relay처럼 해당 빌드의 릴레이 프로토콜이어야 하며 번들이 이 값을 제공합니다. dialect의 packets_directory 기본값은 packets입니다. 로직 행의 reply_word는 0..4294967295를 허용하며 기본값은 0입니다. 네이티브 응답 처리기가 읽은 뒤 버리는 의미 미확정 4바이트 값이며, 요청 타임스탬프를 되돌려 주는 값이 아닙니다.

완전한 요청마다 인증을 마쳤고 임대가 여전히 유효한 원래 릴레이 연결로 한 번 응답합니다. 응답은 연결 소유자의 직렬화 게이트를 핸드셰이크 전송과 공유하며 장면 초기화 완료를 요구하지 않습니다. 잘못된 본문, 무효 임대, 전송 실패는 연결 오류로 처리하고 기존 연결 및 송신 큐 예산으로 자원을 제한합니다. 핸드셰이크 순서와 클라이언트 샘플러 설정은 유지됩니다. 두 행을 활성화해도 클라이언트 탐측은 시작되지 않습니다. 네이티브 클라이언트 수용 검증이 끝날 때까지 두 행은 기본 비활성 상태입니다. all 프로필 패치에서는 빌드 접두사가 붙은 행 ID를 사용합니다.

선택적 UDP 전송 ​

net.udp 플러그인이 UDP를 제공합니다. 게임 로그인, 방 입장 및 경기 인증은 TCP를 유지하며, UDP는 검증된 네이티브 이동 및 탐색 트래픽을 전달합니다. 기본 프로필은 UDP 리스너를 활성화하지 않습니다.

선택적 패치검증된 프로필전송 방식
profiles/bundles/udp-relay.patch.yamlkr-812, cn-717, id-1809, kr-1256, cn-774, tw-454서버 UDP 엔드포인트로 인증된 이동을 전송하며, 수신자의 엔드포인트가 없으면 TCP로 전달합니다.
profiles/bundles/udp-peers.patch.yamlcn-279, cn-324, cn-406, id-400, cn-404, cn-408, cn-705, cn-706서버가 탐색과 피어 간 직접 이동을 조정하며, 실패한 경로는 경기 TCP 전송을 유지합니다.

일치하는 단일 프로필에 두 패치 중 하나를 적용하세요. 두 패치는 대안이며, 버전 접두사가 없는 행 ID를 all에 직접 적용할 수 없습니다. BFF_UDP_PORT는 사용 가능한 UDP 포트, BFF_BIND_HOST는 수신 주소입니다. 선택적 BFF_UDP_PUBLIC_PORT는 외부에 매핑한 UDP 포트이며, 0이면 실제 바인딩 포트를 알립니다. UDP 포워딩은 기존 게임 및 릴레이 TCP 포트와 별개입니다. 피어 탐색은 인증된 게임 서버의 IPv4 주소를, 릴레이 우회는 릴레이 서버의 IPv4 주소를 사용하므로 외부 UDP 매핑도 해당 공인 주소를 사용해야 합니다.

일반 TCP/관리 포트를 사용 가능한 로컬 포트로 지정하고 해당 빌드의 클라이언트 데이터를 준비한 뒤 다음과 같이 실행합니다.

powershell
$env:BFF_LOGIN_AUTHENTICATION = "open"
$env:BFF_BIND_HOST = "127.0.0.1"

선택적 UDP 패치를 적용하면 BFF_UDP_ENABLED의 기본값은 true입니다. false로 설정하면 TCP를 유지하며 UDP 리스너와 협상을 시작하지 않습니다. 혼자 있는 방은 기본적으로 TCP를 사용합니다. 경기가 시작되고 모든 relay가 초기화되며 엔드포인트 검증이 완료된 뒤에만 UDP 이동을 허용합니다.

UDP 설정은 공개된 게임 방으로 제한합니다. CN279, CN324, CN406 및 ID400은 게임 장면에서 탐색 패킷을 전송하지 않으므로 대기실에서 엔드포인트를 탐색하고 피어 테이블을 확인합니다. 전체 방 설치는 준비된 테이블을 무효화합니다. 제어 메시지는 방 작업과 같은 직렬 큐를 사용하므로 방 설치나 장면 진입을 추월하지 않습니다. 펀칭과 직접 이동은 경기 시작 및 모든 relay의 초기화 이후에만 수행합니다. 다른 검증된 빌드는 이 장벽 이후에 협상을 시작합니다. 로그인 및 자동 장면, 메뉴, 로비, 광장과 1인 훈련에서는 UDP를 협상하지 않으며, 방의 강제 설정으로도 이 제한을 우회할 수 없습니다.

방장은 !udp on으로 혼자 있는 방에서도 UDP 협상을 강제하고, !udp off로 TCP를 유지하거나, !udp로 현재 방의 설정을 전환할 수 있습니다. 방 명령으로 전역 비활성화 상태이거나 사용할 수 없는 UDP를 켤 수는 없습니다. 검증되지 않았거나 연결할 수 없는 경로는 TCP를 유지합니다. 모든 플러그인 명령에서 /, !, ！는 같은 명령 시작 문자입니다. 게임에서는 /가 클라이언트 기본 명령으로 처리될 수 있으므로 사용법에 !를 표시합니다. 관리 화면과 콘솔에서는 udp on처럼 시작 문자 없이도 입력할 수 있으며 사용법에는 /를 표시합니다.

방의 모든 구성원은 !udp status로 UDP 사용 여부를 확인할 수 있습니다. 전송 방식(서버를 거치는 relay 또는 직접 연결하는 peer), 방 설정, 그리고 구성원마다 UDP, NEGOTIATING 또는 TCP 상태와 이유(라운드 대기, 제안했지만 UDP 프로브를 받지 못함, 검증됨, 클라이언트의 TCP 전환 등)를 보여 줍니다. 서버에서 UDP가 꺼져 있거나 해당 클라이언트 버전에 UDP 설정이 없을 때도 알려 줍니다. !plaza는 라운드 중에도 현재 방을 즉시 나가 광장으로 갑니다. 좌석은 스스로 나갈 때와 똑같이 해제되므로 라운드는 나간 플레이어를 정산하고 나머지는 계속 플레이하며, 마지막 플레이어가 나가면 방이 삭제됩니다. TCP로 전환되면 그 이유를 표시합니다. UDP 프로브가 서버에 도달하지 못함, 챌린지 응답이 돌아오는 길에 손실됨, 좌석별 탐색 또는 피어 표 시간 초과, 매치 연결 종료, 플레이어 사이에 직접 경로 없음 등입니다.

match-udp-directory.max_sessions는 인증된 우회 임대 수를 제한합니다. match-udp-peers의 max_rounds와 max_peers는 보관할 경기와 피어 수를 제한하며, 탐색, 테이블 확인, 펀칭 및 제어 전송 기한도 설정할 수 있습니다. 사설 엔드포인트 후보는 같은 공인 IPv4에서 관측된 피어끼리만 공유합니다. 방/경기 변경, 연결 종료, 소비자 언로드 및 릴레이 교체 시 해당 경로를 무효화합니다. IPv4만 지원하며, 모든 NAT나 방화벽에서 피어 간 직접 전송이 가능한 것은 아닙니다.

패킷 테이블은 cn-735, cn-738, cn-742의 4바이트 쿠키 및 부동소수점 이동 우회 형식도 검증합니다. 전송 어댑터의 격리 테스트는 있지만, 연구 프로필에는 릴레이 패치에 필요한 전체 방/경기 구성이 아직 없습니다. 이는 패킷 지원 범위이며 완전한 프로필 지원을 뜻하지 않습니다. 자동 소켓 시나리오는 클라이언트의 네이티브 프로토콜을 모사하며, 실제 게임 클라이언트 검증은 별도입니다.

여러 빌드를 실행할 때는 각 대상 빌드의 선택적 local.patch.yaml에 해당 패치 작업을 넣고 빌드 접두사 없는 행 ID를 사용합니다. 공유 프로필 패치는 빌드 행을 추가하기 전에 적용되므로 all의 패치에서 kr-812.dialect.rooms 같은 빌드 접두사 행을 수정할 수 없습니다. 빌드마다 서로 다른 UDP 포트를 지정합니다. peer 패치는 필요한 네이티브 relay 행도 활성화합니다. cn-705와 cn-706은 패치가 없으면 해당 행을 비활성 상태로 유지하며, 패치는 장면 시드 테이블 권한을 활성화하지 않습니다.

UDP 소켓 구독, 임대 등록, 방 큐 콜백, Span/out 매개변수 조회 및 IP 엔드포인트 레코드는 현재 네이티브 플러그인이 필요하며 원격 SDK 어댑터는 아직 없습니다. 직렬화할 수 있는 방 스냅샷과 릴레이 제어 작업은 계약 스키마를 통해 계속 사용할 수 있습니다.

match-udp-peers의 punch_retry_ms 기본값은 250이며 0이면 재시도를 끕니다. punch_window_ms 안에서 네이티브 펀칭 시작 명령을 다시 보내며 시간 창을 연장하거나 피어 ID를 바꾸지 않습니다. 직접 경로는 현재 인증된 매치 연결의 피어별 멤버십 보고가 있어야 허용됩니다. !udp status는 네이티브 결과 미수신과 클라이언트가 보고한 성공 경로 0개를 구분합니다. 이 결과만으로 방화벽이나 NAT 장애를 단정하지 않습니다.

대기실에서만 탐색하는 빌드는 discovery_refresh_ms(기본 1000, 0이면 갱신 비활성화) 간격으로 같은 피어 ID의 네이티브 일회성 탐색 요청을 다시 보냅니다. 로딩 중에는 해당 클라이언트가 탐색을 처리하지 않으므로 요청을 중지합니다. 공인 엔드포인트나 로컬 후보가 바뀌면 테이블을 다시 보내고 확인을 다시 기다립니다. 초기화된 라운드에서 펀칭을 시작하기 전에 탐색을 중지합니다.

schema-1 서버 디렉터리는 응답의 generated_at_utc와 대상의 observed_at_utc, expires_at_utc, status_revision을 제공합니다(Contracts 4.5.0). 시간은 UTC RFC3339이며 첫 보고가 승인되기 전에는 대상의 세 필드가 모두 null입니다. 대상 필드는 소스가 관리하는 동일한 보고를 나타냅니다. 반복 조회나 같은 임대의 재등록은 만료를 연장하지 않습니다. 만료된 수동 항목은 만료 정보를 보존하며 임대 철회나 시계 변경은 만료를 앞당길 수 있습니다. 만료는 소스의 남은 임대를 UTC로 환산한 시점보다 늦을 수 없습니다. 리비전은 동등 비교만 가능한 불투명 값이며 정렬 가능한 버전이나 임대 자격 증명이 아닙니다. 배치에 사용할 때 누락되거나 잘못되었거나 만료된 정보를 거부해야 합니다. 새 응답 생성은 대상의 만료를 갱신하지 않습니다. 공개된 최신성 필드는 계정의 접속을 승인하거나 티켓을 백엔드 구성원에 바인딩하지 않습니다. 자동 실행에는 보고 만료와 인증 승인 만료 모두로 제한되는 명시적으로 승인된 실행별 후보 집합이 별도로 필요합니다.

선택적 cluster-launch-selection.patch.yaml은 티켓 발급 측에 cluster.launch-selection을 등록합니다. BFF_CLUSTER_NODE_ID, BFF_CLUSTER_AUTHORITY_ID, BFF_CLUSTER_AUTHORITY_URL, BFF_CLUSTER_DATA_SCOPE, BFF_CLUSTER_AUTOMATIC_SELECTOR_ID로 로컬 노드, 인증 기관 식별자와 정확한 API 원본, 영구 데이터 범위 및 자동 선택 항목을 명시합니다. 인증된 POST /v1/launch에 serverSelection: true를 전달하면 티켓에 결합된 serverSelection에 schema, grantId, build, authorityId, policyRevision, dataScope, expiresAtUtc, generated_at_utc, servers가 반환됩니다. 허용된 구성 노드 풀에는 오프라인이거나 아직 보고하지 않은 노드도 포함될 수 있으며, 이는 인증 허용 범위이지 현재 배치 가능 상태가 아닙니다. 스냅샷은 해당 실행의 네이티브 선택 항목, 물리 노드 및 엔드포인트 바인딩을 고정합니다. 티켓은 인증 bearer로 제한되는 기존 수명을 유지하며 짧은 하트비트가 느린 게임 시작의 로그인 시간을 줄이지 않습니다. POST /v1/launch/servers는 같은 인증 세션과 {ticket,build,grantId}를 요구하고 원래 바인딩의 관측 상태만 갱신합니다. 티켓을 소비하거나 교체하지 않고 구성원을 추가하거나 엔드포인트 또는 원본 만료를 변경하지 않습니다. 소비되었거나 만료되거나 유효하지 않은 허가는 HTTP 409 admission_closed를 반환하여 정상 로그인 뒤 갱신 루프를 종료할 수 있습니다. 신뢰된 작업 노드의 교환은 일회성 소비와 같은 잠금 안에서 인증된 노드가 티켓 구성원인지 확인하고, 로컬 교환은 명시된 로컬 노드 식별자를 사용합니다. 일반 실행 동작은 유지됩니다. 이 API는 네이티브 리디렉션 승인, 공유 저장소 또는 노드 간 방 입장을 구현하지 않습니다. home_unavailable_notice_enabled의 기본값은 true이며 기본 알림 공급자가 필요합니다. 이전 패치는 검증된 알림 처리기가 없는 cn-406, cn-774, tw-454에서만 빌드 변수 MIGRATION_HOME_NOTICE로 이를 끕니다. 홈 복귀가 거부되면 항상 경고를 기록하며 플레이어는 계정 권한을 유지한 채 방문 노드에 남습니다.

유지된 플레이어의 입장 서비스는 빌드별 inventoryview 하위 트리에서 격리되므로 로비와 이전 입장 처리는 해당 빌드의 로그인 공급자만 공유합니다.

ingame 행에서 room_admission_reservations: true를 설정하면 빌드별로 해제 가능한 IRoomAdmissionDirectory를 등록하여 목적지 좌석을 예약합니다(Contracts 4.9.0). room_admission_lifetime_ms의 기본값은 10000이며 범위는 100–60000입니다. 예약 수는 방 좌석 수로 제한되고 단조 시계로 만료되며 방 생성 식별자와 계정을 고정합니다. 일반 참가와 봇은 예약 좌석을 사용할 수 없습니다. 취소, 만료, 방장의 좌석 잠금, 게임 시작, 방 폐쇄 및 플러그인 해제 시 미사용 예약을 반환합니다. 사용 시 비밀번호를 다시 확인하고 같은 계정과 빌드로 독립 인증된 게임 소유 연결 및 변경되지 않은 메뉴 또는 광장 상태를 요구한 뒤 일반 입장과 멤버 알림을 사용합니다. 예약은 인증이나 계정 소유권이 아니며 원격 방 클릭, 새 네이티브 소켓 인증 또는 원본 노드 소유권 이전을 아직 연결하지 않습니다. 단독 서버에서는 기본적으로 비활성화됩니다.

launcher.http의 center: { enabled: false, mode: gateway } 설정은 기본적으로 꺼져 있습니다. 명시적 enabled: true만 Center를 켜며 mode를 생략하면 gateway, 명시적 native는 서버 자체 Center를 사용합니다. GET /v1/catalog와 GET /v1/servers/{build}는 같은 최상위 center: {enabled,mode} 객체를 반환합니다. 이전 catalog에 Center가 없거나 mode만 있으면 비활성 상태입니다. Launcher는 catalog를 먼저 읽으며 비활성/native 모드는 게임 엔드포인트를 유지하고 디렉터리나 Gateway를 요구하지 않습니다. 활성 gateway 모드만 schema-1 디렉터리를 읽고 Center 설정의 일치를 확인합니다. Launcher 항목은 하나이며 게임의 기본 UI에서 서버를 선택합니다. 서버가 제공한 automatic: true 항목만 자동 배치를 켜고 targets가 후보 풀을 제한합니다. 자동 항목이 없으면 수동 전용이며 허가를 발급하지 않습니다. 선택 서비스가 등록되어도 비활성/native 모드는 허가를 발급하지 않으며 명시적 요청은 HTTP 409 server_selection_unavailable을 반환합니다. 선택 ID/이름과 물리 노드 ID/엔드포인트는 별개입니다. 이 설정 자체가 선택 후 인증이나 노드 간 방 입장을 구현하지는 않습니다.

수동 선택 항목은 대상 주소를 추측하지 않고 비활성 항목을 예약하도록 빈 nodes 목록을 허용합니다. 자동 선택 항목에는 여전히 구성된 후보가 필요합니다. Launcher API는 빈 항목을 유지하며, 클라이언트는 이를 비활성으로 유지하고 임의 주소를 확인하거나 연결해서는 안 됩니다.

선택 항목은 선택적 short_name을 지원합니다. 길이는 UTF-16 코드 단위 1..128개이며 공백만 있는 문자열, 제어 문자 및 짝이 없는 서로게이트는 허용하지 않습니다. 디렉터리와 실행 권한은 short_name으로 반환하며, 생략하면 전체 name을 사용합니다. 상태 갱신은 권한 발급 시의 두 이름을 유지합니다. 짧은 지역 이름은 전체 이름에서 추출하지 않고 명시적으로 설정하며, 이름은 엔드포인트나 인증 바인딩을 변경하지 않습니다.

선택 항목은 sections(예: Main, Test Server, Oversea Server)로 묶을 수 있으며 첫 번째 섹션이 기본 섹션입니다. 각 섹션에는 id, name, 선택적 api_url이 있습니다. api_url이 없는 섹션은 디렉터리를 게시하는 런처 API의 로그인을 공유하므로 한 번 로그인하면 게임 내 목록으로 해당 서버에 들어갈 수 있습니다. api_url이 있는 섹션은 그 API로 로그인하고 자체 티켓을 발급하며, 런처는 그 계정을 따로 보관합니다. 그룹화는 전부 아니면 전무입니다. 섹션을 구성하면 모든 선택 항목이 section에 섹션 하나를 지정해야 하고, 구성하지 않으면 어느 항목도 지정하지 않습니다. GET /v1/servers/{build}에는 sections와 각 선택 항목의 section이 추가됩니다. 노드는 start와 end(초와 시간대 오프셋을 포함한 ISO 8601, 둘 다 생략 가능), Markdown 형식의 description으로 maintenance를 선언할 수도 있습니다. 점검이 적용되는 동안 대상에 점검 기간이 포함되고, 자동 배치는 해당 노드를 제외하며, 런처는 해당 서버를 점검 중으로 표시하고 게임 내 목록에서 뺍니다. 런처는 마지막으로 읽은 디렉터리를 보관하므로, 게시 API에 연결할 수 없는 동안에도 모든 섹션을 나열하고 독립 섹션은 자체 API로 상태를 확인하며 나머지 서버는 오프라인으로 표시합니다.

selectors[].nodes는 표시할 노드를 지정하며 수동 항목은 노드가 없거나 하나만 갖습니다. selectors[].automatic은 임대가 유효하고 준비되었으며 드레인 중이거나 정원이 찬 상태가 아닌 후보만 반환합니다. 풀 구성원은 동일한 비어 있지 않은 data_scope를 선언해야 합니다. nodes[].data_scope와 nodes[].join_scope는 불투명한 관계 선언입니다. 빈 값은 공유나 참가 권한을 주지 않으며 같은 이름도 해당 기능을 구현하지 않습니다. nodes[].room_directories는 방 요약 공유를 독립적으로 제어하므로 우호 서버가 계정을 분리한 채 방 목록만 공유할 수 있습니다.

자동 선택 항목에는 권한 데이터베이스의 persistent_domain_id도 필요합니다. SELECT REPLACE(domain_id, '-', '') FROM cluster_data_domain WHERE singleton_id = 1로 읽으며 MySQL 마이그레이션 0035가 한 번만 초기화합니다. 권한 데이터베이스에서 먼저 마이그레이션한 뒤 작업 노드는 auto_migrate: false로 시작하고 같은 권한 데이터베이스에 연결하십시오. 각 하트비트는 요청 기한 내에 식별자를 다시 읽으며 일치하는 후보만 자동 풀에 들어갑니다. 잘못 설정된 노드가 정상 후보를 제거하지 않습니다. 같은 고정 데이터 범위의 수동 항목은 식별자가 다르면 목록에 유지되지만 오프라인으로 표시됩니다. 복원된 데이터베이스 복사본은 식별자를 유지하므로 이 검사는 설정 오류를 감지할 뿐 데이터베이스 인증이나 실시간 복제를 증명하지 않습니다. 독립 복사본은 배치를 활성화하기 전에 다른 식별자를 사용해야 합니다. 식별자 제공자가 없는 노드는 빈 data_scope로만 보고할 수 있고 자동 풀에 들어갈 수 없습니다.

등록은 세대가 구분된 임대를 만들고 증가하는 순번의 하트비트가 갱신합니다. 만료되면 자동 후보와 방을 제거하되 수동 항목은 오프라인으로 남깁니다. 준비 상태에는 호스트 준비와 등록된 게임 리스너가 필요합니다. 보고에는 인증된 로그인 수와 공개 게임 방 요약만 포함하며 비밀번호나 플레이어 신원은 제외합니다. 실제 라우팅 구현 전 원격 방의 joinAllowed는 항상 false입니다.

노드/항목/방 수, 본문 크기, 연결 및 기한에는 상한이 있습니다. lease_seconds는 heartbeat_seconds + request_timeout_seconds보다 커야 하며 잘못된 조합은 보고 실패로 처리합니다. draining은 자동 배치를 제외하고 수동 상태와 방 요약을 유지합니다. 검색은 공유 저장소, 전역 세션 권한, 원격 방 참가, 파티 연동이나 릴레이 이전을 제공하지 않습니다. 다중 노드에서 실제 플레이어를 받기 전에 각 기능을 구현하고 검증하십시오.

선택적 persistence.mysql-account-ownership 행은 계정 점유 기본 기능인 IAccountOwnershipStore를 제공합니다. 마이그레이션 0036를 적용한 후에만 profiles/bundles/cluster-account-store.patch.yaml을 탑재하고 BFF_CLUSTER_ACCOUNT_CONNECTION_STRING과 권한 데이터베이스 식별자를 설정하십시오. 데이터베이스 메모리에 맞게 max_owners를 제한하십시오. 각 점유는 풀링하지 않는 전용 연결에서 대기 없이 명명된 잠금을 요청합니다. 검증은 원래 잠금과 고정 식별자를 모두 확인하며, 잃은 점유는 자동으로 다시 획득하지 않습니다. 언로드는 진행 중인 획득을 기다리고 기존 점유를 닫습니다. 이 기본 기능은 아직 게임 로그인이나 저장소 쓰기를 보호하지 않으므로 이것만으로 공유 노드 로그인이 안전해지지 않습니다. 단독 서버 프로필은 이를 탑재하지 않습니다. 계정 획득은 네이티브 연결 수명을 소유하는 핸들을 반환합니다. 원격 SDK에는 이 결과의 어댑터가 없으므로 스키마는 획득 작업을 지원하지 않는다고 명시합니다.

선택적 cluster.account-sessions 행은 계정 점유를 게임 로그인에 연결합니다. 계정 저장소 패치 다음에 profiles/bundles/cluster-account-sessions.patch.yaml을 탑재하고 각 로비에 require_account_ownership: true와 duplicate_login: reject_new를 설정하십시오. 접속 승인 서비스가 없으면 활성화가 실패합니다. 세션은 열린 게임 연결에만 생기므로 그 수는 리스너의 연결 제한을 따르며, verification_seconds와 verification_concurrency는 백그라운드 검사를 제한합니다. 권한을 잃으면 연결을 닫습니다. 언로드는 대기 중인 접속을 취소하고 승인된 연결을 닫은 뒤 정리가 끝날 때까지 기다립니다. IAccountSession 기능은 점유 수명을 넘기지 않고 검증을 제공합니다. 이 계층은 진행 중인 저장소 쓰기나 캐릭터 생성을 격리하지 않습니다. 해당 쓰기 경로의 격리와 종료 대기가 구현되기 전에는 공유 운영 데이터베이스를 활성화하지 마십시오. 기본 단독 서버 프로필은 두 패치를 탑재하지 않습니다.

계정은 모든 클라이언트 빌드가 공유하며, 한 계정은 한 번에 한 빌드에서만 플레이합니다. 코어 번들의 account-builds 행은 모든 빌드의 로그인을 서버 전체의 잠금 하나 아래에서 처리합니다. 계정이 다른 빌드에 접속해 있을 때 새 로그인은 로비의 duplicate_login에 따라 그쪽 세션을 닫거나(kick_old, 기본값) 거부됩니다(reject_new).

계정 인계에는 마이그레이션 0037과 디렉터리의 노드 식별자와 일치하는 persistence.mysql-account-ownership의 명시적 node_id가 추가로 필요합니다. 기본 빈 값은 일반 점유 기능을 유지하며 IAccountHandoffStore를 제공하지 않습니다. 출발 노드는 자신의 인계만 기록할 수 있으며, 데이터베이스는 기록된 목적지 노드의 인수와 출발 노드의 철회만 허용합니다. cluster.account-sessions는 해당 저장소가 있을 때만 IAccountSessionHandoff를 제공합니다. 원격 SDK는 네이티브 점유 핸들, 마이그레이션 IP 주소 또는 브로커 콜백 등록을 전송할 수 없으므로 어댑터가 제공될 때까지 해당 메서드를 명시적으로 지원하지 않습니다. 이 설정은 단독 서버 프로필에서 네이티브 마이그레이션을 활성화하지 않습니다.

선택적 cluster.migration-broker는 cluster.node와 같은 node_id, directory_url을 사용해야 하며 access_key는 해당 노드의 비공개 키입니다. 디렉터리에서 migrations를 활성화해야 합니다 (기본 false). 요청은 현재 임대 자격 증명과 snake_case JSON을 TLS 또는 보안 터널로 전송합니다. 비밀번호는 진단 로그에서 제외됩니다. 공유 계정 이동은 같은 참가 및 데이터 범위, 인증 기관과 실제 영구 데이터 영역 식별자가 필요합니다. 방문자는 명시적 참가 신뢰와 다른 데이터 범위가 필요합니다. 전송만 활성화해도 네이티브 이동이나 좌석 예약이 활성화되지는 않습니다. 가득 찬 수신함은 503, 중복 식별자나 오래된 임대는 409, 응답 시간 초과는 504를 반환합니다.

HTTP 제한 시간은 폴링 대기 및 콜백 제한보다 커야 합니다. 관리되는 작업 하나가 목적지 수신함을 폴링하며 송신 동시 실행 한도를 넘는 요청은 즉시 거부됩니다.

선택적 cluster.migration-destination 행에는 broker, arrivals, 하트비트 식별자와 계정 세션 인계 서비스가 필요합니다. node_id는 하트비트 식별자와 같아야 하며 endpoints에는 서로 다른 { client_build, listener_id, host, port } 항목을 1..64개 지정합니다. host는 정식 DNS 이름이어야 합니다. 목적지는 요청마다 이를 해석하고 IPv4 주소를 요구합니다. 방 요청에는 해당 빌드의 IRoomAdmissionDirectory도 필요합니다. 엔드포인트 누락, 만료된 목적지 임대 세대, DNS 실패 시 준비를 거절합니다. 원래 서버로 돌아가는 요청은 방 좌석을 예약하지 않습니다. 이 행은 아직 네이티브 게임 연결을 인증하거나 원격 방 클릭을 활성화하지 않습니다.

필수 listener_id는 프로필 접두사를 포함한 목적지 전송 행의 정확한 ID입니다. 활성화 시 이 ID와 해당 빌드의 게임 프로토콜을 가진 가시적인 활성 리스너가 정확히 하나 있어야 합니다. 도착 기록은 이 ID를 보관하며 ConnectionAcceptedEvent에서 실제로 관찰한 연결을 확인한 뒤 소비됩니다. 관찰되지 않았거나 닫힌 연결, IP가 아닌 연결, 다른 리스너의 연결은 빌드, 계정 번호 및 주소가 같아도 기록을 소비할 수 없습니다. 거절된 시도는 올바른 연결을 위해 기록을 보존합니다. 이 검사는 계정 권한을 부여하지 않습니다. 네이티브 이전 처리기는 플레이어 상태를 불러오기 전에 계정 인계를 인수해야 합니다.

arrival_lifetime_ms의 기본값은 10000(100..60000), cleanup_interval_ms는 1000(100..10000), operation_timeout_ms는 5000(100..30000)입니다. 방의 room_admission_lifetime_ms는 도착 유효 기간과 준비 시간을 포함하도록 설정합니다. cluster.migration-arrivals의 max_arrivals는 기본 64, 범위 1..4096이며 대기 중인 도착과 정리를 기다리는 만료 기록이 용량을 공유합니다. 만료된 도착은 사용할 수 없습니다. 취소 실패는 기록하고 재시도하며 성공 전까지 용량을 유지합니다. 해제 시 작업 제한 시간 내에 남은 예약을 취소하고 실패를 보고합니다. 도착 기록을 성공적으로 가져간 소비자는 이후 입장 또는 예약 취소를 책임집니다.

INodeLeaseSource와 IMigrationArrivalCleanup은 공유 Contracts 4.12.0 서비스이므로 독립적으로 로드한 플러그인에서도 같은 인터페이스 식별자를 사용합니다. 임대 기록은 SDK로 직렬화할 수 있지만 bearer 토큰은 비밀이며 진단 문자열에서 제외됩니다. 도착 정리 기록에는 IP 주소가 있고 완료 작업은 객체 식별자를 유지해야 하므로 네이티브 어댑터가 필요합니다.

선택적 profiles/bundles/cluster-account-write-fencing.patch.yaml에는 계정 저장소 및 세션 패치, 마이그레이션 0036, 계정 점유를 요구하는 로비가 필요합니다. 이 패치는 core.packet-router.decoratable: true와 persistence.mysql.require_account_write_authority를 설정하고 cluster.account-mutations를 탑재합니다. 명시적으로 장식을 켜지 않은 일반 라우터는 직접 호출을 유지합니다. IAccountMutationScopes는 변경되지 않는 점유 핸들을 원래 게임 세션에 연결합니다. 패킷 처리는 해당 세션을 선택하며 플레이어별 경기 정산과 보상 카드 지급은 수신자의 원래 세션을 선택합니다. 지연된 이전 작업은 새 세션의 권한을 빌릴 수 없습니다. 보호된 MySQL 쓰기는 플레이어 상태를 변경하기 전에 동일한 연결과 트랜잭션에서 권한 행을 잠그고 검증합니다. 점유 이전은 이미 승인된 트랜잭션의 종료를 기다립니다. 권한이 없거나 교체되면 다시 획득하지 않고 실패합니다. 새 계정의 캐릭터 생성은 원자적으로 초기화하며 기존 계정 변경에는 해당 점유가 필요합니다. Contracts 4.4.0은 이 네이티브 수명 및 트랜잭션 인터페이스를 제공하며 원격 SDK는 호출을 명시적으로 거부합니다. 이 기능은 공유 저장소를 구성하거나 다른 플러그인을 자동 보호하거나 노드 간 방 입장을 구현하지 않습니다. 공유 운영 데이터를 활성화하기 전에 나머지 모든 쓰기 경로를 검토하십시오. 단독 서버 프로필은 이 패치를 탑재하지 않습니다.

문제가 생기면 ​

  • 환경 변수 누락으로 구성이 실패합니다. 오류 메시지가 변수 이름을 알려 줍니다. .env(또는 프로세스 환경)에 추가하거나, 빈 값이 유효한 곳에서는 ${VAR:-default} 형식을 사용하십시오.
  • 패치가 알 수 없는 행을 가리킵니다. 프로필과 패치 목록이 어긋난 것입니다. 패치를 적용하지 않은 프로필이나 해당 행을 제공한 번들에서 --dump-config로 행 id를 확인하십시오.
  • 게임 프로필이 클라이언트 데이터 메시지와 함께 활성화에 실패합니다. 메시지에 나온 data/dataraw 디렉터리가 없습니다. 해당 빌드 id의 디렉터리를 준비하거나 management를 사용하십시오.
  • 리스너가 바인딩할 수 없습니다. 다른 프로세스가 포트를 점유하고 있습니다. 빌드별 포트 변수를 바꾸거나 해당 프로세스를 중지하십시오.

순서대로 확인하는 목록은 문제 해결을 참고하십시오.

라운드 취소와 시작 규칙 ​

다음 ingame 행 옵션은 모든 빌드에 적용됩니다. 라운드를 불러오거나 플레이하는 중에 연결이 끊긴 플레이어가 있으면 라운드가 취소됩니다. 결과는 표시되지 않으며 남은 모든 플레이어는 대기실에서 나간 플레이어와 같은 방식으로 광장으로 이동합니다. cancel_round_on_disconnect(기본값 true)로 이 동작을 끌 수 있으며, 그러면 연결이 끊긴 플레이어만 나갑니다. 스스로 방을 나가거나 !plaza를 입력하면 일반적으로 나머지는 계속 플레이합니다. 좀비 탈출을 활성화한 경우 Lua 방장이 나가면 보상 없이 라운드를 취소합니다. load_timeout_ms(기본값 60000, 0은 제한 없음, 최대 600000)는 그때까지 모든 플레이어가 불러오기를 마치지 못하면 같은 방식으로 라운드를 취소합니다. 가장 느린 클라이언트의 맵 불러오기와 매치 연결 준비 시간보다 크게 두십시오. plaza_command_during_round(기본값 true)를 false로 두면 !plaza는 플레이어를 진행 중인 라운드에서 빼내지 않고 시간 제한이 끝난 것처럼 라운드를 바로 끝냅니다. 진행 중인 라운드에서 빠지면 오류가 나는 클라이언트(kr-186)를 위한 옵션이며, 플레이어는 방에서 !plaza를 다시 입력합니다. menu_session_chat(기본값 false)는 메뉴에서 대기실 채팅 패킷으로 보낸 채팅에 응답합니다. 해당 빌드에서 메뉴에 있는 모든 플레이어가 발언자 닉네임이 담긴 시스템 메시지로 보게 되며, 채팅 모듈 패킷이 없는 빌드(kr-186)를 위한 옵션입니다.

좀비 모드에서는 현재 있는 모든 플레이어가 감염되어야 좀비가 이깁니다. 연결이 이미 닫힌 플레이어는 생존자로 세지 않습니다.

두 가지 시작 규칙은 기본적으로 꺼져 있습니다. start_min_players(0–32, 좌석과 AI 플레이어 합계)는 인원이 부족하면 방장의 시작을 거부합니다. start_requires_team_balance는 레드/블루 팀 모드에서 assign_spawn_teams_on_start가 팀 없는 플레이어를 배치한 뒤 두 팀 인원 차이가 한 명보다 크면 방장의 시작을 거부합니다. 그렇지 않으면 팀 없는 플레이어는 레드로 셉니다. 클라이언트에는 이 규칙에 맞는 거부 사유가 없으므로 서버는 로그만 남기고 방은 계속 대기합니다. 네이티브 자동 시작은 검사하지 않습니다.

다음 단계 ​

배포에서 릴리스 빌드와 실행을 이어서 살펴보거나, 플러그인에서 각 행이 실제로 하는 일을 확인하십시오.

최신 계열 대기방 강제 퇴장 ​

dialect.rooms.config.room_kicking의 기본값은 false입니다. kr-1256, cn-774, tw-454에서 활성화하면 검증된 닉네임 요청과 퇴장 알림이 공통 방장 권한 로직에 연결됩니다. 대기 중인 방의 방장만 방 안의 다른 플레이어를 내보낼 수 있습니다. 좌석 제거 전에 알림을 보내며, 퇴장한 플레이어는 광장으로 돌아갑니다. 이 옵션은 modern_rooms: true가 필요하고 plaza_only와 함께 사용할 수 없습니다. 필요한 기본 패킷 이름이나 구조가 없으면 활성화에 실패합니다.

dialect.rooms.config.npc_rounds는 해적 모드가 기다리는 현대 클라이언트 방장의 기본 웨이브 관리자에 응답합니다. kr-1256 번들에서 기본으로 켜져 있습니다. 해적 모드 방에서는 방장의 웨이브 시작, 웨이브 종료, 몬스터 생성 표 응답을 모든 멤버에게 보내고, 전체 웨이브 종료 응답은 방장에게만 보냅니다. 다른 모드에서는 이 요청을 무시합니다. 일반 대전의 몬스터 생성 요청은 형식만 검사하고 아직 전달하지 않습니다. 전송 방식이 아직 확인되지 않았기 때문입니다. 초기 튜토리얼도 같은 바인딩을 사용하며 여전히 혼자 플레이하는 방장에게만 응답합니다. 이 옵션은 대전 바인딩이 있는 modern_rooms: true가 필요합니다.

단일 빌드의 격리 시험에서는 --patch tools/local-checks/isolated-memory.patch.yaml에 더해 --patch profiles/bundles/modern-room-kicking.patch.yaml을 지정합니다. all 배포에서는 패치의 set 작업을 대상 빌드별로 Git에서 제외된 local.patch.yaml에 복사하고, 접두사가 없는 dialect.rooms 행 ID를 사용합니다. 실제 클라이언트 승인 전에는 옵션을 꺼 두십시오. 기존 레거시 강제 퇴장 바인딩은 이 옵션의 영향을 받지 않습니다.

최신 계열 빠른 매칭 ​

cn-774와 tw-454에서는 dialect.rooms.config.quick_matching이 기본 로비 상태 매칭 요청을 등록합니다. quick_match_default_mode_id는 공통 매칭 모드를 선택합니다(0–65535, 기본값 0은 요청 거부). kr-1256에서는 매칭 요청이 확인되지 않아 이 옵션을 켜면 로드 시 오류가 납니다. 제공되는 최신 계열 프로필에서는 실제 클라이언트 검증 전까지 이 옵션이 꺼져 있습니다.

기본 서버 선택 후 로그인 연결 ​

선택 항목 dialect.messages.config.center_migration_prelogin의 기본값은 false이며 일반 로그인이 필요합니다. kr-1256에서는 protocol.config.pre_handshake_opcodes: [gcpReqMoveInto]도 함께 설정해야 패치 요청 전의 새 서버 선택 연결을 허용합니다. 어댑터는 두 워드 본문의 정확한 길이, 보존된 식별자 0, 단계 플래그 0 또는 1을 검증하고 이미 인증되었거나 반복된 요청을 거부한 후 기본 패치 응답을 보내 일반 로그인을 계속합니다. IInitialHandshakeContinuation은 현재 패킷 디스패치 동안만 유효하며 핸들러가 성공적으로 반환한 경우에만 적용됩니다. 버전 검증 표시, 티켓 사용, 플레이어 식별자 등록 또는 마이그레이션 승인을 제공하지 않습니다. 로비는 여전히 유효한 일회용 Launcher 티켓을 요구해야 하며 계정 이름으로 대체할 수 없습니다. 기본 단일 서버 프로필은 변경되지 않습니다. 서버 와이어 테스트와 실제 클라이언트 검증은 별개입니다.

dialect.messages.native_migration의 기본값은 false입니다. center_migration_prelogin과 네이티브 이동 요청 라우터 하나를 공유합니다. 식별자가 0이면 명시적인 사전 로그인 옵션이 필요하며, 0이 아니면 MoveIntoRequested로 전달합니다. 전달만으로 초기 핸드셰이크 제한이 해제되거나 계정 소유권이 부여되지는 않습니다. 이 옵션은 표로 검증한 이동 응답과 연결 전환 메시지도 제공합니다. 확인 및 완료 메시지는 opcode 표에 선언된 경우에만 등록됩니다. 목적지 허용 처리기는 리스너에 연결된 도착 기록을 확인하고 계정 권한을 인수한 뒤 플레이어 상태를 설치해야 핸드셰이크 연속 처리를 요청할 수 있습니다. 목적지 허용은 아래의 선택적인 cluster.migration-admission 행이 제공합니다. 출발 노드 조정은 cluster.migration-source가 제공하며 배포 연결은 명시적으로 활성화해야 합니다.

선택적인 cluster.migration-admission 행은 대상 예약 후 공유 계정의 방 이동을 조정합니다. 해당 빌드의 로비와 방 서비스가 보이는 위치에 배치합니다. lobby.native_migration(기본 false)과 dialect.messages.native_migration을 활성화해야 하며, 로비는 계정 소유권, 영구 저장소의 기존 계정 조회, 저장형 인벤토리와 지갑, 캐릭터 생성 미리보기 비활성화를 요구합니다. 별도 조정 플러그인은 로비와 방 서비스의 순환 의존성을 방지합니다. Contracts 4.16.0은 IRetainedPlayerAdmission을 추가합니다. 설치 결과는 네이티브 플레이어 상태이므로 원격 SDK 어댑터는 없습니다.

현재 로그인을 소유한 메인 메뉴 또는 광장 게임 연결만 출발할 수 있습니다. 방 흐름은 장면 잠금을 유지하며 파티 디렉터리는 원자적 단독 예약을 지원해야 합니다. 기존 초대를 취소하고 정리 전까지 해당 플레이어의 새 초대와 파티 가입을 거부합니다. 단독 예약의 상한은 설정된 대기 초대 용량입니다. 준비 전에 플레이어는 Migrating 단계에 들어갑니다. 목적지가 정확한 방 인스턴스를 예약한 뒤 출발지가 계정 쓰기 권한을 넘기고 표에 정의된 네이티브 이동 제안을 보냅니다. 시간 초과, 응답 유실, 전송 실패 또는 연결 무효화 시 정확한 목적지 요청을 취소하고 해당 인계만 철회합니다. 목적지가 이미 인수했다면 일반 계정 권한을 다시 획득하지 않고 출발 연결을 닫습니다. 정리 실패는 용량과 단독 예약을 유지하여 재시도합니다. Contracts 4.17.0은 출발 인터페이스와 네이티브 제안을 추가하며 소유된 파티 예약에는 원격 SDK 어댑터가 없습니다.

공유 계정 이동은 여러 방을 방문해도 최초 로그인 노드와 네이티브 채널을 유지합니다(Contracts 4.18.0). 출발 플러그인에는 IMigrationTargetDirectory가 필요하며 home_unavailable_notice_enabled가 true이면 단일 네이티브 ServerNotice 전송기도 필요합니다. 브로커는 인증된 조회로 홈 노드의 현재 임대를 확인하며 준비 상태, 용량, 참가 범위, 영구 데이터 도메인과 계정 발급자를 다시 검사합니다. 조회 자체는 도착 기록이나 계정 권한을 부여하지 않습니다. 홈 노드가 거부하거나 사용할 수 없으면 현재 노드에 머무르며 알림이 활성화된 경우 home_unavailable_notice(1..512자)를 표시합니다.

InGame의 return_on_leave 기본값은 home이며 stay는 방문 노드에 머무릅니다. return_delay_ms 기본값은 1500(0..60000)입니다. 정상 방 퇴장 정리와 경기 퇴장 정산을 마친 뒤 복귀를 기다립니다. 대기 중에는 장면 잠금을 유지하지 않습니다. 연결 종료, 연결 교체 또는 장면 세대 변경은 이전 복귀를 취소하며 이후 광장 퇴장으로 다시 시도할 수 있습니다. 홈 InGame에서 home_migration_admission: true를 설정하고 room_admission_reservations와 네이티브 메인 메뉴 전송기를 제공해야 합니다. 홈 준비는 방 좌석을 예약하지 않습니다. 같은 계정 인수와 연결 승격 후 보존된 장비로 출발 노드의 유휴 장면을 복원하고 튜토리얼을 다시 제안하지 않습니다. 홈 요청은 home_scene (MainMenu 또는 Plaza)을 전달하며 방 요청은 항상 MainMenu를 사용합니다. 광장에서 귀환하면 기존 네이티브 광장 설치를 사용하여 메인 메뉴로 다시 이동하지 않습니다. 광장 인코더가 없는 빌드는 메인 메뉴로 복귀합니다. Contracts 4.21.0은 MigrationRequest와 IMigrationHomeAdmission.EnterAsync에 장면 매개변수를 추가합니다. 파티 디렉터리가 있으면 목적지는 승격 확인과 장면 설치까지 원자적 단독 예약을 유지합니다. 정리 실패 시 자원 해제까지 예약을 유지합니다. 기본 프로필은 배포와 실제 클라이언트 검증 전까지 비활성화 상태입니다.

파티장은 파티와 함께 이동합니다. 파티장이 원격 방으로 출발하거나 원래 서버로 돌아갈 때, 같은 빌드에서 메인 메뉴나 광장에 있는 모든 온라인 파티원은 파티장의 이동 제안 직후 같은 목적지의 제안을 받습니다. 두 클라이언트 계열 모두 스스로 요청하지 않았어도 수락된 이동 제안을 받으면 대기 연결을 엽니다. 파티원은 단독 예약 없이 이동하며, 원래 서버 복귀는 원래 서버가 파티장과 같은 파티원만 데려갑니다. 방이나 라운드에 있는 파티원, 또는 목적지가 거절한 파티원(예: 방이 가득 참)은 자기 노드에 남아 로컬 파티를 유지하며, 파티장의 이동은 취소되지 않습니다. 파티장이 아닌 파티원은 혼자 출발할 수 없고 스스로 복귀를 시작하지도 않습니다. 각 요청은 party_leader에 파티장을 적고 단독 이동에서는 노드 전송에서 이 필드를 생략합니다. 목적지는 IPartyDirectory.RejoinAsync로 도착한 각 플레이어를 이미 도착한 파티장의 파티에 다시 넣으며 도착 순서는 상관없고, 짝이 없는 도착은 도착 기한이 지나면 버립니다. Contracts 4.23.0이 둘을 추가합니다. 아직 네이티브 클라이언트에서 확인되지 않았습니다.

디렉터리의 nodes[].native_migration_builds 기본값은 빈 목록입니다. 네이티브 출발, 리스너에 연결된 목적지 입장 및 연결 승격 처리기가 배포되고 클라이언트 경로를 검증한 빌드만 나열합니다. 항목은 중복 없이 설정된 엔드포인트를 지정해야 합니다. 디렉터리에서 migrations: true를 켜도 양쪽 노드가 빌드를 명시해야 공유 계정 원격 방을 참가 가능으로 표시하거나 이동 요청을 수락합니다. 홈 복귀에도 같은 검사가 적용됩니다. 참가 표시는 유효한 양쪽 임대, 준비된 빌드, 목적지 여유 용량, 일치하는 참가·방 디렉터리 범위, 동일한 영구 데이터베이스 ID와 계정 발급자도 요구합니다. 목록은 좌석 예약이나 계정 권한을 부여하지 않으며 준비 단계에서 경로를 다시 확인합니다. 방문자 입장이 구현되기 전에는 독립 데이터 도메인은 목록 검색만 제공합니다.

예약한 방이 플레이어 입장 전에 닫히거나 경기를 시작하거나 비밀번호를 변경하면, 입장 조정기는 좌석을 해제하고 대상 노드의 계정 쓰기 권한을 유지한 채 기존 플레이어 상태로 메인 메뉴를 설치합니다. cluster.migration-admission은 빌드마다 정확히 하나의 IMigrationRoomRecovery 서비스를 요구하며, InGame은 home_migration_admission: true일 때 이를 제공합니다. 복구는 원래 핸드셰이크 메시지 처리가 끝난 후 return_on_leave와 return_delay_ms를 적용합니다. 그동안 장면이 바뀌면 귀환을 취소하고, stay는 플레이어를 대상 노드에 남깁니다. 복구 작업은 max_migrations 용량을 공유하며 입장 잠금 밖에서 실행됩니다. 메인 메뉴 설치에 실패하면 연결을 닫고 획득한 자원을 해제합니다. Contracts 4.19.0에 이 복구 서비스가 추가되며 기존 메인 메뉴 메시지 형식은 유지됩니다.

방 서비스는 IRemoteRoomMigrationEndpoint(Contracts 4.20.0)를 제공하고, cluster.migration-source는 해당 client_build의 엔드포인트 하나에 연결됩니다. 방 서비스가 하트비트에 의존하는 이동 소스를 기다리지 않으므로 방 공개, 노드 하트비트 및 이동 기능을 함께 시작할 수 있습니다. 중복 소스나 일치하는 방 엔드포인트의 부재는 활성화 오류입니다. 소스를 해제할 때 새 원격 입장을 거부하고 진행 중인 입장 및 원래 서버 복귀 호출이 끝날 때까지 기다린 후 소스를 해제합니다. 소스 또는 하트비트를 다시 로드해도 방 서비스는 유지됩니다. 추가 프로필 행은 필요하지 않으며 이동 기능을 기본으로 활성화하지 않습니다.

레이싱 대포 중계 ​

extreme_racing_cannon은 dialect.rooms.config와 ingame.config 모두에서 기본값이 false이며, extreme_racing_initialization과 함께 양쪽에서 활성화해야 하고 빌드의 extreme_racing_cannon 능력(현재 kr-1256만)이 필요합니다. 활성화하면 방은 설정된 각 맵의 option.ini 옆에서 Maps/<stage_directory>/cannon.ini를 읽습니다. 선언된 대포 수는 맵의 Cannon/PairCount와 같거나 0이어야 하고, 각 대포에는 WEAPONCOUNT, 양수 INTERVAL, 맵에 있는 STAGE가 필요하며, 무기마다 WEAPONID(50000~50008), COUNT, 유한한 양수 SCALE을 담은 [CannonN_WeaponM] 구역이 있어야 합니다. 그 밖의 불일치나 형식 오류는 활성화를 실패시킵니다. 대포를 0개로 선언한 맵(예: 9쌍을 초기화하는 rel_Racing01_Extreme)은 대포를 예약하지 않으며, 그 대포 쌍은 유휴 상태로 남고 어떤 발사도 통과하지 않습니다. 방은 중계 대포 발사 프레임(중계 32902)의 행위자가 보낸 사람 자신의 좌석이고, 벡터가 유한하며, 대포 식별자가 이번 세대에 초기화되었고, 무기가 그 대포의 리소스 목록에 있으며, 아직 응답되지 않은 서버 명령 하나와 정확히 일치할 때만 이를 받아들인 뒤, 원본 바이트를 초기화된 다른 참가자에게 한 번 전달합니다. 보낸 사람에게 되돌리지 않고, 재시도하지 않으며, 일련번호도 바꾸지 않습니다. 대포 쌍마다 미응답 명령은 최대 하나이므로 장부 크기는 맵의 대포 수입니다. 이 옵션만으로는 대포 명령을 보내지 않으므로 아래 스케줄이 명령을 발행하기 전에는 어떤 발사도 통과하지 않습니다. 네이티브 클라이언트 검증은 아직 끝나지 않았습니다.

레이싱 대포 스케줄 ​

extreme_racing_cannon_fire는 ingame.config에서 기본값이 false이며 extreme_racing_cannon이 필요합니다. 클라이언트에는 대포를 쏘는 타이머가 없으므로 이 옵션이 꺼져 있으면 대포는 발사되지 않습니다. 켜면 각 레이스 라운드는 레이스 시계(S2C 711)를 보낸 직후 대포를 가동하고, 명령(S2C 718)은 정확히 한 좌석, 즉 원점 좌석에만 갑니다. 그 클라이언트가 발사하고 중계(중계 32902)하면 방 경로가 이를 전달합니다. 원점 좌석, 주기, 무기 순서는 네이티브 동작이 아니라 서버 정책이며, INTERVAL을 읽는 클라이언트 코드는 찾지 못했습니다.

  • 원점 좌석은 초기화를 받았고 게임 연결이 열려 있는 가장 낮은 슬롯의 좌석입니다. 각 수신자가 자기 탄환을 발사하므로 명령은 둘 이상의 좌석에 보내지 않습니다.
  • 각 대포는 레이스 시계가 시작되고 INTERVAL 후에 처음 만기가 되고, 이후 만기 때마다 한 간격 뒤에 다시 만기가 됩니다. 쌍에 미응답 명령이 남아 있는 대포는 대기열에 넣지 않고 건너뛰며, 시계가 멈췄다고 놓친 발사를 몰아서 보내지 않습니다. STAGE는 사용하지 않습니다. 무기가 여러 개인 대포는 파일 순서대로 순환합니다.
  • 명령은 그룹 0(모든 대포 그룹), 대포 쌍의 첫 식별자, 스케일 1.0을 담습니다. 중계되는 발사에는 스케일이 없으므로 다른 값은 원점의 대포만 바꿉니다.
  • 레이스 라운드가 닫히거나, 라운드가 취소되거나 끝나거나, 방이 멈추거나, 세대가 바뀌면 주기가 멈추고 미응답 명령은 폐기됩니다. 다음 레이스 라운드에서 다시 가동됩니다.
  • 원점 좌석이 나가거나 연결이 끊기면 그 미응답 명령은 폐기되고 다시 보내지 않으며, 초기화된 남은 좌석 중 가장 낮은 슬롯이 이후 명령에 한해 새 원점이 됩니다. 초기화를 받지 못한 좌석은 선택되지 않으며 명령 이력도 받지 않습니다.
  • 전송이 실패하면 그 세대의 스케줄이 끝납니다. 명령은 폐기되고 재시도하지 않으며 레이스는 대포 트래픽 없이 계속됩니다.

네이티브 클라이언트 검증은 아직 끝나지 않았습니다.

WeaponMaster 라운드 ​

dialect.rooms.config.weapon_master의 기본값은 false이며, 빌드의 weapon_master 능력(현재 kr-1256만, cn-774와 tw-454는 상속하지 않음)과 함께 modern_rooms, 그리고 result_scoreboard_modes에 모드 26이 포함되어야 합니다. 이 옵션은 좌석에 무기를 지급하는 장비 프레임과, 여러 번 사망한 뒤 클라이언트가 새 무기를 요청하는 프레임을 마운트합니다.

같은 프로토콜의 인게임 행에 ingame.config.weapon_master_levels를 함께 설정해야 하며, 둘 중 하나만 있으면 활성화가 실패합니다. 이 옵션에는 기본값이 없습니다. 빈 목록이면 모드 26은 일반 시간제 라운드로 진행됩니다. 목록의 각 항목은 순서대로 한 레벨이며, experience 기준값(첫 레벨은 0, 이후 레벨마다 더 크고 65535 미만)과 선택적인 weapons 목록(item은 양수 아이템 ID로 같은 레벨 안에서 중복 불가, weight는 양수)을 가집니다. 무기를 나열하지 않은 레벨은 공유 weapon_master_weapons 풀에서 뽑으므로, 레벨과 무관한 무기는 한 번만 적으면 됩니다. weapon_master_experience는 인정된 각 이벤트가 주는 경험치를 { event, points }로 나열합니다. 이벤트는 kill, knockdown, rescue 중 서로 다른 것이고 점수는 양수이며, 나열하지 않은 이벤트는 경험치를 주지 않습니다. 모드 26은 native_life_every_mode 또는 26을 포함한 native_life_mode_ids로 네이티브 생명 판정도 사용해야 합니다. 프레임은 무기를 무기 카탈로그 ID로 지정하며 kr-1256 sub_4ADD70이 이를 해석합니다. 주무기의 상점 아이템 ID는 200000에 그 ID를 더한 값입니다. kr-1256 프로필의 패치는 200 경험치 간격의 여섯 레벨, 킬당 100 경험치, 구형 L1, L2, L3, S1, S2, R3 주무기로 이루어진 하나의 무작위 풀을 사용합니다.

모든 좌석은 라운드 시작 시 무기를 받습니다. 인정된 이벤트는 경험치를 더하고, 좌석의 경험치가 다음 레벨의 기준값에 도달하면 그 레벨로 오르며 그 레벨의 무기 하나를 받습니다. 한 이벤트가 여러 기준값을 넘어도 무기는 하나입니다. 실시간 점수는 각 좌석의 레벨, 경험치, 현재 레벨의 시작 경험치, 다음 레벨의 경험치를 종류 31~34로 전달합니다(kr-1256 sub_9E9160이 좌석 기록 +204~+216에 저장). 마지막 레벨에서는 다음 값이 시작값보다 1 큽니다. 마지막 레벨에 가장 먼저 도달한 좌석이 승리하고 라운드는 즉시 끝납니다. 클라이언트가 마지막 무기 이후 정해진 횟수만큼 플레이어가 죽었다고 보고하면 서버는 같은 레벨의 새 무기를 줍니다. 서버는 그 횟수 WeaponMasterNoPangDeadCount를 클라이언트의 Config/GameOption.xml에서 읽으므로 이 파일을 가져와야 하며, 값이 없거나 중복되거나 양수가 아니면 활성화가 실패합니다. 너무 이른 요청은 기록되고 무시됩니다. 부활은 공통 규칙을 따릅니다. 아무도 마지막 레벨에 도달하기 전에 시간이 끝나면 가장 높은 레벨의 좌석이 승리하며, 모든 좌석의 레벨이 같으면 무승부입니다. 결과 화면의 레벨 열은 여전히 계정 레벨을 표시합니다. 네이티브 클라이언트 검증은 아직 남아 있습니다.

밴픽 ​

밴픽은 원래 클라이언트에 없던 서버 기능입니다. 기본으로 설치되어 켜져 있지만 누군가 규칙을 정하기 전에는 아무것도 금지하지 않습니다. core의 banpick 행이 서버 전체 문서를 갖고, 각 빌드의 banpick.room 행(그 빌드 ingame 행의 하위 행)이 그 빌드의 방에 적용합니다. 두 행을 끄면 기능이 사라집니다.

금지는 두 가지입니다.

  • 방 금지는 방장이 정하며 방이 있는 동안만 유지됩니다. !banpick(별칭 !bp)은 add <아이템 번호, 이름 또는 그룹>, remove <...>, set <번호 또는 그룹...>(목록 전체를 한 번에 바꾸며 오버레이가 이 방식을 씁니다), clear, list [페이지]를 받습니다. 누구나 목록을 볼 수 있고, 방장만 게임 시작 전에 바꿀 수 있습니다.
  • 서버 정책은 관리자가 gbanpick(별칭 gbp, 권한 game.management.banpick)으로 정합니다. state_path(기본 data/banpick-policy.json)에 저장되며 저장할 때마다 수정한 리비전을 밝힙니다. state_path가 비어 있으면 설정의 policy는 읽기 전용입니다.

문서 구조는 클라이언트 정책과 같습니다. policy.groups는 모든 빌드가 공유하는 ShopItem2의 MainCategory/SubCategory 시트 번호나 function 열로 아이템 그룹을 정합니다. 기본 그룹에는 weapon, sniper, rifle, shotgun, clothes, hat, character, pet이 있습니다. policy.policies에는 정책을 몇 개든 둘 수 있고, 정책마다 범위(builds, modes, rooms: all|public|password)와 유형이 있는 규칙이 있습니다.

규칙 유형효과
block정책이 적용되는 곳에서 아이템 장착을 거부하고, 착용한 채로는 라운드를 시작할 수 없습니다.
confirm방 금지와 같은 강도입니다. 방장에게 경고하고 방장은 그래도 시작할 수 있습니다.
warn허용되지만 누가 착용했는지 방에 알립니다. 새로 들어온 사람은 이미 착용한 모든 사람의 알림을 받습니다.

방장이 시작을 누를 때 누군가 방 금지 또는 confirm 아이템을 착용하고 있으면 모든 멤버에게 누가 무엇을 착용했는지 알립니다. Nirinsou Link 오버레이가 있는 방장은 확인 창을 보고, 그 밖의 방장은 reclick_window_ms(기본 10000) 안에 시작을 다시 누르거나 !bp start를 입력하면 됩니다. announcement_items(기본 25)보다 긴 목록은 개수만 알립니다. 오버레이는 game.ban.list.changed, game.ban.start.confirm, game.ban.warn을 받고 game.ban.list.get, game.ban.catalog.search 요청으로 목록을 읽습니다. 확인 창의 확인을 포함해 오버레이가 하는 모든 변경은 실행에 묶인 명령 채널(game.command.execute)로 보내는 bp 명령이므로 직접 입력한 명령과 똑같이 검사됩니다. 이를 위해 companion.commands 행을 켜야 합니다(core에서는 기본으로 꺼져 있습니다). 메시지 행이 서버 공지를 보내지 않는 빌드는 같은 내용을 시스템 채팅으로 받습니다. 네이티브 클라이언트 검수는 아직입니다.

네이티브 광장 파티 모집 ​

지원하는 열세 프로필에는 광장 모집이 활성화되어 있습니다. 사용자 지정 프로필은 dialect.rooms와 ingame에 각각 plaza_recruitment: true를 설정하고 해당 party 행을 탑재해야 합니다. 두 옵션의 기본값은 false이며, 네이티브 바인딩이나 파티 디렉터리 또는 광장 기능이 없으면 활성화에 실패합니다. ingame.plaza_recruitment_text_length는 기본 128 UTF-16 문자이며 1–1024를 허용합니다. 게시와 수정에는 채팅 속도 제한을 적용하지만 모집 취소는 계속 허용합니다.

현재 광장의 파티장만 모집할 수 있습니다. 네이티브 표지판 상태, 말풍선, 파티 구성과 장면 따라가기를 함께 갱신합니다. 취소, 퇴장, 장면 변경 또는 파티장 교체 시 이전 표지판을 지웁니다. KR1256과 CN2019는 파티장이 선택한 분류와 정원으로 페이지당 열 개의 모집 문서를 표시합니다. 목록에서는 현재 노드의 파티장에게만 가입할 수 있으며, 원격 플레이어의 광장 외형을 표시하는 것만으로 다른 노드의 파티 가입을 허용하지는 않습니다. 입장 위치는 네이티브 클라이언트가 결정하고 서버는 실제 위치 보고만 재전송합니다.

경기 자동 메달은 기본적으로 별도 비활성화 상태입니다. titles 행에 round_medals_enabled: true를 설정하고 비어 있지 않은 round_medal_rules 목록을 제공해야 합니다. 각 규칙은 네이티브 medal_id, 정확한 mode_ids, metric, 경계를 포함하는 minimum과 선택적 maximum, 지급 count(기본값 1), minimum_participants(기본값 2, 실제 플레이어만 집계)를 지정합니다. 지표는 Completed, Wins, Kills, Knockdowns, Rescues, Score, Deaths, Stars입니다. 같은 메달은 하나의 규칙에만 사용할 수 있습니다. max_round_medal_rules(기본값 256)와 max_modes_per_round_medal_rule(기본값 128)은 보관하는 정책의 크기를 제한합니다. 기준값과 허용 모드는 명시적인 배포 정책이며, 칭호를 활성화하는 것만으로 과거 지급 규칙이 선택되지는 않습니다.

경기 정책은 서버가 인정한 최종 통계를 사용합니다. 메달, 경기 진행도, 지갑 보상과 경기 영수증은 원자적 경기 메달 정산을 선언한 공급자를 통해 같은 트랜잭션에서 커밋됩니다. Memory, MySQL, SQLite는 모두 이 기능을 구현합니다. 완전히 같은 경기를 다시 정산해도 메달은 중복 지급되지 않습니다. 지급 시 칭호 창을 열지 않으며, 다음 메달 조회에서 현재 잔액을 반환합니다. 예를 들어 다음 패치는 실제 플레이어가 최소 두 명이고 인정된 버블 수가 5~9인 아이템전 경기에서 네이티브 메달 하나를 지급합니다. 기준값은 정책 예시입니다.

yaml
- set:
    id: titles
    config:
      round_medals_enabled: true
      round_medal_rules:
        - medal_id: 30007
          mode_ids: [3]
          metric: Knockdowns
          minimum: 5
          maximum: 9
          count: 1
          minimum_participants: 2

기간 제한 획득에는 서버에 설치된 acquisition_time_zone(예: Asia/Shanghai)을 명시해야 합니다. 빈 값이면 기간 제한 획득을 허용하지 않습니다. 네이티브 획득 기간은 월, 일, 시, 분을 양 끝 경계까지 포함해 비교하고 연도는 무시합니다(kr-812 sub_4FE3D0, kr-1256 sub_EAE090). 따라서 현지 시간 기준으로 매년 반복되는 기간이며, 연말을 넘는 구간을 자동으로 순환 처리하지 않습니다. 이 제한은 이미 소유한 칭호의 장착에는 적용되지 않습니다.

네이티브 stock과 stock-set 추가 보상은 같은 상점 워크북에서 해석하며 칭호와 메달 비용에 함께 커밋됩니다. Memory와 MySQL은 독립된 영수증을 보관하므로 칭호가 삭제되거나 만료되어도 추가 보상을 반복 지급하지 않습니다. MySQL에는 마이그레이션 0046이 필요합니다. SQLite schema 13에는 추가 보상 영수증 기능이 없으므로 추가 보상이 있는 칭호 획득만 거부하며, 일반 교환과 메달 조회 및 경기 메달은 계속 지원합니다. 현재 확인한 stock 보상은 영구 또는 일수 지급을 사용하며, 루찌 보상이 포함된 stock-set은 지원하지 않습니다. 네이티브 메달 추가 보상 참조에는 수량 열이 없으므로 bonus_medal_quantity로 양의 정수 지급량을 명시해야 합니다. 생략하면 해당 획득은 허용되지 않습니다.

커플 및 챌린지 칭호 획득은 아직 지원하지 않습니다. 커플 관계가 존재한다는 사실만으로 다이아 커플링 조건을 충족하지 않으며, Luxury, Gallery, Honor 조건에는 각 시스템의 권위 있는 게임 상태와 자동 지급 경로가 필요합니다. Favorite 칭호는 kr-1256에서의 예외입니다. BFF_FAVORITE_TITLES_ENABLED=true(BFF_TITLES_ENABLED와 BFF_FAVORITE_WEAPON_ENABLED가 필요하며 기본값은 꺼짐, kr-1256 전용)일 때 계정의 무기 Article 1, 2, 3개가 Favorite 달인 등급이면 칭호 400312, 400313, 400314가 훈장 소모 없이 영구 지급되며, 로그인 시와 Favorite 포인트가 지급될 때마다 확인합니다. 지급 시 인벤토리를 게시한 뒤 칭호 창의 진행도(S2C 933, 조건 6, 현재 값은 요구 값을 넘지 않음)를 보냅니다. 확인 시점에 계정이 다른 쓰기 작업 중이면 이번 확인은 건너뛰며, 칭호는 다음 로그인이나 다음 Favorite 포인트 지급 때 지급됩니다. 훈장으로 이 칭호를 얻는 것은 계속 거부됩니다. 네이티브 클라이언트 검증과 실제 MySQL 환경 검증은 아직 남아 있습니다.

선택적 사용자 지정 방 규칙 ​

kr-1256 프로필에는 profiles/bundles/custom-room-rules.patch.yaml이 포함되어 있습니다. BFF_CUSTOM_ROOM_RULES_ENABLED의 기본값은 true이며, true로 설정하면 dialect.rooms와 ingame의 custom_room_rules가 함께 활성화되고 클라이언트 데이터의 Config/CustomGameMode.xml을 사용합니다. 이 번들은 다른 빌드에서 해당 기능을 활성화하지 않습니다.

ingame 행은 custom_room_rules_max_bytes(기본값 8388608), custom_room_rules_max_rows(선택한 시트 전체에서 희소 행 채우기를 포함한 4096행), custom_room_rules_max_columns(64), custom_room_rules_max_cell_characters(8192)로 워크북 파싱 자원을 제한합니다. 클라이언트 데이터가 없거나 바인딩이 지원되지 않거나 설정이 잘못되면 활성화가 실패합니다. 네이티브 클라이언트 검증은 아직 남아 있습니다.

선택적 레거시 과학실 ​

비동기 레시피는 시작한 로그인에 계속 연결됩니다. 로그인이 교체되면 이전 플레이어의 재료를 소비하거나 이전 완료 결과를 전송하지 않습니다. 장면이나 로그인 변경 전에 커밋한 인벤토리는 유지되며 다음 일반 인벤토리 전송에서 복원됩니다.

kr-812, id-1809, cn-324, cn-406, cn-404, cn-408, cn-705, cn-706, cn-717 프로필에는 profiles/bundles/science-lab.patch.yaml이 포함됩니다. BFF_SCIENCE_LAB_ENABLED의 기본값은 true이며 science-lab 행과 dialect.messages.config.legacy_science_lab를 함께 제어합니다. 이 행에는 공유 인벤토리 바인딩, 클라이언트 카탈로그와 일치하는 인벤토리 범위 build_key, 네이티브 Config/ShopItem2.xml 및 Config/SynthesisSystem.ini가 필요합니다. 현재는 검토된 이 빌드들만 허용됩니다. 다른 빌드는 요청 리더, 결과 처리 경로와 재료 자격을 검토한 뒤 허용 데이터를 변경해야 합니다. kr-812와 id-1809는 전체 요청(2차 비밀번호 문자열, 세트 그룹 플래그)과 40바이트 응답을 사용합니다. 나머지 빌드는 두 항목이 없는 이전 요청과 28바이트 응답을 사용하며, 결과 워드가 영구(3)와 상한(4) 결과도 함께 전달하고 추가 결과 슬롯은 하나뿐입니다. 따라서 이 빌드들은 첨가제 결과를 표시할 수 없으므로 첨가제 옵션을 설정하지 마십시오. 이 빌드들이 보내는 세트 선택에는 그룹 플래그가 없어 서버가 거부합니다. tw-410은 cn-324와 같은 패킷을 사용하지만 설치된 클라이언트에 Config/SynthesisSystem.ini가 없어 허용되지 않습니다. 이 행은 합성과 분해를 처리하며, 기존 item-enhancement 행이 과학실 설정 요청 처리기를 계속 단독 소유합니다. 합성에 성공하면 무작위 기한제 보너스 아이템도 하나 지급됩니다. synthesis_bonus_basis_points(0~10000)는 합성당 확률이고 synthesis_bonus_pool은 item_id, days(정수 일수), weight로 이루어진 항목 목록이며 기본값은 10000과 아이템 100140, 100172(각 1일)입니다. 이 풀은 클라이언트 데이터가 아니라 서버 정책입니다. 클라이언트는 받은 Stock 번호를 해석해 해당 아이템과 기간만 표시합니다. 각 항목은 사용 가능한 기한제 아이템이어야 하고 네이티브 카탈로그에 정확히 그 일수의 Stock 행이 있어야 하며(번호가 가장 낮은 동일 행 사용), 그렇지 않으면 행이 로드되지 않습니다. 분해에서는 보너스가 지급되지 않으며, 첨가제 보상이 이미 응답의 두 번째 슬롯을 채운 경우에도 지급되지 않습니다. 인벤토리 저장소가 거부할 후보(영구 보유, 만료, 착용 중, 중복, 최대 기간 초과)와 레시피가 이미 지급하거나 소모하는 아이템은 건너뛰므로, 유효한 합성이 보너스 때문에 거부되는 일은 없습니다. 확률을 0으로 두거나 풀을 비우면 보너스가 꺼집니다.

합성은 서로 다르고, 조건에 맞으며, 장착하지 않았고 만료되지 않은 기간제 아이템 세 개 또는 완전한 네이티브 세트 세 개를 소모하고 설정에 따라 하나를 남깁니다. 네이티브 세트는 setId와 다를 수 있는 stockSetId와 순서가 정확히 일치하는 setCnt개 구성품을 사용합니다. 세트와 일반 아이템을 혼합한 요청은 거부합니다. 한 세트의 모든 구성품은 같은 수명을 가져야 합니다. 분해는 조건에 맞는 무제한 아이템 하나 또는 완전한 무제한 세트 하나를 소모합니다. 두 작업 모두 설정된 수량형 카드를 차감하고, 선택한 첨가제는 별도의 명시적 수량을 차감합니다. 요청은 메인 메뉴에서만 허용합니다. 누락되거나 변경되었거나 모호하거나 장착되었거나 만료되었거나 지원되지 않는 소유권이 있으면 전체 작업을 커밋하지 않습니다.

다음 profiles/kr-812/local.patch.yaml 예시는 합성 전용 배포 정책입니다. 숫자는 예시이며 복원한 네이티브 경제 규칙이 아닙니다. 설치된 SYNTHESISINFO 값만으로 서버의 레시피 가격이나 확률을 확정할 수 없습니다. 활성화 전에 실제 사용할 정책을 정해야 합니다.

yaml
- set:
    id: science-lab
    config:
      enabled: true
      synthesis_card_item_id: 100622
      card_quantity: 1
      synthesis_survivor: first
      synthesis_maximum_days: 729
      synthesis_permanent_at_days: 730
- set:
    id: dialect.messages
    config:
      legacy_science_lab: true

card_quantity는 설정한 레시피에서 공통으로 차감하는 양의 정수 카드 수량입니다. synthesis_survivor는 first 또는 uniform이어야 합니다. 합성은 소수 부분을 포함한 정확한 남은 일수를 합산하고, 네이티브 무제한 표시 기준인 730일보다 작은 synthesis_maximum_days를 상한으로 적용합니다. 합계가 그보다 높은 synthesis_permanent_at_days에 도달하면 무제한 소유권으로 전환합니다. 무제한 입력도 무제한 결과를 만듭니다. 암묵적인 경제 기본값으로 활성화되는 합성 카드나 분해 레시피는 없습니다.

선택적 decomposition 항목에는 card_item_id(이 네이티브 카탈로그에서는 100623 또는 100656), category(0 액세서리, 1 의상/세트, 2 무기), 비어 있지 않은 rewards 배열이 들어갑니다. 각 보상에는 네이티브 stock_id, 고유 item_id, kind(Count 또는 Days), 양의 정수 amount, maximum, 양의 정수 weight가 필요합니다. Stock 행은 같은 아이템을 가리켜야 하며 duration은 이번에 지급하는 수량 또는 일수와 정확히 같아야 합니다. 클라이언트는 누적 인벤토리 소유량이 아닌 해당 상품 규격을 표시합니다. 판매 중이 아닌 Stock 행도 보상을 나타낼 수 있습니다. 소수 일수의 Stock 보상은 거부하지만 합성 주 결과의 수명은 소수를 계속 유지합니다. 무제한 분해 및 첨가제 보상은 지원하지 않습니다. 네이티브 결과 포맷터는 Stock.duration: -1을 무제한으로 처리하지 않으며, 이 카탈로그에는 무제한 소유권을 표시하는 것으로 검토된 Stock 규격이 없습니다. 합성 주 결과의 무제한 전환은 별도의 지원 경로를 사용합니다. 조건은 네이티브 카탈로그와 일치해야 하며 가중치 합계는 부호 있는 32비트 추출 범위 안에 있어야 합니다. 분해마다 보상 하나를 선택합니다.

permanent_additive_item_id(100624)에는 permanent_additive_quantity와 permanent_additive_basis_points(0..10000)가 필요합니다. 확률이 10000보다 작으면 위 보상 형식의 permanent_failure_reward도 필요합니다. 아직 무제한으로 전환되지 않은 합성에서만 이 첨가제를 허용합니다. bonus_additive_item_id(100655)에는 bonus_additive_quantity와 bonus_reward가 필요합니다. 첨가제 ID와 작업/효과 역할은 네이티브 ASSISTINFO와 대조하며, ID가 0이면 비활성화합니다. 허용되는 레시피 안에서 보상 ID는 충돌할 수 없습니다.

자원 예산은 검증되는 배포 필드입니다. max_workbook_bytes는 네이티브 소스당 기본 134217728바이트, max_catalog_rows는 65536, max_catalog_columns는 256, max_cell_characters는 16384, max_in_flight_accounts는 128, max_decomposition_recipes는 64, max_rewards_per_recipe는 128입니다. 모두 양의 정수이며 배포에 맞게 높일 수 있습니다. 열 제한은 비어 있지 않은 값에 적용됩니다. 네이티브 표 끝의 서식만 있는 빈 셀은 희소 채움 공간을 할당하지 않지만 인덱스는 계속 증가해야 합니다. 인벤토리 용량과 네이티브 선택/프레임 제한은 별도로 적용됩니다.

Memory, SQLite, MySQL은 하나의 소모 및 지급 트랜잭션을 사용하여 무관한 소유권, 남길 아이템의 메타데이터, 일관된 가방 미러와 슬롯 할당 상한을 보존합니다. 일반 Article 및 펫 준비는 새 보상 행이 만들어진 뒤 실행되며 함께 커밋됩니다. 전체 인벤토리를 결과보다 먼저 전송합니다. 소수 수명은 절대 타임스탬프로 저장하고, 합성 주 결과 일수에는 클라이언트와 동일한 전체 인벤토리 세션 기준 시각을 사용합니다. 결과 전송 시 새로 시작하는 카운트다운이 아닙니다. 분해 및 추가 보상 결과에는 설정한 Stock ID를 보내며 수량과 기간은 클라이언트 Stock 테이블에서 읽습니다. 커밋 후 전송 실패는 소유권을 되돌리지 않으며 인벤토리 전송 없이 성공 결과를 알리지 않습니다.

네이티브 선행 문자열은 2차 비밀번호입니다(kr-812 sub_9E29F0, kr-812 sub_4F8A20). 검증된 비밀번호 확인 서비스가 없으므로 비어 있지 않은 비밀번호와 0이 아닌 진단 요청 경로를 거부합니다. 별도 무기 진화는 지원하지 않습니다. gspEvolveResult 경로는 펫에 속하며 독립적인 무기 요청/결과 흐름은 아직 확정되지 않았습니다. 네이티브 게임플레이/UI 검증과 실제 MySQL 과학실 검증은 남아 있으며 자동 프로토콜 및 영속성 검사는 이를 대신하지 않습니다.

캐시 아이템 보관함(cash_inbox) ​

캐시 아이템 보관함은 계정 단위의 대기 캐시 아이템을 일반 가방과 분리해 보관하고, 플레이어가 수령할 때 캐릭터 가방으로 지급합니다(gcpReqCashInven, gcpReqPickup, gcpReqCloseGiftBox, gspCashInvenUpdateAllInventorySlot, gspRepPickup). 검증된 빌드(kr-812, kr-1256, cn-774, tw-454, id-400, id-1809, cn-324, tw-410, cn-406, cn-404, cn-408, cn-705, cn-706, cn-717)에서는 기본 활성화되며, 캐시 보관함 패킷이 확인되지 않은 빌드(kr-186, cn-279, cn-735, cn-738, cn-742)에서는 꺼져 있습니다.

shop에서 cash_inbox: true를 켜려면 grant_purchased_items: true, inventory_only: false, 해당 빌드의 cash_inbox 기능 지원, dialect.messages.config.cash_inbox: true, ICashInboxStore 공급자가 필요합니다. 의도적으로 끄려면 shop과 dialect.messages 모두에서 cash_inbox: false를 설정합니다. 격리된 인벤토리 스코프를 쓰는 프로필은 inventoryview.isolated_services에 ICashInboxService를 포함합니다.

대회 개최 상금방 (user_host) ​

유저 개최 상금방(is_user_host)은 대회 개최권(101164 또는 101859)과 충분한 루찌를 보유한 방장이 상금 PvP 방을 개설하고, 다이얼렉트 심판 슬롯(12)에 자리해 설정 범위 내에서 상금을 조정(gcpUserHostSetting / gspUserHostSetting)하며, 동기화된 5초 시작 카운트다운(gcpUserHostStart / gspUserHostStart)을 시작할 수 있게 합니다. 공용 패치 profiles/bundles/user-host.patch.yaml은 kr-812, cn-717, id-1809, kr-1256, cn-774, tw-454에서 기본 활성화(BFF_USER_HOST_ENABLED, 기본 true)되며, 나머지 빌드는 기본 비활성 상태를 유지합니다.
