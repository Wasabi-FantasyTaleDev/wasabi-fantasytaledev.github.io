배포

이 페이지는 다른 사람을 위해 Bubble Fighter Fantasy를 실행하려는 경우를 다룹니다. 릴리스 빌드, 이 저장소의 Docker Compose 구성, Linux와 Windows 수동 설치, 영속 데이터와 백업, 로그, 네트워크 보안, 안전한 업그레이드와 롤백 방법을 설명합니다.

대상 독자: 노트북에서 한 번 시작하는 것이 아니라 서버 프로세스를 배포하고 유지하는 운영자입니다.

시작하기 전에:

  • 설정을 읽으십시오. 배포는 프로필 선택과 환경 변수로 이루어지며, 이 페이지는 구성 방식 자체를 반복하지 않습니다.
  • 배포하려는 정확한 리비전을 빌드하고 검증하십시오. 릴리스 디렉터리는 경고 0개로 끝난 dotnet build BubbleFighter.Fantasy.sln -c Release에서 만들어집니다.
  • 호스트를 계획하십시오. 지원되는 운영 체제와 아키텍처, 프레임워크 종속 빌드에 필요한 ASP.NET Core Runtime 10(또는 Docker), 전용 서비스 계정, 직접 소유한 데이터베이스가 필요합니다.
  • 서비스할 모든 빌드의 클라이언트 데이터를 준비하십시오. 게임 프로필은 데이터가 없으면 활성화 단계에서 실패합니다.
  • 백업 위치를 정하십시오. 백업은 릴리스 디렉터리 안에 두면 안 됩니다.

배포 전에 ​

이 프로젝트는 프리릴리스입니다. 지원되는 모든 클라이언트에 대해 검증되지 않았으며, 나열된 프로필이나 통과한 자동 점검은 실제 클라이언트 호환성을 입증하지 않습니다. 프리릴리스 서비스로 운영하고, 실제 클라이언트로 테스트하며, 복원 경로를 마련해 두십시오.

이 릴리스의 지원 대상은 Windows x64, Windows ARM64, Linux x64, Linux ARM64입니다. 알려진 배포 환경은 Debian 13이며 다른 Linux 배포판은 테스트되었다고 주장하지 않습니다. 게시 스크립트는 Windows x64와 Linux x64/ARM64를 다루며, Windows ARM64는 나열된 대상으로 동일한 Host 게시 명령에 -r win-arm64를 지정해 게시합니다.

공개 Windows 패키지, Linux 설치 스크립트, 원클릭 Docker 설치은 아직 게시되지 않았습니다. 이 저장소에 있는 것은 소스, tools/의 게시 스크립트 두 개, deploy/docker/의 Docker 파일, Compose 구성입니다. 다른 곳의 설치 프로그램이나 이미지 레지스트리로 대체하지 마십시오.

배포에서는 네 가지 네트워크와 저장소 사항을 계획해야 합니다.

사항계획할 내용이 릴리스의 기본값
게임 포트서비스하는 빌드마다 TCP 리스너 하나입니다.kr-1256은 7100, 레거시 kr-812는 7110을 사용합니다.
릴레이프로필이 릴레이 리스너를 여는 빌드만 해당합니다.kr-1256은 7101을 사용하며, 레거시 빌드는 열지 않습니다.
관리 / WebUIstart로 시작한 서버는 기본적으로 다른 컴퓨터에서 접근할 수 있으며 관리자 계정으로 로그인합니다. BFF_ADMIN_HOST=127.0.0.1이면 로컬에만 둡니다. run --profile 서버는 계정이 없어 루프백에만 있습니다.0.0.0.0:7300(start), 127.0.0.1:7300(run).
MySQL서버만 접근할 수 있게 하고 절대 공개하지 않습니다.127.0.0.1:3306, 데이터베이스 bf_game_db.

클라이언트 데이터는 로컬 저장소에 준비하고 가능하면 읽기 전용으로 마운트하거나 복사하십시오. 서버는 그것을 읽기만 합니다.

선택적 펫 공용 장착 슬롯 ​

equipment 행의 pet_shared_slot 옵션은 기본값이 false입니다. 활성화하면 펫 한 마리만 장착할 수 있으며, 펫은 해당 빌드의 Config/ShopItem2.xml에서 function 값이 10001인 항목으로 판별합니다. 두 번째 펫 장착은 거부되므로 현재 펫을 먼저 해제해야 합니다. 이 규칙은 인벤토리 트랜잭션 안에서 최종 대상도 검사하고, 장비 외관을 읽을 때 과거의 중복 펫 장착 상태를 정규화합니다. 보유 아이템, 수량 및 관련 없는 플래그 비트는 유지됩니다.

all 프로필의 빌드펫 슬롯 활성화
kr-812, kr-1256, cn-406, cn-404, cn-408, cn-706, cn-717, id-400, id-1809, cn-774, tw-454해당 빌드의 클라이언트 데이터와 장비 영속 저장 공급자가 있으면 활성화할 수 있습니다.
cn-279, cn-324활성화 시 거부됩니다. 현재 카탈로그에 펫 항목이 없고 네이티브 펫 선택 경로도 확인되지 않았습니다.

예를 들어 profiles/kr-1256/local.patch.yaml에 다음 내용을 추가하면 해당 빌드에서 활성화됩니다. replace 블록은 행의 전체 설정을 교체하므로 기존 배포의 다른 재정의 값도 유지하십시오. 다른 지원 빌드는 해당 프로필 디렉터리를 사용하고 유효 설정의 protocol, client_profile, version_major 값을 복사하십시오.

yaml
- replace:
    id: equipment
    config:
      protocol: kr-1256/game
      client_profile: kr-1256
      version_major: 1256
      pet_shared_slot: true

persist_worn_state: true와 인벤토리 외관 공급자를 활성화한 상태로 유지하십시오. 클라이언트 데이터 누락, 지원되지 않는 빌드 또는 겹치는 장착 그룹은 명시적인 오류를 발생시킵니다. 이 옵션은 보유 펫 장착과 인벤토리 저장소에서의 복원을 다룹니다. 먹이 주기, 성장, 진화 및 능력 변경은 구현하지 않으며, 이러한 작업에는 펫별 영속 상태와 별도로 검증된 동작이 필요합니다. 이 옵션을 배포하기 전에 대상 네이티브 클라이언트로 장착, 두 번째 펫 거부, 해제 및 재로그인 복원을 검증하십시오.

선택적 펫 성장과 스킬 ​

별도의 펫 번들은 먹이 주기, 성장, 스킬 교체와 회귀, 선택적 경기 보상과 전투 효과를 제공합니다. 모든 스위치는 기본적으로 꺼져 있으며 네이티브 클라이언트 검증이 필요합니다. 소유권은 빌드 간에 공유하지만 성장과 스킬은 빌드별로 저장합니다. 최신 클라이언트의 Article 식별자는 영속 저장소에서 할당합니다. 두 가방은 같은 소유권을 참조하며, 제거 후 다시 지급하면 새 식별자를 받습니다.

kr-812, kr-1256, cn-406, cn-404, cn-408, cn-706, cn-717, id-400, id-1809의 프로필에는 이 패치들이 이미 포함되어 있으며 먹이 주기, 성장, 스킬이 기본으로 켜져 있습니다. 보상, 전투 효과, 마일리지는 계속 꺼져 있습니다. BFF_PETS_ENABLED=false로 설정하면 성장, 스킬, 단일 펫 슬롯이 함께 꺼집니다. 각 프로필은 PET_CLIENT_UTC_OFFSET_MINUTES로 클라이언트 지역의 시간대를 지정합니다(한국 540, 중국과 대만 480, 인도네시아 420). cn-774와 tw-454는 먹이 주기에 필요한 기본 아이템 사용 처리기가 프로필에 아직 설치되지 않아 포함하지 않습니다.

대상 빌드의 일반 패치 뒤에 profiles/bundles/pets.patch.yaml을 포함하십시오. kr-1256, cn-774, tw-454에는 pets-modern.patch.yaml도 필요하며, 한국 또는 대만 빌드는 마지막에 각각 pets-kr-1256.patch.yaml 또는 pets-tw-454.patch.yaml을 추가합니다. 그 밖의 검증된 펫 빌드는 기본 펫 패치를 사용합니다. 이 패치들은 pets.entitlements, pets, pets.combat-effects 행을 설치합니다. BFF_PETS_ENABLED는 equipment.pet_shared_slot도 활성화하여 한 번에 펫 한 마리만 장착하도록 합니다. 성장 패치를 사용자 지정할 때도 이 장비 규칙을 유지하십시오. 펫 행의 빌드 키는 인벤토리 행이 필터링한 카탈로그와 일치해야 합니다.

pets 행에는 같은 프로토콜의 방 정책 서비스가 필요합니다. 펫 장착, 해제, 먹이 주기, 레벨 및 스킬 요청은 저장된 인벤토리와 외형의 전송이 끝날 때까지 수동 및 자동 시작을 보류합니다. 시작된 방의 요청과 같은 세션에서 동시에 들어온 두 번째 펫 요청은 거부합니다. max_in_flight_sessions는 진행 중인 요청 수를, max_held_rooms는 보관 중인 시작 기록 수를 제한합니다. 둘 다 기본값은 128이고 허용 범위는 1–65536입니다. 재개 작업은 처리 중인 기록을 하나 더 보유할 수 있습니다. 한도에 도달하면 새 변경을 거부하거나 시작 기록 한도 오류를 보고하므로 해당 프로토콜의 예상 동시 요청 수에 맞게 설정하십시오. 보류된 시작을 재개하기 전에는 다른 방 정책도 다시 평가합니다.

BFF_PETS_ENABLED를 켜기 전에 두 펫 행에 client_utc_offset_minutes를 명시하십시오. 네이티브 먹이 날짜는 클라이언트의 로컬 시계를 사용합니다. 두 행의 먹이 정책은 다음과 같습니다.

클라이언트 정책필수 설정
자동 성장client_configuration_source: None; 0이 아닌 먹이 대기 시간을 설정하지 않습니다.
KR1256 및 CN774client_configuration_source: DynamicConfig, 명시적인 feed_cooldown_seconds와 양수 mileage.display_maximum. 마일리지 적립을 꺼도 설치된 dialect가 두 값을 검증하고 게시할 수 있어야 합니다.
TW454client_configuration_source: NativePetConfig, native_pet_config_path: Config/PetConfig.xml, 해당 파일의 PetSystem.FeedCoolTime 분 단위 값과 일치하는 명시적 대기 시간. 검증된 파일은 420분, 즉 25200초입니다. 대만 빌드에는 한국/중국 설정 필드를 보내지 않습니다.

skill_resets_enabled는 별도로 켭니다. 네이티브 마일리지 잔액이 있는 빌드는 완전한 mileage 정책을 활성화해야 합니다. 각 초기화 소모품의 적립량을 0까지 포함하여 명시하고 표시 상한을 지정합니다. 선택적 교환에는 임계값, Single 또는 All 모드, Preserve 또는 Discard 잔여량 정책, 제한된 교환 횟수, 종류와 수량이 명확한 보상 묶음도 필요합니다. 원래 서버의 적립량, 임계값이나 보상을 추정하지 않습니다. 검증된 대만 카탈로그에는 마일리지 잔액이 없습니다. 소모품, 성장, 마일리지와 보상은 같은 트랜잭션에서 커밋되며 거부 시 아무것도 소모하지 않습니다.

보상과 전투 효과를 각각 켜고 rewards.mode_ids와 dialect.scene-seeds.pet_combat_mode_ids를 명시하십시오. 보상 중첩과 반올림은 운영 정책입니다. 상쇄 시드는 네이티브 소비 경로가 확인된 빌드에서만 사용할 수 있습니다. 배포 전에 각 대상 클라이언트에서 먹이 주기, 일반/고급 성장, 스킬 변경, 재로그인 복원, 방/파티/광장 외관과 경기 효과를 검증하십시오. MySQL 추가 마이그레이션 파일을 별도로 검토하고 같은 데이터베이스를 공유하는 모든 노드와 적용 시점을 조율하십시오.

MySQL 마이그레이션 0042_inventory_slot_key_watermark.sql은 아이템을 소모한 뒤에도 일반 인벤토리 키의 최댓값을 보존합니다. 펫 마일리지 보상을 켜기 전에 공유 데이터베이스에 아이템을 지급하는 모든 프로세스를 이 최댓값을 사용하는 구매 할당기로 업데이트하십시오. 이전 구매 또는 선물 쓰기 프로그램은 이미 소모한 마일리지 보상의 키를 볼 수 없어 재사용할 수 있습니다. 구매 이력을 읽으면 새 프로그램이 이전 구매를 반영할 수 있지만, 이전 프로그램이 새 최댓값을 따르게 되지는 않습니다. 모든 지급 프로그램의 업데이트가 끝날 때까지 마일리지를 꺼 두십시오. 마일리지가 키를 할당한 뒤에는 롤백하더라도 이 할당 동작을 유지해야 합니다.

릴리스 디렉터리 빌드 ​

tools/의 두 스크립트는 Host와 모든 플러그인을 대상 머신으로 복사할 수 있는 디렉터리에 게시합니다. 둘 다 프레임워크 종속 빌드를 만들므로 .NET 런타임을 포함하지 않으며, 대상에는 일치하는 ASP.NET Core Runtime 10이 필요합니다.

스크립트대상설명
tools/publish-windows-x64.ps1win-x64apphost가 Windows x64이고 포함된 런타임이 없는지 확인합니다.
tools/publish-linux.ps1linux-x64(기본) 또는 linux-arm64apphost가 요청한 아키텍처의 ELF인지 확인합니다.

두 스크립트 모두 PowerShell 세션이 필요하며 필수 -OutputPath를 받습니다. 디렉터리는 없어도 되지만, 있으면 비어 있어야 합니다. 이전 릴리스가 들어 있는 디렉터리에 게시하면 그 릴리스의 런타임 파일이 남습니다. 스크립트는 덮어쓰지 않고 실패합니다.

Windows ​

저장소 루트의 PowerShell 프롬프트에서:

powershell
.\tools\publish-windows-x64.ps1 -OutputPath C:\BFF\release-2026-10-18

성공하면 Windows x64 framework-dependent publish ready: <path>를 출력하고 대상에 x64 ASP.NET Core Runtime 10.0이 필요하다는 점을 알려 줍니다.

Linux ​

어느 머신이든 PowerShell 7 세션에서 게시할 수 있으며 출력은 Linux 바이너리입니다.

powershell
pwsh -File tools/publish-linux.ps1 -OutputPath /srv/bff-release/server

ARM64 대상에는 -Runtime linux-arm64를 추가하십시오. 성공하면 Linux framework-dependent publish ready: <path> (<runtime>)를 출력하고 InGame 플러그인이 게시되었는지 확인합니다. PowerShell은 스크립트 호스트일 뿐이며 대상 머신에는 PowerShell이 필요하지 않습니다.

게시 내용 ​

  • BubbleFighter.Fantasy.Host(apphost)와 BubbleFighter.Fantasy.Host.dll, Host의 종속성 및 runtimeconfig.json.
  • plugins/<ProjectName>/, 플러그인 프로젝트마다 하나의 디렉터리이며 Host 옆의 기본 플러그인 루트입니다.
  • profiles/, 프로필마다 하나의 디렉터리이며 local.patch.yaml은 포함되지 않습니다.
  • packets/, 패킷 표와 builds.yaml.
  • bootstrap/, 로더 프로필과 data/level-experience.csv, data/locales/*.json.

스크립트 대신 dotnet publish src/BubbleFighter.Fantasy.Host -c Release -o <directory>를 사용할 수도 있습니다. 이는 플러그인 게시 대상과 콘텐츠 복사를 포함한 동일한 Host 게시를 수행합니다. 다만 스크립트의 빈 디렉터리 및 apphost 검사를 생략하므로 새 디렉터리를 사용하고 결과를 직접 검증하십시오. Windows ARM64에는 이 형식에 -r win-arm64를 붙이십시오.

복사 전에 결과를 확인하십시오. 디렉터리에는 Host 실행 파일, 플러그인마다 디렉터리가 있는 plugins/, 그리고 profiles/, packets/, bootstrap/, data/ 디렉터리가 있어야 합니다. coreclr.dll, libcoreclr.so 같은 런타임 파일이 있으면 안 됩니다. 발견된다면 게시가 런타임을 포함한 것이므로 의도한 릴리스가 아닙니다.

이 저장소의 Docker Compose ​

deploy/docker/compose.yaml은 이 저장소의 소스로 서버와 MySQL 데이터베이스를 시작합니다. 실행 가능한 컨테이너 구성을 얻는 가장 짧은 경로입니다.

  1. 환경 파일을 복사하고 비어 있지 않은 데이터베이스 암호를 지정하십시오. Compose 파일은 BFF_MYSQL_PASSWORD를 요구하며 없으면 시작을 거부합니다. BFF_SETUP_TOKEN은 선택 사항이며, 설정하면(32자 이상의 무작위 문자) 원격 첫 설치 시 이를 요구합니다.

    sh
    cp .env.example .env

  2. Compose 파일이 찾는 위치에 클라이언트 데이터를 준비하십시오. 선택할 모든 빌드에 대해 저장소 옆에 client-data/<build>/data와 client-data/<build>/dataraw를 두거나 BFF_CLIENT_DATA_HOST로 다른 위치를 지정하십시오. 컨테이너에서는 /app/client-data에 마운트됩니다.

  3. 저장소 루트에서 두 서비스를 빌드하고 시작하십시오.

    sh
    docker compose -f deploy/docker/compose.yaml up --build

시작되는 내용:

  • bff 서비스는 deploy/docker/Dockerfile에서 빌드됩니다. .NET SDK와 ASP.NET 10 이미지를 쓰는 다단계 빌드이며 권한 없는 bff 사용자(uid 1001)로 실행됩니다. 명령 없이 호스트를 실행하므로 최초 설정이 시작됩니다. http://<docker-host>:7300을 열고, 페이지가 요청하면 BFF_SETUP_TOKEN을 입력하고, 관리자 계정을 만든 뒤 MySQL을 선택해 호스트에 mysql, 데이터베이스 이름·사용자·암호는 .env 값을 입력하고, 데이터 폴더 /app/client-data로 클라이언트를 선택하십시오. 이후에는 저장된 설치가 실행되고 관리자는 그 계정으로 로그인합니다. 7100(게임), 7101(릴레이), 7300(관리와 WebUI)을 공개하며, 공개된 관리 포트가 컨테이너에 닿도록 Compose가 BFF_ADMIN_HOST=0.0.0.0을 설정합니다.
  • mysql 서비스는 BFF_DB_IMAGE가 지정한 이미지를 실행하고(.env.example에서 복사한 .env는 MariaDB 11.4, 이 줄이 없으면 MySQL 8.4이므로 기존 mysql-data 볼륨은 그것을 만든 데이터베이스를 계속 사용합니다) BFF_MYSQL_DATABASE, BFF_MYSQL_USER, BFF_MYSQL_PASSWORD로 데이터베이스와 계정을 만들며, 호스트에 ${BFF_MYSQL_PORT:-3306}을 게시하고 데이터를 mysql-data 볼륨에 보관합니다. 서버는 상태 확인이 통과한 뒤 시작하며 컨테이너 네트워크 안에서 BFF_MYSQL_HOST=mysql을 받습니다.
  • 클라이언트 데이터는 /app/client-data에 읽기 전용으로 마운트되고, 저장된 설치는 bff-state 볼륨에, 데이터베이스 상태는 mysql-data 볼륨에 있습니다. 서버 자체 로그는 컨테이너 안에 기록되며 이 Compose 파일은 이를 호스트에 보존하지 않습니다.

동작 확인: Docker 호스트에서 curl http://127.0.0.1:7300/health가 status 필드가 있는 JSON을 반환하고 콘솔에 설정 또는 설치 진행 상황이 표시됩니다. 다음 명령으로 콘솔을 따라가십시오.

sh
docker compose -f deploy/docker/compose.yaml logs -f bff

docker compose -f deploy/docker/compose.yaml down으로 두 서비스를 중지하십시오. 데이터베이스 볼륨은 유지됩니다. down -v는 볼륨도 삭제하므로 데이터베이스를 버리려는 것이 아니라면 -v를 사용하지 마십시오.

이 Compose 파일을 외부에 노출하기 전에 검토하십시오. MySQL을 호스트에 게시하고, Docker 기본 로그 처리(크기 제한 없음)를 그대로 두며, 기본 게임 프로필을 실행합니다. 개발 스타일 구성이며 강화된 운영 템플릿이 아닙니다.

Linux 릴리스 루트에서 외부 데이터베이스와 함께 Docker 사용 ​

deploy/docker/compose.external-db.yaml은 다른 산출물입니다. 이미 데이터베이스가 실행 중인 Linux 호스트의 릴리스 루트를 위한 템플릿입니다. 대상 머신에서 다음 배치를 만드십시오.

text
<release-root>/
  compose.yaml     deploy/docker/compose.external-db.yaml 복사본
  Dockerfile       deploy/docker/Dockerfile.published 복사본
  .env             BFF_RELEASE를 포함한 배포 변수
  server/          프레임워크 종속 Linux 게시 출력
  logs/            컨테이너가 기록
  client-data/     선택 사항. 또는 BFF_CLIENT_DATA_HOST로 다른 위치 지정

  1. tools/publish-linux.ps1로 릴리스 출력을 server/에 게시하십시오. 게시 디렉터리는 비어 있어야 하므로 다른 내용을 복사하기 전에 server/에 게시하십시오.

  2. deploy/docker/compose.external-db.yaml을 <release-root>/compose.yaml로, deploy/docker/Dockerfile.published를 <release-root>/Dockerfile로 복사하십시오.

  3. <release-root>/.env를 만드십시오. BFF_RELEASE(이미지 태그)와 로컬 데이터베이스의 MySQL 값을 설정해야 합니다. 주소와 토큰을 검토하십시오. BFF_BIND_HOST, BFF_MYSQL_HOST, 관리 주소는 템플릿이 강제로 설정합니다.

  4. <release-root>에서 시작하십시오.

    sh
    docker compose up -d --build

이 템플릿이 제공하는 것: server/에서 빌드한 bf-fantasy:<release> 이미지, 호스트 네트워킹(따라서 .env에 구성된 게임, 릴레이, 관리 포트가 그대로 사용되고 127.0.0.1의 데이터베이스에 접근 가능), 작은 쓰기 가능 /tmp가 있는 읽기 전용 컨테이너 파일 시스템, 모든 capability 제거, no-new-privileges, 30초 중지 유예 기간, 중지하지 않는 한 재시작, 패킷 로그 파일을 위한 ./logs를 /app/logs에 마운트, 클라이언트 데이터를 /app/client-data에 읽기 전용 마운트, 10 MB 파일 5개로 제한된 json-file 로깅.

이 Dockerfile 변형은 이미지를 run --profile all로 시작하므로 릴리스는 기동된 모든 빌드를 각자의 포트로 서비스하며 해당 빌드들의 클라이언트 데이터가 필요합니다. 하나의 빌드만 서비스하려면 운영자가 관리하는 Dockerfile 복사본에서 CMD를 바꾸십시오.

docker compose down은 서비스를 중지하고 logs/ 디렉터리를 유지합니다. 데이터베이스는 이 템플릿이 관리하지 않으므로 자체 도구로 백업하고 업그레이드하십시오. deploy/docker/Dockerfile.published는 이 배치가 빌드에 사용하는 저장소 파일이며, 어떤 이미지도 레지스트리에 게시되지 않으므로 이미지는 항상 대상 머신에서 빌드됩니다.

Linux 수동 배포 ​

컨테이너를 원하지 않을 때 사용하는 경로입니다. Linux 게시 출력을 대상으로 복사하고 Host를 직접 실행하십시오.

  1. tools/publish-linux.ps1로 게시하고 출력을 <release-root>로 복사하십시오. 게시의 디렉터리 배치는 그대로 유지하십시오.

  2. 전용 서비스 계정(예: bff)을 만들고 릴리스 디렉터리를 소유하게 하되 대화형 로그인은 허용하지 마십시오. Host는 profiles/, packets/, bootstrap/, plugins/, data/만 읽으면 되고, logs/를 쓸 수 있는 작업 디렉터리와 SQLite를 사용할 경우 저장 파일을 둘 쓰기 가능한 위치가 필요합니다.

  3. 복사 과정에서 실행 권한이 사라졌다면 apphost를 실행 가능하게 만드십시오: chmod +x BubbleFighter.Fantasy.Host.

  4. 프로세스 환경에 배포 변수를 제공하십시오. 릴리스 디렉터리에는 저장소 표식이 없으므로 그 옆에 둔 .env는 Host가 읽지 않습니다. .env 로드 규칙은 체크아웃 안에서만 적용됩니다. 서비스 관리자나 셸이 읽는 환경 파일을 사용하십시오. 예:

    sh
    set -a
. <release-root>/deployment.env
set +a

    이 파일에는 .env.example과 같은 KEY=VALUE 항목이 들어가며 실제 MySQL 암호, 공개 주소, 관리 토큰을 채웁니다.

  5. 릴리스 루트로 이동해 Host를 포그라운드로 시작하십시오.

    sh
    cd <release-root>
./BubbleFighter.Fantasy.Host run --profile kr-1256

    작업 디렉터리가 중요합니다. profiles, packets, client-data, logs가 이를 기준으로 확인됩니다. Ctrl+C 또는 SIGTERM은 정상 종료를 요청하며 콘솔은 Shutdown complete.로 끝납니다.

  6. 저장소는 서비스 유닛을 제공하지 않습니다. 장기 운영 시에는 직접 관리하는 서비스 관리자(예: systemd 서비스) 아래에서 Host를 실행하고, 작업 디렉터리를 <release-root>로 설정하며 환경 파일로 변수를 제공하십시오. 서비스 계정은 비특권으로 유지하고 릴리스, 로그 디렉터리, 사용하는 경우 SQLite 파일에만 접근 권한을 주십시오.

호스트에서 curl http://127.0.0.1:7300/health로 확인하고 아래의 리스닝 포트 점검을 사용하십시오. 서비스 관리자의 SIGTERM 또는 포그라운드의 Ctrl+C로 중지하십시오.

Windows 수동 배포 ​

  1. tools/publish-windows-x64.ps1로 게시하고 출력을 배포 디렉터리로 복사하십시오.

  2. 시작 전에 프로세스에 배포 변수를 설정하십시오. 예를 들어 프로세스를 소유할 PowerShell 세션에서:

    powershell
    $env:BFF_MYSQL_HOST = '127.0.0.1'
$env:BFF_MYSQL_PASSWORD = '<your-database-password>'
$env:BFF_PUBLIC_HOST = '<public-address-clients-use>'

    Linux와 마찬가지로 릴리스 디렉터리에 복사한 .env는 읽히지 않습니다. Host는 저장소 루트를 찾을 수 있을 때만 저장소 .env를 로드합니다.

  3. 상대 경로 profiles, packets, client-data, logs가 그곳에서 확인되도록 릴리스 디렉터리에서 Host를 시작하십시오.

    powershell
    Set-Location C:\BFF\<release>
.\BubbleFighter.Fantasy.Host.exe run --profile kr-1256

  4. 방화벽에서 계획한 게임, 릴레이, 관리 포트만 허용하십시오. 관리 포트는 신뢰할 수 있는 네트워크에서만 접근 가능하게 하고 MySQL은 공용 인터페이스에서 멀리 두십시오.

  5. 이 저장소에는 Windows 서비스 래퍼가 없습니다. 머신과 함께 시작해야 한다면 직접 관리하는 서비스 관리자 아래에서 실행 파일을 실행하고 서비스 계정은 비특권으로 유지하십시오.

Invoke-RestMethod http://127.0.0.1:7300/health로 확인하십시오. status 필드가 있는 JSON을 반환합니다. Ctrl+C로 중지하며, 플랫폼이 신호를 제공하는 경우 Host는 SIGTERM과 SIGINT도 처리합니다.

영속 데이터와 백업 ​

데이터위치업그레이드 전 백업
게임 및 계정 데이터MySQL 데이터베이스 bf_game_db, 또는 SQLite 저장 파일 하나.예; 모든 업그레이드마다.
클라이언트 데이터client-data/<build>/ 아래의 읽기 전용 파일.한 번, 또는 클라이언트 복사본을 바꿀 때.
구성과 비밀 정보Compose .env 또는 서비스 관리자의 환경 파일.예; 안전하게 보관.
컴파일된 클라이언트 데이터작업 디렉터리의 state/compiled-data/<build>.bffdata, 또는 BFF_COMPILED_DATA.아니요; 서버가 다시 만드는 캐시입니다.
로그와 패킷 로그작업 디렉터리의 logs/<date>/, 또는 컨테이너 경로.선택; 정책에 따라 회전 및 보존.
이전 릴리스별도 디렉터리.롤백 기간이 끝날 때까지 보관.

데이터베이스, 그 백업, SQLite 저장 파일은 릴리스 디렉터리 밖에 두십시오. 릴리스는 교체되기 때문입니다. MySQL은 서버가 중지되었거나 쓰기가 없을 때 데이터베이스 자체 백업 도구(예: 논리 덤프 mysqldump 또는 일관된 스토리지 스냅샷)를 사용하십시오. SQLite는 먼저 서버를 중지한 뒤 단일 저장 파일을 복사하십시오. 서버가 쓰는 중인 SQLite 파일을 복사하지 마십시오.

백업에 의존하기 전에 별도 인스턴스에서 복원을 테스트하십시오. 데이터베이스를 복원하거나 저장 파일을 복사하고, 그것으로 릴리스를 시작해 /health, 플러그인 행 상태, 클라이언트 흐름을 확인하십시오. 한 번도 복원해 보지 않은 백업은 검증된 백업이 아닙니다.

클라이언트 데이터는 상태가 아니라 입력입니다. 서버는 읽기만 하고 Docker 구성은 읽기 전용으로 마운트하므로 릴리스를 교체해도 바뀌지 않습니다.

메모리 ​

Host의 메모리 설정은 BubbleFighter.Fantasy.Host.runtimeconfig.json에 담겨 함께 배포됩니다. 워크스테이션 수집기, 동시 수집, 그리고 수집기가 더 적극적으로 압축하도록 9로 설정한 System.GC.ConserveMemory입니다. 모든 행이 활성화되면 Host는 힙을 한 번 압축하고 Startup allocated N MB in C collection(s); the managed heap was compacted from A MB to B MB committed를 기록합니다. B는 로드된 프로필이 실제로 유지하는 메모리에 가깝습니다. 프로세스는 런타임 자체의 코드와 매핑된 프로그램 파일만큼 B보다 큽니다.

시작에는 실행 중보다 훨씬 많은 메모리가 필요합니다. 저희 측정에서는 클라이언트 빌드 하나가 클라이언트 데이터를 파싱하는 동안 약 140 MB까지 올라갔다가 전용 메모리 약 40 MB로 안정되었고, 전체 빌드를 함께 시작하면 약 300 MB까지 올라갔습니다(작은 서버 참고). 메모리가 작은 머신에는 최고점보다 낮은 제한을 두지 말고 시작 단계를 위한 스왑을 마련하십시오.

환경 변수는 이 파일보다 우선합니다. 두 가지를 유의하십시오.

  • 런타임은 숫자형 DOTNET_GC* 변수를 16진수로 읽습니다. DOTNET_GCHeapHardLimit=20000000은 20 MB가 아니라 512 MB입니다. 진법이 드러나도록 0x20000000으로 쓰십시오.
  • 시작 도중 힙 제한에 도달하면 서버는 OutOfMemoryException으로 멈춥니다. 시작 최고점에는 모든 빌드의 클라이언트 데이터 파싱이 포함되므로, 유휴 서버에 맞는 제한이라도 시작은 멈출 수 있습니다. 메모리 제한이 있는 컨테이너에서는 런타임이 스스로 그 제한의 75%를 힙 제한으로 적용합니다. 사용하는 프로필이 해당 제한 안에서 시작되는지 직접 측정하지 않았다면 힙 제한을 설정하지 마십시오.

python tools/perf/measure.py --profile <id>로 자신의 머신에서 시작을 측정할 수 있습니다. 각 수치의 의미는 tools/perf/README.md에 있습니다.

연결은 수락된 순간부터 소켓, 세션, 읽기 버퍼를 하나씩 차지합니다. 지원되는 모든 클라이언트는 인사를 받자마자 첫 프레임을 보내므로, first_frame_seconds(각 protocol 행의 설정 키, 기본값 30) 안에 완전한 프레임을 보내지 않은 연결은 닫힙니다. 어떤 클라이언트가 더 오래 기다린다는 것이 측정된 경우에만 늘리십시오.

버전 핸드셰이크 이후 요청 처리에 실패하면 서버는 오류를 기록하고 그 요청 하나만 버린 채 플레이어 연결을 유지합니다(keep_connection_on_handler_failure, 기본값 true). 형식이 잘못된 패킷이나 핸드셰이크 이전의 실패는 여전히 연결을 닫으며, false로 설정하면 모든 실패에서 연결을 닫습니다.

읽기를 멈춘 클라이언트가 있으면 서버는 그 클라이언트에게 보낼 데이터를 대기열에 쌓습니다. 각 세션은 send_queue_bytes(4 MB)에 도달하면 닫히며, total_send_queue_bytes(각 protocol 행의 설정 키, 기본값 64 MB)는 그 행의 모든 세션이 함께 쌓을 수 있는 양을 제한하므로 여러 클라이언트가 동시에 멈춰도 누적되지 않습니다. 어떤 프레임이 이 한도를 넘게 되면 대기 바이트가 가장 많은 세션이 닫히고 그 프레임은 그대로 전송되며, 어떤 송신자도 기다리지 않습니다. 메모리가 작은 머신에서는 머신이 감당할 수 있는 값으로 낮추십시오. 세션은 종료될 때 대기열에 쌓았던 최댓값을 Debug 수준으로 기록합니다.

작은 서버 ​

서버에 필요한 자원은 서비스하는 클라이언트 빌드, 사용하는 데이터베이스, 함께 시작하는 구성 요소에 따라 정해집니다. 아래 수치는 메모리 영속성을 사용하는 릴리스 빌드에서 tools/perf/measure.py로 측정했습니다. 이를 참고해 구성을 고른 뒤 같은 방법으로 자신의 프로필을 측정하십시오.

느린 VPS 코어에서는 시작 CPU가 두 배에서 네 배까지 듭니다. 최고점은 클라이언트 데이터를 파싱하는 동안에만 유지되며 이후 서버가 그 메모리를 반환합니다.

컴파일된 클라이언트 데이터. 빌드를 처음 시작할 때 서버는 클라이언트 워크북을 파싱하고 그 결과를 작업 디렉터리의 state/compiled-data/<build>.bffdata에 보관합니다(폴더를 옮기려면 BFF_COMPILED_DATA를 설정하십시오). 이후 시작은 이 파일을 읽으므로 CPU가 훨씬 적게 듭니다. 이 파일은 캐시입니다. 클라이언트 데이터와 서버 릴리스가 파일을 쓴 때와 같을 때만 사용되고, 그렇지 않으면 다시 만들어지며, 파일이 없어도 서버는 똑같이 동작합니다. 따라서 언제든 삭제할 수 있고 백업할 필요가 없습니다. 업그레이드 후 첫 시작은 다시 첫 시작이 됩니다. bff data compile <profile>은 이 첫 시작을 수행하고 멈추므로, 플레이어를 받기 전에 미리 끝내 둘 수 있습니다. 컨테이너에서는 이 폴더를 볼륨으로 마운트하십시오. 그렇지 않으면 새 컨테이너마다 처음부터 다시 시작합니다.

512 MB. SQLite로 빌드 한두 개를 서비스하고(persistence.sqlite 행을 켜는 패치, SQLite 참고) MySQL은 사용하지 마십시오. 데이터베이스 서버 하나만으로도 이런 머신 메모리의 대부분을 차지합니다. 시작 최고점이 메모리 부족 종료를 일으키지 않도록 1 GB 스왑이나 zram을 추가하십시오. BFF_PACKET_LOG는 꺼 두십시오.

1 GB. SQLite로 여러 빌드를 서비스하거나, 아래처럼 설정한 MariaDB로 빌드 한두 개를 서비스하십시오. 512 MB 스왑을 유지하십시오.

2 GB 이상. MariaDB 또는 MySQL로 모든 빌드(profiles/all)를 서비스하십시오.

작은 서버용 패치. profiles/bundles/small-vps.patch.yaml은 플레이어만 서비스하는 서버에 필요 없는 관리 웹 페이지와 클라이언트 및 플러그인 배포 행을 끕니다. 관리 API는 켜진 채로 남습니다. 프로필 자체 패치 다음에 run 또는 start에 --patch profiles/bundles/small-vps.patch.yaml을 추가하십시오. 각 빌드의 리스너는 기본적으로 연결 512개를 받습니다(리스너 행의 max_connections). 머신이 그만큼의 플레이어를 감당할 수 없으면 자신의 패치에서 낮추십시오.

잠자는 빌드. 한 프로세스에서 여러 빌드를 서비스하는 서버(profiles/all, 또는 builds를 나열한 자신의 서버 프로필)는 플레이어가 필요로 할 때까지 빌드를 로드하지 않은 채로 둘 수 있습니다. BFF_BUILD_ACTIVATION=on_demand를 설정하십시오. 자신의 서버 프로필에서는 build_activation: on_demand라고 씁니다. 각 빌드의 리스너와 와이어 방언은 서버와 함께 시작되므로 모든 포트가 처음부터 연결을 받습니다. 빌드의 나머지는 첫 클라이언트가 연결할 때 로드되고, 연결도 방도 없는 상태가 BFF_BUILD_IDLE_MINUTES(기본값 30)분 이어지면 언로드됩니다. 우리 측정에서 all은 CPU 약 16초와 95 MB 대신 약 2초 만에 프라이빗 메모리 30 MB로 준비되었고, 빌드 두 개를 로드했을 때 최고치는 300 MB 대신 약 155 MB였으며, 둘 다 다시 잠든 뒤에는 32 MB로 돌아왔습니다. 그 대가는 잠자는 빌드의 첫 플레이어가 치릅니다. 빌드가 로드되는 동안 연결이 기다리며, 테스트 머신에서 서버 시작 후 첫 빌드는 약 11초, 그 뒤의 빌드는 약 2초였고 느린 코어에서는 더 걸립니다. wake_timeout_seconds(30, core.activation-groups 행)보다 오래 기다리게 될 연결은 닫히며, 빌드가 올라온 뒤 클라이언트가 다시 연결할 수 있습니다. 한 빌드의 로드나 언로드는 다른 빌드의 플레이어, 관리 API, 런처 채널을 방해하지 않습니다. 항상 실행되어야 하는 행은 패치에서 activation: always라고 지정할 수 있습니다. 이 수치는 단일 노드에서 측정한 것입니다. 클러스터 행을 마운트한 프로필은 잠자는 빌드와 함께 검토되지 않았으므로 그런 프로필에서는 always로 두십시오.

빌드 제외. profiles/all의 일부 빌드를 아예 서비스하지 않을 서버는 그 빌드들을 쉼표로 구분해 BFF_EXCLUDE_BUILDS에 지정합니다. 예: BFF_EXCLUDE_BUILDS=tw-410. 자신의 서버 프로필에서는 exclude_builds: [tw-410]라고 씁니다. 제외된 빌드는 행을 하나도 구성하지 않으므로 포트가 열리지 않고 메모리도 쓰지 않습니다. 제외하는 이름은 모두 프로필의 빌드여야 하고, 모든 빌드를 제외할 수는 없습니다. 어느 실수든 빌드가 모르는 사이에 계속 실행되는 대신 서버가 시작 시점에 멈춥니다.

선택 빌드. profiles/all의 일부 빌드는 아직 공개되지 않은 kr-186처럼 대부분의 운영자가 갖고 있지 않은 클라이언트입니다. 이런 빌드는 optional_builds에 나열되며 BFF_INCLUDE_BUILDS에 이름을 적었을 때만 시작합니다. 예: BFF_INCLUDE_BUILDS=kr-186. 따라서 해당 클라이언트 데이터가 없는 서버도 그 빌드 없이 정상적으로 시작합니다. WebUI도 이 빌드를 설치 목록에 보여 주지 않습니다. 적는 이름은 모두 선택 빌드여야 합니다.

로그 ​

BFF_LOG_FILE 또는 --log-file을 설정하면 콘솔 출력과 함께 Host ILogger 기록을 파일에 보관합니다. 경로를 설정하지 않으면 파일 로깅은 꺼집니다. 파일 기준 수준은 기본 Warning이며 BFF_LOG_FILE_LEVEL 또는 --log-file-level로 지정합니다. BFF_LOG_LEVEL과 독립적이며 로깅 팩터리의 범주 및 공급자 필터 규칙도 적용됩니다. 허용된 기록에는 UTC 타임스탬프, 수준, 범주, 이벤트 ID 및 내부 예외와 스택을 포함한 전체 예외 텍스트가 들어갑니다.

기존 영구 볼륨 안에서 쓰기 가능한 경로를 선택하세요. deploy/docker/compose.yaml의 /app/state/logs/host.log는 bff-state:/app/state 마운트 안에 있습니다. 변수도 컨테이너 환경에 추가해야 합니다. 네이티브 서비스는 자체 영구 데이터 디렉터리를 사용하세요. 작성기는 상위 디렉터리를 만들고 실행 중 host.log.lock을 독점합니다. 다른 프로세스는 같은 로그에 동시에 쓸 수 없습니다. 잘못된 경로, 권한 문제 또는 잠긴 대상은 시작 오류입니다.

파일은 host.log, host.1.log 등의 고정 슬롯으로 순환합니다. 기본값은 현재 파일을 포함해 파일 다섯 개를 보관하고 새 쓰기를 파일당 16 MiB로 제한합니다. 재시작하거나 보관 수를 줄여도 개수 제한은 적용됩니다. 시작 시 기존 현재 파일이 상한을 넘으면 첫 번째 백업으로 순환합니다. 이전 백업은 정상 보관 순환으로 교체될 때까지 새로 줄인 크기 상한을 넘을 수 있습니다. 보관 슬롯이 하나이면 현재 파일을 교체합니다. 작성 작업 하나에 기록 슬롯 수와 UTF-8 바이트 예산이 모두 적용됩니다. 호출자는 디스크를 기다리지 않습니다. 큐 포화, 바이트 예산 소진, 과대 기록 또는 형식화 실패 시 최신 기록 전체를 버리고 dropped_entries=N 집계 줄을 남깁니다. 예외를 상한에 맞춰 자르지 않습니다. 쓰기, 플러시 또는 순환 I/O 오류 시 작성기는 예외 유형을 포함한 짧고 제한된 stderr 줄 하나를 출력하고 스트림을 닫으며 사용 불가 기간의 기록을 손실로 집계합니다. 지수 백오프로 파일 열기를 재시도하며 기본 지연은 1초에서 최대 60초입니다. 복구 후에는 새 기록보다 먼저 대기 중 손실 보고를 씁니다. 실패한 순환은 마지막으로 완료한 파일 이동 다음부터 이어집니다. Warning 이상 기록과 손실 보고는 다음 쓰기 전에 운영 체제로 플러시합니다. 종료 시에는 제한된 시간 동안 큐를 처리하며 완료하지 못하면 실패를 보고합니다. I/O 오류는 일부 기록만 남길 수 있으며 정전 후 복구도 보장하지 않습니다. 모든 제한은 구성을 참고하세요. 전체 예외에는 계정 또는 연결 데이터가 포함될 수 있으므로 접근을 제한하고 일반 보관 정책을 적용하세요.

서버는 콘솔에 로그를 기록합니다. 각 줄은 한 줄이며 UTC 타임스탬프를 가집니다. 수준은 BFF_LOG_LEVEL 또는 --log-level에서 오고 기본값은 Information입니다. 정상 시작은 활성화된 각 행, 각 리스너의 수신 주소, 준비 후 Server started with <n> active row(s).를 보고합니다. 정상 종료는 Shutdown complete.로 끝납니다.

진단 행은 패킷 로그 파일도 기록할 수 있습니다. 켜면 패킷마다 한 줄을 만들고 파일에 써야 하므로 기본적으로 꺼져 있으며, 디버깅할 때 BFF_PACKET_LOG=true를 설정하면 켜집니다. 연결 이벤트는 어느 경우든 콘솔에 기록됩니다. 이 파일은 콘솔과 별개이며 패킷과 연결 이벤트마다 한 줄입니다.

  • 기본 경로는 작업 디렉터리 기준 logs/{date}/packets_{timestamp}.log입니다. 프로필이 이름을 덮어씁니다. kr-812는 packets-kr-812_{timestamp}.log, all 프로필은 packets-all_{timestamp}.log를 씁니다.
  • 각 파일은 10 MiB에서 .1로 회전하며 {date}가 바뀌면 새 파일을 시작합니다. 기본적으로 설정된 파일 이름 패턴당 최대 100개 파일을 유지하고, 싱크가 시작할 때 더 오래된 파일을 삭제합니다. 파일 이름 시간대는 기본값이 China Standard Time입니다.
  • 쓰기는 경계가 정해진 큐(기본 32768개 레코드)를 거치며 종료 시 최대 10초 동안 플러시합니다. 오버플로는 packet-log-overflow로 보고되며 게임플레이 패킷을 절대 버리지 않습니다.
  • 전체 패킷 기록기는 기본적으로 꺼져 있습니다. BFF_PACKET_CAPTURE=true를 설정하면 활성화되며 같은 logs/ 트리 아래에 별도 JSONL 패킷 파일을 씁니다.

패킷 로그 줄과 캡처에는 플레이어와 연결 데이터가 포함될 수 있습니다. logs 디렉터리를 민감 정보로 취급하고 평소의 보존 정책을 적용하십시오. Docker 구성에서 릴리스 루트 템플릿은 ./logs를 마운트해 패킷 파일을 호스트에 보존하며, 콘솔 출력은 컨테이너의 json-file 로그로 가서 10 MB 파일 5개로 제한됩니다.

관리 및 네트워크 보안 ​

  • start로 시작한 서버(실행 파일을 인수 없이 실행하면 이렇게 됩니다)는 관리 리스너를 기본적으로 0.0.0.0:7300에 바인딩하고 관리자가 계정과 비밀번호로 로그인합니다. 브라우저가 로그인 페이지를 불러올 수 있도록 /health와 WebUI 파일은 열려 있습니다. 첫 관리자가 생기기 전에는 포트에 닿는 누구나 설치를 마칠 수 있으므로 첫 시작 직후 바로 마치거나 BFF_SETUP_TOKEN을 설정하십시오. 접근 가능한 주소에서는 BFF_ADMIN_ALLOWED_HOSTS가 이름을 나열하지 않는 한 모든 호스트 이름을 받습니다. run --profile로 시작한 서버는 계정이 없어 로그인이 필요 없으며 루프백에서만 대기합니다.
  • 관리 포트를 루프백 밖으로 노출하기 전에 원본 네트워크를 제한하십시오. 제한할 수 없다면 루프백에 두고 직접 관리하는 터널이나 리버스 프록시를 사용하십시오.
  • 방화벽에서는 선택한 프로필이 서비스하는 게임 및 릴레이 포트만 여십시오. 관리 포트나 MySQL을 공용 인터페이스에 게시하지 마십시오.
  • 전용 데이터베이스 계정을 사용하고 MySQL 포트를 루프백이나 사설 네트워크에 두며, 데이터베이스 관리자 계정을 서버에 재사용하지 마십시오.
  • 비밀 정보는 배포 로컬 .env(Compose) 또는 서비스 관리자 환경 파일(수동)에 보관하십시오. 권한을 제한하고 절대 커밋하지 마십시오. --dump-config는 보간된 비밀 정보를 보여 주므로 그 출력을 공개 보고서에 첨부하지 마십시오.
  • 클라이언트 데이터, 패킷 로그, 캡처를 공개하지 마십시오. 전용 클라이언트 파일과 플레이어 데이터가 포함될 수 있습니다.

업그레이드와 롤백 ​

업그레이드는 나란히 설치하는 방식입니다. 새 릴리스를 새 디렉터리에 설치하고 이전 릴리스를 유지한 뒤, 한 프로세스를 중지하고 다른 프로세스를 시작해 전환합니다.

  1. 유지 관리 시간을 공지하고 새 작업 수락을 중단하십시오. 경기를 끝내거나 의도적으로 종료한 뒤 SIGTERM 또는 Ctrl+C로 서버를 정상 중지하고 Shutdown complete.를 기다리십시오.
  2. 위에서 설명한 대로 데이터베이스를 백업하고 실행 중인 정확한 릴리스 디렉터리와 구성을 기록하십시오.
  3. 새 릴리스를 새 빈 디렉터리에 게시하십시오. 이전 릴리스 위에 게시하지 마십시오.
  4. 배포 변수와 클라이언트 데이터를 복사하거나 재사용하십시오. 클라이언트를 업데이트하지 않는 한 클라이언트 데이터는 릴리스 간에 바뀌지 않습니다.
  5. 새 디렉터리에서 새 릴리스를 시작하고 검증하십시오. /health, 플러그인 행 상태, 리스닝 포트, 저장소 연결 줄, 콘솔 오류 없음.
  6. 롤백이 더 이상 필요하지 않을 때까지 이전 릴리스 디렉터리와 업그레이드 전 백업을 보관하십시오.

롤백하려면 새 릴리스를 중지하고 이전 릴리스 디렉터리를 같은 구성으로 시작하며, 새 릴리스가 스키마를 바꿨다면 업그레이드 전 데이터베이스 백업을 복원하십시오. 바이너리만 롤백하는 것은 보장되지 않습니다. MySQL 마이그레이션은 영속성 행이 활성화될 때 자동으로 적용되며 순방향 전용입니다. 서버에는 다운그레이드 경로가 없으므로 이전 바이너리는 새 릴리스가 이미 마이그레이션한 데이터베이스에서 실행되지 못할 수 있습니다. 안전한 롤백 조합은 이전 릴리스와 업그레이드 전에 받은 백업입니다.

배포 후 점검 ​

  • [ ] GET /health가 status가 ok인 JSON을 반환합니다.
  • [ ] WebUI 플러그인 목록(또는 로그인한 세션의 GET /api/plugins)에 예상한 모든 행이 실패 상태 없이 표시됩니다.
  • [ ] 호스트의 리스닝 포트가 계획과 일치합니다. Linux는 ss -ltn, PowerShell은 Get-NetTCPConnection -State Listen으로 확인합니다.
  • [ ] 콘솔에 저장소 연결 줄이 표시됩니다(MySQL 연결됨 또는 SQLite 활성).
  • [ ] 서비스하는 모든 게임 빌드의 clientdata 행이 실패가 아니라 활성 상태입니다.
  • [ ] 로그 수준이 운영에 적절하고, 패킷 로그가 예상된다면 패킷 로그 디렉터리가 쓰기 가능하며 증가합니다.
  • [ ] 백업을 받았고 테스트 인스턴스에서 최소 한 번 복원했습니다.
  • [ ] 소유자가 실제 클라이언트로 테스트했습니다. 자동 점검과 나열된 프로필은 클라이언트 수용이 아닙니다.

문제가 생기면 ​

  • 컨테이너가 즉시 종료됩니다. 기본 프로필이 게임 프로필이고 클라이언트 데이터가 없습니다. client-data/<build>/data 또는 dataraw를 추가하거나 클라이언트 데이터가 필요 없는 프로필을 실행하십시오.
  • 서버가 MySQL에 연결하지 못합니다. 주소, 포트, 계정, 데이터베이스 이름을 확인하십시오. 릴리스 디렉터리는 로컬 .env를 읽지 않으므로 프로세스 환경의 변수를 확인하십시오.
  • /api가 401을 반환합니다. 요청에 로그인한 관리자 세션이 없습니다. 먼저 WebUI에서 로그인하십시오.
  • 포트가 이미 사용 중입니다. 충돌 프로세스를 중지하거나 빌드별 포트 변수를 바꾼 뒤 다시 시작하십시오.

순서대로 확인하는 목록은 문제 해결을 참고하십시오.

설치 자격 증명 ​

state/administration/installation.json에는 서버가 재시작 후 다시 연결할 수 있도록 MySQL 비밀번호가 평문으로 저장됩니다. 상태 디렉터리는 소유자만 접근하도록 제한하십시오. Windows에서는 파일 보안 속성으로 서비스 계정만 허용하고, Linux에서는 서비스 사용자로 chown한 뒤 chmod 700 state/administration 및 chmod 600 state/administration/installation.json을 실행합니다. 원격 MySQL에서 SslMode=None을 사용하면 서버가 경고하므로 로컬이 아닌 데이터베이스에는 TLS를 활성화하십시오.
