런처

Bubble Fighter Fantasy의 동반 데스크톱 애플리케이션 Fantasy Tale Launcher는 게임 클라이언트를 설치하고 실행하며 플레이어가 선택한 서버에 연결하는 것을 목표로 개발 중입니다. 이 애플리케이션은 별도 프로젝트인 FantasyTale.Launcher이며 MIT 라이선스로 배포됩니다. 이 서버 저장소에는 포함되어 있지 않고, 어느 프로젝트도 게임 클라이언트나 그 데이터를 배포하지 않습니다.

이 페이지는 현재 개발 체크포인트의 런처와, 운영자가 이미 활성화할 수 있는 서버 측 런처 API를 설명합니다. 런처는 초기 개발 단계에 있습니다. 플레이어 대상 흐름 대부분은 아직 동작하는 화면이 아니라 정의와 계약으로만 존재합니다. 아래의 모든 절은 무엇이 구현되었고 무엇이 계획인지 밝히므로, 플레이어와 운영자 모두 이 커밋에 존재하지 않는 동작에 의존하지 않게 됩니다.

현재 개발 상태 ​

영역현재 체크포인트의 상태
창, 게임 카탈로그, 설정 셸구현됨: 호스트가 games 폴더에서 게임 및 클라이언트 빌드 정의를 읽어 인터페이스로 보냅니다. 셸은 게임, 인스턴스, 서버, 다운로드, 플러그인, 계정, 설정 페이지를 렌더링하며 모양과 언어 환경 설정을 로컬에 저장합니다.
Bubble Fighter 빌드 정의데이터로 구현됨: 클라이언트 빌드 9개가 각각 별도 빌드 파일로 정의되어 있습니다.
세션 파일(session.toml)작성기는 라이브러리 도우미로 구현되어 있지만, 아직 프로덕션 실행 흐름이 이를 호출하지 않습니다.
네이티브 훅 런타임과 메신저 호스트구현되었고 네이티브 테스트로 검증되지만, 실제 게임 클라이언트에서는 아직 검증되지 않았습니다.
내장 훅 플러그인 3개데이터 플러그인으로 정의되었고 같은 네이티브 테스트로 검증되지만, 역시 실제 게임 클라이언트에서는 검증되지 않았습니다.
백엔드 다운로드, 소스, 플러그인 관리자, 인스턴스구현되지 않음: 다운로드 엔진, 매니페스트 적용, 플러그인 관리자, 인스턴스 모델은 아직 로드맵에 남은 작업입니다. 다운로드 소스 종류 하나에 대한 소스 리졸버는 존재합니다.
플레이어 대상 목록과 동작인스턴스, 서버, 다운로드, 플러그인, 계정 페이지는 현재 자리 표시자 데이터를 렌더링합니다. 인터페이스는 호스트 브리지 메서드가 마련될 때까지 명시적으로 미리보기 빌드입니다. 아직 동작하는 "인스턴스 만들기", "서버 추가", "로그인", "실행" 동작은 없습니다.
서버 런처 API(이 저장소)구현되었고 운영자가 활성화할 수 있음: 계정, 세션, 티켓, 카탈로그, 클라이언트 프리셋, 버전 게이트, 플러그인 권장 목록.

현재 런처 체크아웃이 게임 클라이언트를 설치하거나 실행할 것이라고 기대하지 마십시오. 아래 절들은 남은 흐름이 완성된 뒤에도 가이드가 정확하도록 소스를 기준으로 작성되었습니다.

런처 구하기 ​

런처는 자체 저장소와 릴리스 절차를 가진 별도 프로젝트입니다.

  • 저장소: FantasyTale.Launcher.
  • 라이선스: MIT.
  • 상태: README에 명시된 대로 초기 개발 단계입니다.

저장소에는 소스에서 빌드하는 방법(.NET 솔루션 빌드, x86 네이티브 훅 호스트의 Visual Studio 빌드, 프런트엔드의 npm 빌드)이 설명되어 있습니다. 공개된 설치 프로그램, 릴리스 자산, 다운로드 페이지에 대한 설명은 없으므로 이 가이드에서도 제공하지 않습니다. 개발자용 소스 빌드를 플레이어 설치로 취급하지 말고 런처 릴리스를 기다리십시오.

표에 대한 참고 사항:

  • 브랜치 열은 게임 정의의 지역 그룹입니다. 아래 messenger 표는 런처 정의가 있는 빌드만 다루며, 클라이언트 표의 나머지 profile은 아직 런처로 시작할 수 없습니다.
  • "메신저 모드"와 "로그인 모드"는 정의 필드입니다. stand-in은 런처의 메신저 호스트가 클라이언트의 메신저 호출에 직접 응답한다는 뜻이고, forward는 설치본이 이름을 바꿔 보관하는 원본 라이브러리로 호출을 전달한다는 뜻입니다. 로그인과 인증을 참고하십시오.
  • unverified로 표시된 세 빌드는 아직 검증된 로그인 공급자나 실행 인수가 없습니다. 런처 모듈은 해당 빌드의 실행 계획 생성을 거부하고, 빌드에 검증된 실행 인수가 없다고 보고합니다. 정의에는 나열되어 있지만 현재 체크포인트에서는 시작할 수 없습니다.
  • 기본 포트가 없는 빌드는 포트를 제공하는 서버 엔드포인트를 선택해야 합니다.
  • 빌드의 표시 이름과 연도는 표시용 데이터입니다. 식별에는 참여하지 않으며, 서버 프로필과 패킷 테이블이 사용하는 것은 id(<region>-<wire version>)입니다.
  • 런처는 현재 UI에 각 빌드의 id, 브랜치, 연도, 현지화된 이름을 보냅니다. 실행 파일, 메신저 모드, 로그인 모드, 지문, 기본 포트는 실행 및 세션 계약에서 사용하는 정의 데이터이며 플레이어가 편집하는 데이터가 아닙니다.

계획된 플레이어 흐름 ​

런처 설계는 다음 흐름을 설명합니다. 화면이 아직 실제 데이터에 연결되지 않았으므로, 각 단계를 현재 체크포인트의 상태와 함께 나열합니다.

단계저장소가 정의하는 내용상태
1. 런처 시작games 폴더에서 게임 카탈로그를 읽어 온 네이티브 창.구현됨
2. Bubble Fighter 선택Bubble Fighter가 유일하게 활성화된 게임이며, 다른 게임 항목은 선택할 수 없는 자리 표시자가 됩니다.구현됨
3. 클라이언트 인스턴스 생성인스턴스는 자체 폴더, 서버 바인딩, 플러그인 집합, 옵션을 가진 설치된 클라이언트 복사본 하나입니다. 따라서 같은 빌드의 복사본 여러 개가 공존할 수 있습니다.계획됨. 인스턴스 페이지는 현재 자리 표시자 행을 사용합니다
4. 빌드 선택빌드는 인스턴스의 속성입니다. 각 빌드 정의는 실행 파일, 실행 인수, 메신저 모드, 기본 플러그인을 제공합니다.계획됨. 정의는 있지만 빌드 선택기는 아직 없습니다
5. 서버 추가서버는 런처 API 기본 URL로 추가합니다. API가 없는 서버는 주소로 수동 추가할 수 있게 할 예정이며, 검증된 로그인과 자동 설치를 제공하지 않습니다.계획됨. 서버 페이지는 현재 자리 표시자 행을 사용합니다
6. 서버에 로그인서버 측 계정 등록, 로그인, 갱신, 로그아웃은 이미 존재합니다(서버 런처 API 참고).서버 측 구현됨, 런처 클라이언트 측 계획됨
7. 클라이언트 설치 또는 업데이트서버는 파일 크기와 해시가 포함된 빌드별 배포 매니페스트를 게시하도록 설계되었습니다. 런처는 모든 파일을 검증하고 파일 단위로 업데이트를 적용합니다.계획됨. 다운로드 엔진과 업데이트 확인은 아직 없습니다
8. 실행런처는 클라이언트 폴더에 session.toml을 쓰고, 인스턴스 폴더를 작업 디렉터리로 하여 실행 파일을 시작하며, 클라이언트가 종료되면 세션 파일을 삭제합니다.계약과 작성기 구현됨, UI에는 아직 실행 동작이 없음

이 흐름들이 완성되기 전까지 런처는 정의, 세션 계약, 네이티브 훅 호스트, 서버 API를 개발하고 테스트하는 데 유용하며, 플레이어용 설치본은 아닙니다.

인스턴스와 실행 ​

UI가 아직 실행을 시작할 수 없지만, 설계와 구현된 코드는 실행의 형태를 정의합니다.

  • 인스턴스는 자체 폴더에 있는 클라이언트 복사본 하나입니다. 빌드, 서버 바인딩, 활성화된 플러그인, 옵션을 담은 instance.toml을 가집니다. 인스턴스를 복제할 수 있어 같은 빌드로 서로 다른 서버나 플러그인 집합을 지원할 수 있습니다.
  • 빌드 정의가 지정한 실행 파일은 인스턴스 폴더 안에서 확인되어야 하며, 폴더를 벗어나는 경로는 거부됩니다.
  • 실행 인수는 {account}, {host}, {port} 자리 표시자가 있는 템플릿으로 빌드 정의에서 가져옵니다. 값이 없는 자리 표시자는 깨진 인수로 클라이언트를 시작하는 대신 실행 계획을 실패시킵니다.
  • 런처의 실행 계획은 서버 엔드포인트가 선택되면 이를 사용하고, 그렇지 않으면 빌드의 기본 포트를 사용합니다. 기본 포트가 없는 빌드는 포트를 제공하는 서버 엔드포인트가 필요합니다.
  • 매 시작 직전에 런처는 클라이언트 폴더에 session.toml을 임시 파일로 쓰고 이전 파일을 원자적으로 교체합니다. 훅 호스트는 클라이언트 로드 시 한 번 읽으며, 파일이 없으면 플러그인을 적용하지 않습니다.

세션 파일은 세션 파일과 로컬 데이터에서 다룹니다.

로그인과 인증 ​

로그인에는 서로 독립적인 두 계층이 있으며, 혼동해서는 안 됩니다.

  1. 런처 계정은 서버에 있으며 서버의 런처 API가 검증합니다. 액세스 토큰, 리프레시 자격 증명, 프로필 요약을 제공합니다. 운영자의 서버가 제어하는 부분입니다.
  2. 게임 로그인 신원은 게임 클라이언트가 로그인 요청에 담아 보내는 값입니다. stand-in 메신저 빌드에서는 런처의 메신저 호스트가 클라이언트의 패스포트 질의에 응답하여 그 신원을 제공합니다.

클라이언트가 신원을 받는 방법 ​

메신저 호스트는 다음 순서로 패스포트를 결정합니다(처음으로 비어 있지 않은 값이 사용됨).

  1. session.toml의 실행 티켓,
  2. 클라이언트 자체 로그인 대화 상자에 입력한 계정,
  3. session.toml의 런처 계정,
  4. 이전 런처 스크립트가 프로세스 환경으로 제공한 계정,
  5. guest.

클라이언트는 그 패스포트를 로그인 id로 보냅니다. 클라이언트가 자체 로그인 대화 상자를 사용하면 stand-in은 입력된 id를 기록해 반환하므로, 게임은 플레이어가 직접 입력한 값으로 로그인합니다.

런처 티켓 로그인과 게임 내 로그인 ​

이 가이드가 구분하는 두 가지 경우입니다.

  • 런처 티켓 로그인. 플레이어가 런처(서버 API)에 로그인하면, 런처가 API에 선택한 빌드의 일회용 실행 티켓을 요청하고 이를 session.toml에 기록합니다. 메신저 stand-in은 티켓을 패스포트로 반환하고, 게임 서버는 로그인 시 이를 계정 이름으로 취급하는 대신 티켓을 교환합니다. 티켓은 빌드 정의의 login 설정에 따라 두 경로로 전달됩니다. stand-in 빌드(kr-812, id-400, id-1809, tw-454. nmcogame stand-in이 티켓을 로그인 패스포트로 클라이언트에 전달)와 로그인 브리지 빌드(cn-404, cn-406, cn-774. 로그인 모듈이 티켓을 SDO 로그인 진입점으로 전달)입니다.
  • 게임 내 로그인. 런처 계정이나 티켓이 제공되지 않으면 클라이언트는 자체 로그인 흐름을 사용할 수 있습니다. stand-in 빌드에서는 stand-in이 클라이언트 로그인 화면에 입력된 id(로그인 호출의 클라이언트 대화 상자 변형)를 받아 패스포트로 반환하므로, 서버는 일반 계정 이름을 봅니다. forward 빌드에서는 원본 라이브러리가 클라이언트에 응답하므로 런처의 stand-in이 전혀 관여하지 않습니다. 빌드 정의의 gamewidget(cn-279, cn-324) 또는 hook(kr-1256) 로그인 모드가 그 경우를 설명하지만, 런처는 현재 체크포인트에서 그 공급자들을 구현하지 않습니다.

빌드 정의의 login 값은 데이터입니다. 런처 모듈은 현재 unverified만 강제하며(해당 빌드를 거부함), 그 외에는 공급자에 따라 분기하지 않습니다. 위의 대응은 선언된 메신저 모드와 호스트 코드를 따른 것이며, 현재 체크포인트에서 실제 클라이언트로 관찰된 것은 아닙니다.

티켓을 교환하는 위치 ​

각 로비 행의 authentication 옵션이 게임 로그인이 계정을 증명하는 방식을 정합니다. 기본 제공 프로필은 이 값을 BFF_LOGIN_AUTHENTICATION(${BFF_LOGIN_AUTHENTICATION:-ticket})에서 받으므로 변수 하나로 모든 빌드를 설정합니다.

authentication로그인할 수 있는 대상필요한 것
ticket(기본값)해당 빌드용으로 발급된 실행 티켓을 교환하는 로그인만 허용합니다. 빈 문자열이나 게임 내 로그인 창에 입력한 이름을 포함한 그 밖의 계정 문자열은 launcher ticket required로 연결을 닫고, 이미 사용했거나 알 수 없거나 빌드가 다른 티켓은 invalid launcher ticket으로 연결을 닫습니다.활성 상태의 launcher.http 행. 이 행이 없으면 로비가 authentication: ticket requires an active launcher.http row, which publishes ILauncherTicketService.와 함께 시작되지 않습니다.
open클라이언트가 보낸 모든 계정 이름. auto_create_players가 켜져 있으면 알 수 없는 이름으로 새 플레이어를 만듭니다. 시작할 때마다 경고를 기록합니다.없음. 신뢰할 수 있는 LAN이나 로컬 테스트에서만 사용하십시오.

open 모드에서는 기존 launcher_tickets 스위치(BFF_LAUNCHER_TICKETS)로 티켓 형태의 로그인을 일반 이름과 함께 교환할 수 있으며, ticket 모드에서는 교환이 항상 켜져 있습니다.

런처에서 티켓을 받는 빌드는 각 빌드 정의의 login 설정이 결정합니다. 현재 정의는 두 경로로 티켓을 전달합니다. 대체(stand-in) 빌드(kr-812, id-400, id-1809, tw-454)와 로그인 브리지 빌드(cn-404, cn-406, cn-774)입니다. 나머지 빌드는 아직 티켓을 받지 못합니다. kr-1256은 클라이언트를 직접 후킹하고, cn-279와 cn-324는 일반 위젯을 사용하며, cn-706, cn-717, cn-735의 로그인은 검증되지 않았습니다. 따라서 ticket에서는 이 빌드들의 플레이어가 로그인할 수 없습니다. 해당 정의가 티켓을 제공할 때까지 이 빌드들은 신뢰할 수 있는 네트워크에서 open으로 실행하십시오.

티켓이 증명하는 것과 증명하지 않는 것 ​

유효한 실행 티켓은 이 서버가 비밀번호 또는 갱신 자격 증명으로 인증된 런처 계정에 바로 그 빌드용으로 발급했고, 아직 사용되지 않았으며, 짧은 유효 기간 안에 있다는 것을 증명합니다. 티켓은 일회용이고 빌드에 묶이며 서버 프로세스 안에만 보관되고, 늦어도 이를 승인한 액세스 토큰과 같은 시점에 만료됩니다.

티켓은 클라이언트 바이너리가 수정되지 않았음, 게임 로그인 시점에 런처 버전이 허용 가능했음, 권장 플러그인이 설치되었음, 연결이 TLS를 사용했음을 증명하지 않습니다. 인스턴스별 launcher_login 정책(required, optional, none)은 서버 카탈로그에 광고되지만 게임 서버는 이를 강제하지 않으며, 강제 수단은 로비의 authentication 옵션입니다. ticket에서는 런처 계정 없는 직접 게임 로그인이 거부되고, open에서는 게임 로그인이 전혀 보호되지 않습니다.

세션 파일과 로컬 데이터 ​

런처와 서버는 서로 다른 데이터를 보관하며, 현재 체크포인트에서 구현된 런처 파일은 하나뿐입니다.

session.toml(실행마다) ​

  • 위치: 클라이언트 폴더의 게임 메신저 호스트 라이브러리 옆입니다(Bubble Fighter의 경우 nmcogame.dll). 매 시작 직전에 기록됩니다.
  • 스키마: 버전 1. 게임과 빌드 id, 브랜치, 인스턴스 id, 메신저 모드, 훅 로그 경로, 선택적 빌드 지문, 계정과 티켓이 있는 선택적 [login] 섹션, 서버 호스트와 포트가 있는 선택적 [endpoint], 그리고 순서가 있는 [[plugins]] 항목과 각 옵션을 담습니다.
  • 훅 런타임은 빌드 지문이 일치하지 않으면 플러그인을 거부하고 알 수 없는 키를 오류로 처리합니다. 이 검사는 세션 형식과 호환성을 검증하지만, 로컬 사용자가 파일을 수정하거나 삭제하거나 플러그인 항목을 생략하는 것을 막지는 않습니다.
  • 이 파일은 수명 동안 비밀로 취급해야 합니다. 계정 이름과 실행 티켓을 담을 수 있기 때문입니다. 런타임은 그 값을 절대 로그에 남기지 않으며, 런처는 클라이언트가 종료되면 파일을 삭제합니다. 파일을 복사하거나 편집하거나 공유하거나 클라이언트와 함께 패키징하지 마십시오.
  • 파일이 없어도 클라이언트는 시작됩니다. 플러그인을 로드하지 않고, 이름이 바뀐 원본 라이브러리의 존재 여부로 메신저 모드를 선택합니다.
  • 훅 런타임은 세션에 지정된 경로에 로그를 쓰며, 세션에 경로가 없으면 기본값인 %LOCALAPPDATA%\FantasyTale\BubbleFighter\logs\fthook.log에 씁니다. 로그는 크기가 제한됩니다. 파일은 열 때 잘리고, 크기 상한은 16 KiB에서 64 MiB 사이로 고정되며(세션 기본값은 1024 KiB), 긴 줄은 잘리고, 상한에 도달하면 마지막 표시 줄이 기록됩니다. 플러그인마다 결과 줄 하나를 기록하며 계정이나 티켓은 절대 기록하지 않습니다.

클라이언트 종료 시 삭제하는 것은 세션 작성기 계약의 일부입니다. 작성기와 정리를 호출하는 프로덕션 실행 흐름은 아직 로드맵에 남은 작업이므로, 이는 관찰된 수명 주기가 아니라 설계된 수명 주기로 취급하십시오.

런처 환경 설정과 정의 ​

  • 런처는 시작할 때 실행 파일 옆의 games 폴더에서 게임 및 클라이언트 빌드 정의를 읽습니다.
  • 인터페이스는 6개 언어로 제공되며, 선택한 테마, 강조 색 원본, 언어를 런처 창의 로컬 환경 설정으로 저장합니다. 이는 표시 환경 설정이며 계정이 아닙니다.
  • 런처는 현재 자체 로그가 없으며, 기록되는 유일한 로그는 위에서 설명한 클라이언트 내부의 네이티브 훅 로그입니다.
  • 인스턴스, 서버, 계정, 다운로드 파일 형식은 아직 구현되지 않았습니다. 이들은 해당 화면과 같은 로드맵 작업에 속합니다. 이 가이드는 그 파일 경로를 문서화하지 않습니다.

서버 측 런처 데이터 ​

  • 런처 계정은 서버의 계정 저장소에 PBKDF2-SHA256 비밀번호 해시로 저장되며, 런처는 비밀번호를 직접 검증하지 않습니다.
  • 지속성 있는 로그인은 현재 리프레시 자격 증명의 SHA-256 해시만 저장하므로, 비밀번호를 보관하지 않고도 세션을 갱신할 수 있고 지속성 공급자를 통해 서버 재시작 후에도 유지됩니다. 액세스 토큰과 실행 티켓은 메모리에만 있으며 재시작하면 사라집니다.
  • 기본 액세스 토큰 수명은 1800초, 리프레시 세션은 30일, 실행 티켓은 60초이며, 운영자는 검증된 범위 안에서 이를 조정할 수 있습니다.

훅 플러그인 ​

Bubble Fighter 클라이언트 패치는 훅 플러그인으로 제공됩니다. 플러그인은 plugin.toml이 있는 폴더로, 파일이 id, 종류, 호환성, 옵션을 선언합니다. 데이터 패치에는 컴파일러가 필요하지 않습니다. 런처에는 현재 데이터 플러그인 세 개가 포함되어 있습니다.

플러그인목적적용되는 빌드필수
bubblefighter.fantasy.font-weight중국판 빌드의 글꼴 두께를 모든 언어 그룹에 적용하여, 다른 지역 클라이언트의 중국어 텍스트가 중국판 빌드처럼 렌더링되게 합니다.kr-812, cn-706, cn-717, id-400, id-1809아니오
bubblefighter.fantasy.no-file-verify클라이언트의 구성 테이블 무결성 비교기가 일치한다고 보고하게 하여 수정된 구성 테이블이 로드되게 합니다. 팩의 멤버별 해시는 여전히 적용되므로, 편집한 테이블은 올바르게 다시 패킹해야 합니다.kr-1256, 그리고 아직 런처 빌드 정의가 없는 kr-710아니오
bubblefighter.fantasy.kr1256-shop-gates최종 한국 클라이언트가 비활성화하는 작업 표시줄 상점 버튼과 공유 기능 진입점을 다시 활성화합니다.kr-1256예, required_on = kr-1256

훅의 의도된 동작 방식:

  • 플러그인은 빌드 id, 브랜치 선택자, 또는 모든 빌드로 빌드 호환성을 선언하며 빌드를 제외할 수도 있습니다. 현재 빌드를 나열하지 않은 플러그인은 사용할 수 없음으로 건너뛰며, 런타임은 런처와 독립적으로 이를 거부합니다.
  • 필수로 표시된 플러그인은 해당 빌드에서 비활성화할 수 없습니다. 필수 플러그인이 실패하면 클라이언트에 경고 메시지 상자 하나가 표시되고("Required client plugins could not be applied; the game may not work correctly."), 훅 로그에는 플러그인마다 결과 줄이 기록됩니다.
  • 플러그인은 인스턴스별로 활성화되며 옵션과 함께 [[plugins]] 항목으로 session.toml에 기록됩니다. 새 인스턴스는 빌드의 기본 플러그인 목록으로 시작하며, 현재 체크포인트에서는 정의 아홉 개 모두에서 이 목록이 비어 있습니다.
  • 런처에서 플러그인을 설치, 전환, 구성하는 플러그인 관리자는 아직 구현되지 않았으며, 플러그인 페이지는 여전히 미리보기입니다. 클라이언트나 그 실행 파일을 직접 편집해 플러그인을 설치하는 것은 지원되는 경로가 아닙니다. 현재 체크포인트의 런타임은 데이터 플러그인만 적용하며, 네이티브 종류의 플러그인은 아직 네이티브 플러그인을 지원하지 않는다는 메시지와 함께 거부합니다.

런처의 나머지 부분과 마찬가지로 네이티브 런타임과 이 플러그인들은 네이티브 테스트로 검증되지만 현재 체크포인트에서 실제 게임 클라이언트로 검증되지는 않았습니다. 세 플러그인 모두 최소 훅 런타임 버전 3.0.0을 선언하며 데이터 전용 패치 플러그인이고, 구성 가능한 옵션을 정의한 플러그인은 없습니다.

서버 런처 API ​

서버는 선택적 launcher.http 플러그인 행을 통해 런처 API를 노출할 수 있습니다. 이는 관리 API와 별개의 공용 HTTP 리스너입니다. 자체 주소와 /v1 아래의 자체 라우트를 가지며, 관리자 라우트나 베어러 토큰 관리는 없습니다. 런처 계정, 지속성 있는 로그인, 실행 티켓, 클라이언트 프리셋 카탈로그, 그리고 런처가 강제해야 하는 호환성 정책을 제공합니다.

행 활성화 ​

  • 코어 번들은 이 행을 비활성화 상태로 제공합니다. all 프로필은 이 행을 활성화하면서 배포 변수 BFF_LAUNCHER_LISTEN, BFF_LAUNCHER_TICKET_SECONDS, BFF_LAUNCHER_HOST_POLICY, BFF_LAUNCHER_REGION을 유지합니다. 기본값은 각각 127.0.0.1:8090, 600, auto, 빈 지역입니다. 이후 set 패치로 카탈로그 구성을 유지하면서 개별 설정을 재정의할 수 있습니다.
  • 이 플러그인은 런처 계정 저장소와 런처 세션 저장소를 게시하는 활성 지속성 공급자가 필요합니다. 메모리, SQLite, MySQL 세 공급자 모두 이를 제공합니다. all 프로필은 프로세스 로컬 메모리 공급자를 사용하므로 재시작하면 계정과 로그인이 초기화됩니다. 지속성이 필요한 배포에서는 SQLite나 MySQL을 사용해야 합니다.
  • 이 행은 admin.http와 독립적이며, 하나를 활성화하거나 비활성화해도 다른 하나는 바뀌지 않습니다.

클라이언트 정책(client_policy) ​

클라이언트 정책은 이 서버로 실행할 때 어떤 플러그인을 반드시 사용해야 하는지, 사용할 수 있는지, 사용하면 안 되는지를 런처에 알려 줍니다. 두 목록으로 구성되며 항목 수에는 제한이 없습니다.

  • sources: 스토어 카탈로그. 각각 소문자 name, kind(http 또는 alist), base_url(자격 증명, 쿼리, 프래그먼트가 없는 HTTP(S)), catalog_path를 가집니다.
  • plugins: 플러그인마다 하나의 항목. 스토어 id, 선택적 name과 description(WebUI에만 표시되며 런처로 보내지 않음), 그리고 rules를 가집니다.

모든 규칙에는 해당 플러그인 안에서 고유한 id, type, 선택적 builds 목록(비어 있으면 모든 빌드)이 있습니다. 규칙 유형은 다음과 같습니다.

유형필드런처 동작
require없음플러그인이 설치되고 활성화될 때까지 실행을 거부하고 설치를 제안합니다.
disable없음이 서버로 실행할 때 저장된 선택은 바꾸지 않고 플러그인을 끕니다. 빌드 자체가 요구하는 플러그인은 끌 수 없으며 이 경우 실행을 거부합니다.
recommendsources클라이언트와 규칙마다 한 번 플러그인을 추천하고 지정한 소스에서 설치합니다(목록이 비어 있으면 선언된 모든 소스 허용).
min_versionversion활성화된 플러그인이 이 버전보다 낮으면 실행 전에 업데이트해야 합니다.
max_versionversion활성화된 플러그인이 이 버전보다 높으면 소스에서 허용되는 가장 높은 버전으로 교체합니다. 사용할 수 있는 버전이 없으면 실행을 거부합니다.
latest없음실행 전에 활성화된 플러그인을 최신 버전으로 업데이트합니다.

버전은 엄격한 SemVer입니다. 한 플러그인의 두 규칙은 빌드 범위가 겹치고 다음 중 하나에 해당하면 충돌합니다. 유형이 같은 경우, 한쪽이 disable인 경우, 한쪽이 latest이고 다른 쪽이 max_version인 경우, 또는 min_version이 max_version보다 높은 경우(같으면 한 버전으로 고정)입니다. 충돌하거나 형식이 잘못되었거나 알 수 없는 규칙이 있으면 해당 행이 시작되지 않습니다. 규칙 유형을 모르는 런처는 이 서버로의 실행을 거부하고 플레이어에게 런처 업데이트를 요청합니다.

카탈로그와 모든 로그인 응답에는 최소 런처 버전과 clientPolicy(version, sources, plugins) 정책이 포함되며, 규칙의 version이나 sources는 해당 유형이 사용할 때만 들어갑니다. 실행에는 플레이어가 로그인할 때 받은 정책이 사용되고, 카탈로그의 사본은 로그인 전에 표시하는 용도입니다. 이 정책은 호환 런처를 구성할 뿐이며 클라이언트 무결성을 증명하거나 게임 로그인 시 로드된 모드를 검사하지 않습니다. 관리 API는 WebUI 클라이언트 정책을 참조하세요.

클라이언트 프리셋(instances) ​

각 프리셋은 선택 가능한 클라이언트 인스턴스 하나를 광고합니다.

필드의미
id안정적인 프리셋 식별자입니다. 문자, 숫자, 하이픈을 사용합니다.
build클라이언트 빌드 id입니다. 예: kr-1256.
name현지화된 표시 이름입니다. en 항목이 필요합니다.
release_version이름 아래에 표시되는 선택적 릴리스 레이블입니다.
client_languages선택적이며 권위 있는 클라이언트 언어 선택지 목록입니다.
host / port런처가 연결하는 공개 게임 엔드포인트입니다. 포트는 필수입니다.
launcher_loginrequired, optional, none: 런처 인증에 대한 서버의 광고 선호입니다. 이는 카탈로그 데이터이며, 게임 서버의 실제 강제 수단은 로비의 authentication 옵션입니다.
download_source클라이언트 패키지의 선택적 다운로드 소스입니다. kind(http 또는 alist), base_url, catalog_path, package_id를 가집니다. URL에는 자격 증명, 쿼리, 프래그먼트를 허용하지 않습니다.

프리셋은 광고되는 데이터이며, 런처는 아직 프리셋을 사용하지 않습니다. 서버는 프리셋의 build를 자체 구성된 프로필과 대조하지 않으므로, 오타가 있으면 티켓을 절대 교환할 수 없는 프리셋이 만들어집니다. 이 휴대용 프리셋은 설계의 로컬 인스턴스 파일이 아닙니다. 플레이어의 서버 바인딩과 플러그인 선택을 담을 로컬 instance.toml은 아직 존재하지 않습니다.

라우트 ​

모든 라우트는 /v1 아래에 있으며 런처 리스너에서만 제공됩니다.

라우트메서드인증목적

버전 게이트와 HTTP 426 ​

minimum_launcher_version이 설정되면 등록, 로그인, 갱신, 티켓 발급에 해당 버전 이상의 런처가 필요합니다. 버전이 없거나, 파싱할 수 없거나, 더 오래된 버전의 요청은 다음 JSON 본문과 함께 HTTP 426 Upgrade Required를 받습니다.

json
{ "error": "launcher_update_required", "minimumLauncherVersion": "<configured version>" }

카탈로그 엔드포인트 자체에는 게이트가 적용되지 않으므로, 런처는 로그인하기 전에 항상 요구 사항을 읽을 수 있습니다. 현재 체크포인트의 런처는 이 응답을 파싱하지도, 버전을 보내지도 않습니다. 따라서 이 게이트는 앱 내 업데이트 안내가 아니라 서버 측 거부로 유효합니다.

JSON 호환성 ​

런처 API는 새 클라이언트에 의도적으로 관대하고, 자기가 소비하는 것에는 엄격합니다.

  • 알 수 없는 최상위 JSON 필드는 무시되므로, 더 새로운 런처가 구버전 서버에 추가 필드를 보내도 실패하지 않습니다.

  • 요청은 여전히 JSON 객체여야 합니다. 중복된 최상위 키, 잘못된 형식, 누락된 필수 값, 유효하지 않은 사용자 이름, 본문과 불일치하는 버전 헤더, 너무 큰 본문, 너무 깊은 중첩은 {"error":"invalid_request"}와 함께 HTTP 400으로 거부됩니다.

  • 알려진 필드는 이를 사용하는 처리기가 검증하며, 서버가 광고하지 않는 빌드는 unsupported_build로 거부됩니다.

  • 이 관대함은 JSON API에만 적용됩니다. 플러그인 행 구성은 계속 엄격하여, 알 수 없는 YAML 키는 시작 시 바인딩에 실패합니다.

  • 런처 API에는 현재 체크포인트에서 비밀번호 변경, 비밀번호 재설정, 계정 삭제 라우트가 없습니다. 운영자는 등록을 비활성화하고 서버 측에서 계정을 차단할 수 있지만, 런처에는 두 동작을 위한 화면이 없습니다.

응답에는 Cache-Control: no-store가 포함됩니다. 리스너는 설계상 일반 HTTP이므로, 런처가 네트워크를 통해 연결할 때는 자체 TLS 종료 뒤에 두고, 그렇지 않을 때는 루프백에 유지하십시오. API는 게임 클라이언트, 그 파일, 업데이트를 절대 제공하지 않습니다. 다운로드 소스는 런처의 향후 클라이언트 설치를 위한 데이터로 광고될 뿐 서버가 프록시하지 않습니다.

구성 예시 ​

이 행은 보통 프로필 패치에서 활성화합니다. 이 예시는 자리 표시자와 합성 값만 사용합니다.

yaml
- replace:
    id: launcher.http
    disabled: false
    config:
      listen: "127.0.0.1:8090"
      name: "Example Community Server"
      region: "KR"
      minimum_launcher_version: "1.4.0"
      client_policy:
        sources:
          - name: "community"
            kind: "http"
            base_url: "https://store.example.com"
            catalog_path: "FantasyTale/source.toml"
        plugins:
          - id: "bubblefighter.fantasy.kr1256-shop-gates"
            rules:
              - { id: "needed", type: "require", builds: ["kr-1256"] }
              - { id: "floor", type: "min_version", builds: ["kr-1256"], version: "1.2.0" }
          - id: "example.optional-overlay"
            rules:
              - { id: "offer", type: "recommend", sources: ["community"] }
      instances:
        - id: "kr-1256-main"
          build: "kr-1256"
          name:
            - language: "en"
              text: "KR 2026"
            - language: "zh-CN"
              text: "KR 2026"
          release_version: "1.0.0"
          host: "game.example.com"
          port: 7100
          launcher_login: "required"

런처 행이 이미 교체되어 리스너 설정이 제거된 프로필에서는 set 패치로 리스너 설정을 명시적으로 다시 추가하십시오.

yaml
- set:
    id: launcher.http
    config:

Nirinsou Link ​

Fantasy Tale Nirinsou Link(줄여서 Nirinsou)는 실행 중인 런처와, 그 런처가 게임을 실행한 서버 사이의 선택형 WebSocket 채널입니다. 게임 위에 뜨는 런처 팝업처럼 원래 게임 클라이언트에 패킷이 없는 기능을 전달합니다. 게임 연결 자체는 바뀌지 않으며, Nirinsou 없이 실행해도 이전과 똑같이 플레이됩니다.

실행이 묶이는 방식 ​

  1. /v1/launch가 실행을 열고 게임 티켓과 Nirinsou 권한을 돌려줍니다. 게임 티켓에는 그 실행이 기록됩니다.
  2. 런처는 서브프로토콜 fantasytale.companion.v1과 Authorization: Bearer 티켓으로 GET /companion/v1을 업그레이드합니다. 티켓은 한 번만 쓸 수 있으며, 재연결할 때는 /v1/companion/tickets로 새 티켓을 받고 새 연결이 이전 연결을 대신합니다.
  3. 런처는 빌드, 실행 ID, 언어, 지원하는 메시지 형식을 담은 companion.hello를 보내고, 서버는 양쪽이 모두 지원하는 형식과 상태 pending_game을 담은 companion.welcome으로 답합니다.
  4. 게임 로그인이 게임 티켓을 사용하면 실행이 그 게임 연결에 묶이고 런처는 상태 connected를 받습니다. 서버 메시지는 그 뒤에만 보냅니다.
  5. 게임 연결이 닫히면 실행이 끝나고 Nirinsou 연결도 닫힙니다.

게임이 끝내 로그인하지 않은 실행은 pending_seconds 뒤에 버립니다. 모든 메시지는 kind, id, type, 스키마 버전, payload를 가진 JSON이며, 형식이 틀리거나 중복되거나 협상되지 않았거나 너무 빠른 메시지는 이유 코드와 함께 연결을 닫고, 런처는 새 티켓으로 다시 연결합니다.

리스너는 평문 ws입니다. 네트워크로 접속할 때는 런처 API와 마찬가지로 TLS 종료 뒤에 두고 public_url을 wss로 설정하세요.

문제 해결 ​

다음은 현재 코드에 존재하는 실패 경로입니다. 현재 체크포인트의 런처에는 앱 내 복구 동작이 없으며, 복구란 메시지나 로그를 읽고 입력을 바로잡는 것을 뜻합니다.

증상확인가능한 원인과 해결
launcher.http 행이 Pending에 머물거나 실패함관리 API의 /api/plugins와 시작 로그런처 계정 저장소와 세션 저장소를 게시하는 지속성 공급자가 없습니다. 지속성 공급자를 정확히 하나 활성화하십시오.
로비가 authentication: ticket requires an active launcher.http row와 함께 시작되지 않음시작 오류티켓 인증(기본값) 또는 launcher_tickets가 켜져 있지만 티켓 서비스를 게시하는 활성 launcher.http 행이 없습니다. 런처 행을 활성화하거나, 신뢰할 수 있는 LAN에서 BFF_LOGIN_AUTHENTICATION=open을 설정하십시오.
로그인 직후 launcher ticket required로 연결이 끊김서버 로그로비가 authentication: ticket으로 실행 중인데 클라이언트가 일반 계정 이름을 보냈습니다. 런처 없이 실행했거나, 해당 빌드가 아직 런처에서 티켓을 받지 못합니다. 런처로 실행하거나 신뢰할 수 있는 LAN에서 open을 사용하십시오.
게임이 invalid launcher ticket과 함께 연결을 닫음티켓이 이 서버에서 이 정확한 빌드에 대해 발급되었고 사용되지 않았는지 여부티켓이 비활성화되었거나, 사용되었거나, 만료되었거나, 다른 빌드에 발급되었거나, 발급 이후 런처 행이 재시작되었습니다. 런처를 재시작하고 다시 로그인한 뒤 다시 실행하십시오.
구버전 런처가 HTTP 426을 받음행의 minimum_launcher_version과 런처 버전런처가 구성된 최소 버전보다 낮습니다. 런처를 업데이트하거나 테스트를 위해 최소 버전을 비우십시오. 현재 런처는 아직 업데이트 안내를 표시하지 않습니다.
HTTP 400 invalid_request요청 본문과 버전 필드잘못된 JSON, 중복된 최상위 키, 잘못된 형식, 유효하지 않은 사용자 이름, 또는 헤더/본문 버전 불일치입니다.
HTTP 401 unauthorized액세스 토큰 수명과 서버 재시작베어러가 만료되었거나 서버가 재시작되어 메모리 내 베어러가 사라졌습니다. 다시 로그인하십시오. 리프레시 자격 증명이 세션을 갱신할 것입니다.
HTTP 429 또는 503요청 속도, 동시 요청, 보관 세션서버의 제한된 인증 한도에 도달했습니다. 나중에 다시 시도하거나 의도적으로 한도를 높이십시오.
빌드가 "has no verified launch arguments yet"를 보고함빌드의 login 값빌드가 login = "unverified"로 정의되어 있습니다. 검증된 로그인 모드가 있는 빌드를 사용하십시오.
클라이언트가 "The launcher session file is invalid; no client plugins were loaded."를 표시함메시지 상자 텍스트와 클라이언트 폴더session.toml이 오래되었거나, 직접 편집되었거나, 형식이 잘못되었습니다. 런처를 통해 클라이언트를 시작해 새 세션이 기록되게 하십시오. 세션을 직접 편집하지 마십시오.
클라이언트에 필수 플러그인 경고가 표시됨훅 로그의 결과 줄필수로 표시된 플러그인이 실패했거나 해당 빌드에서 사용할 수 없습니다. 그 플러그인 id의 로그 줄을 읽고 옵션이나 호환성을 수정하십시오.
런처 미리보기에서 클라이언트를 시작할 수 없음—현재 체크포인트에서는 실행이 구현되지 않았으며, 미리보기의 실행 버튼에는 동작이 없습니다.
클라이언트가 예상한 플러그인 없이 시작됨세션의 로그 경로에 있는 훅 로그(기본값 %LOCALAPPDATA%\FantasyTale\BubbleFighter\logs\fthook.log)세션이 기록되지 않았거나, 플러그인을 해당 빌드에서 사용할 수 없거나, 패치가 일치하지 않았습니다. 플러그인 id의 결과 줄을 읽으십시오. 런처에는 로그 뷰어와 복구 동작이 없습니다.

런처 API 외의 서버 측 실패는 문제 해결을 참고하십시오.

서버 공개 정보와 접속 허용 정책 ​

GET /v1/catalog는 motd, iconUrl, images, onlinePlayers, playerLimit, state, whitelist, rosterEnabled를 담은 presentation도 반환합니다. launcher.http 행의 motd, icon_url, images, show_online_players, player_limit, maintenance, whitelist_enabled, roster_enabled로 설정합니다. 기본값은 접속 제한 없음, 인원 제한 없음, 공개 명단 활성화입니다. 세션 서비스를 사용할 수 없으면 인원은 null이고, show_online_players: false이면 -1입니다. 인증된 게임 플레이어만 계정별로 집계하고, 종료된 연결과 확인된 경기 연결은 제외합니다. 영구 최고 인원 저장소가 연결되지 않아 과거 최고 인원은 제공하지 않습니다.

인증 없이 호출하는 GET /v1/players는 schema: 1, enabled, players, truncated를 반환합니다. 플레이어별 필드는 name과 level뿐입니다. roster_enabled: false이면 세션 레지스트리를 읽지 않고 빈 명단을 반환합니다. 활성화 상태에서 레지스트리가 없으면 HTTP 503 player_state_unavailable입니다. max_roster_players는 응답 크기를 제한하며 기본 1000, 범위 1–10000입니다. truncated: true는 실제 접속자가 더 많다는 뜻입니다. 인원수와 명단 공개는 별도 설정입니다. HTTP 플러그인은 ISessionRegistry와 IPlayerSession.LoginConnectionId를 통해 실제 로그인 연결을 식별합니다. 플레이어 상태를 공유하는 경기 연결과 이 식별자를 제공하지 않는 플러그인 세션은 공개 명단에서 제외됩니다. 따라서 티켓 발급이 티켓을 사용하는 로비 및 경기 서비스의 시작을 기다리지 않습니다.

클라이언트 프리셋은 선택적 protocol_version(1–65535)과 patch_version(최대 64자)을 지원하며 기존 build, releaseVersion, clientLanguages, downloadSource와 함께 protocolVersion, patchVersion으로 출력합니다. 생략한 값은 알 수 없는 상태로 유지됩니다. 이 표시 필드는 아직 실행 요청의 클라이언트 버전을 검증하지 않습니다.

maintenance: true는 로그인과 새 티켓 발급을 HTTP 503 server_maintenance로 거부합니다. 선택적 maintenance_start, maintenance_end, maintenance_description은 각각 maintenanceStart, maintenanceEnd, maintenanceDescription으로 반환됩니다. 날짜는 안내용이며 자동 예약 기능이 아닙니다. whitelist_enabled: true는 whitelist의 계정명을 대소문자 구분 없이 검사합니다. 중복 없는 계정 최대 4096개를 지원하며 미등록 계정은 HTTP 403 not_whitelisted입니다. 양수 player_limit는 시작 시 세션 서비스가 필요합니다. 정원에 도달하면 새 플레이어는 HTTP 503 server_full을 받지만 이미 접속한 계정은 대체 티켓을 받을 수 있습니다. 이 기능은 런처 접속 검사이며 원자적 자리 예약이 아닙니다. 직접 게임 연결과 티켓 교환에서는 아직 이 설정을 다시 검사하지 않습니다.

인증 거부는 JSON error에 HTTP 401 account_not_found, wrong_password, account_banned를 반환합니다. 올바른 비밀번호를 확인한 뒤에만 이용 제한 상태를 알리며 확인되지 않은 제한 사유는 만들지 않습니다. 베어러 실패는 기존 unauthorized입니다. 가입 비활성화는 HTTP 403 registration_disabled, 요청 제한은 HTTP 429 rate_limited, 세션 용량 부족은 HTTP 503 authentication_capacity입니다. 점검 중에도 세션 갱신과 로그아웃이 가능합니다. 네트워크 오류는 호출자가 처리하며 서버 인증 오류로 반환하지 않습니다.

같은 POST /v1/launch 요청에 선택적으로 release_version, patch_version, launcher_language, native_language, client_language를 보낼 수 있습니다. 버전 레이블을 보내는 경우 공백만 있는 문자열이나 제어 문자를 포함해서는 안 되며 최대 64자입니다. 이 레이블은 배포 버전 설명이며 프로토콜 버전으로 해석하거나 공지된 레이블과 비교하지 않습니다. 언어를 보내는 경우 정확히 zh-CN, zh-TW, ko, en, id, vi 중 하나여야 합니다. 잘못된 알려진 필드는 티켓 슬롯을 사용하기 전에 HTTP 400 invalid_request를 반환합니다. 기존 요청은 다섯 필드를 모두 생략할 수 있습니다. 알 수 없는 최상위 필드는 계속 무시하고 중복 키는 거부합니다. 티켓 발급에 성공하면 플러그인 로거에 build와 이 설명 정보를 기록하며 계정 이름, 베어러, 티켓은 기록하지 않습니다. 이 정보로 설치된 클라이언트의 버전, 언어 또는 무결성을 증명할 수는 없습니다.

게임 연결에서 실행 티켓을 사용하면 launcher_language가 방 명령과 자동 시작 알림을 포함한 서버 알림의 언어를 선택합니다. 클라이언트 지역, native_language, client_language는 이 알림 언어를 선택하지 않습니다. 언어 정보나 번역이 없으면 현지화 플러그인의 default_language를 사용합니다. launcher_languages는 UI 태그를 리소스 이름에 연결하며, 기본 설정은 zh-CN을 zh-Hans에, zh-TW를 zh-Hant에 연결합니다. 나머지 태그는 리소스 이름과 직접 일치합니다. 현재 베트남어 사전은 없으므로 vi는 배포 기본 언어를 사용합니다. 실행 티켓 언어 정보가 없는 연결도 기본 언어를 사용합니다. 언어 설정은 연결이 닫힐 때까지 유지되며 최초 캐릭터 생성 중에도 유지됩니다.
